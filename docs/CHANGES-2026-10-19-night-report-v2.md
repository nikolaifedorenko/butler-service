# Изменения 19.10.2026 — ночной отчёт v2, этап 1: зоны, объекты, чек-лист зоны

Задание владельца от 19.10.2026: «в реальности очень много зон и много однотипных
объектов» — плоский список областей ночного отчёта не масштабируется. Согласован
прототип (`docs/PROPOSAL-NIGHT-REPORT-V2.md` — план и модель данных,
`docs/prototypes/night-report-v2.html` — кликабельный макет всех экранов,
`docs/prototypes/night-report-v2.smoke.mjs` — его автотест в jsdom, 110 проверок)
и получены решения владельца.

Этот документ описывает **этап 1** (реализован) и план остальных этапов.

## Решения владельца (19.10.2026)

1. Навигация: **зоны → объекты → чек-лист объекта**.
2. Чек-лист **общий на зону**, но с возможностью правок под объект (индивидуальные
   особенности).
3. У пункта — **ответственная служба** (Батлер-сервис, Хозяйственная служба, Техническая
   служба, IT-департамент, можно добавлять); у службы — **способ доставки** чекбоксами
   (чат и/или письмо), почтовый ящик и чаты.
4. Консолидированный отчёт с недостатками: **отправляем всё скопом или выбираем**, что уйдёт.
5. Отправлять может **любой** пользователь обхода; отправленное **помечается**; отправка
   **только вручную**.
6. **«Не отмечено» включается** в отчёт (отдельным блоком «Не проверено»).
7. Если недостаток **исправили после отправки — ничего не отправляем** (ни «исправлено»,
   ни отзыва сообщения).
8. В тексте сообщения — **ночные батлеры смены**; плейсхолдер `{deadline}` не нужен.
9. Лимиты и срок хранения **видео** настраиваются так же, как у фото (50 МБ — лимит
   Telegram Bot API).
10. Список чатов **получаем в настройках Telegram** (getUpdates), **закрепляем за службой**
    в её карточке.
11. Почта — через **MS Exchange** (позже включим приложение в домен: внутренний релей
    или SMTP AUTH, в перспективе Graph/EWS).
12. **Электрокары — отдельный шаг**, в зоны не переносим.

## Что сделано (этап 1)

### Навигация: три уровня вместо плоского списка

* **Уровень 1 — зоны**: карточки зон с прогресс-баром, счётчиками «закрыто / в работе /
  свободно / замечаний / не отмечено», переход «Объекты зоны →». Шаг «Проверка
  электрокаров» — отдельной панелью (решение 12).
* **Уровень 2 — объекты зоны**: список объектов со статусом, ведущим, прогрессом пунктов,
  фильтры («Все / Свободны / В работе / Закрыты / С замечаниями»), поиск, кнопка
  «К первому незакрытому».
* **Уровень 3 — чек-лист объекта**: прежняя карточка области (ОК/Не ОК, комментарий, фото,
  перехваты, закрытие с неотмеченными пунктами после подтверждения).
* Хлебные крошки на всех уровнях; состояние навигации сохраняется при автообновлении
  (поллинг 60 с) и после отметок.

### Чек-лист задаётся на зону

* Новая таблица **`zone_checklist_items`** — шаблон чек-листа зоны: один пункт
  («Витражи закрыты») действует для всех 12 вилл зоны.
* **Почему отдельная таблица, а не `zone_id` в `checklist_items`:** в существующих базах
  `checklist_items.area_id NOT NULL`, и ослабление потребовало бы пересоздания таблицы
  вместе с FK (на PostgreSQL — с каскадом ограничений). Проект держится «лёгких» миграций
  (`ADD COLUMN` / `CREATE TABLE`, см. ADR-0002), поэтому шаблон зоны живёт своей таблицей.
* `checklist_items` сохраняет прежний смысл: **свой пункт одного объекта**
  («Детская кроватка установлена» только у «Виллы 4001»).
* Эффективный чек-лист объекта (`night.effective_items`): шаблон зоны + свои пункты −
  отключённые у объекта, со своими формулировками. Он **снимком** попадает в отчёт
  (`night_area_sections.snapshot_json` → `{"id","src":"zone"|"area","text","overridden"}`),
  поэтому правки справочников не меняют закрытые смены и не теряют отметки.
* Ответ пункта хранит источник: `night_check_items.zone_item_id` (пункт шаблона зоны)
  или `item_id` (свой пункт объекта).

### Индивидуальные особенности объекта

* Новая таблица **`checklist_overrides`** (`area_id` + `zone_item_id`, `text`, `disabled`,
  уникальность по паре): своя формулировка и/или отключение пункта шаблона у конкретного
  объекта. В справочнике у пункта шаблона виден счётчик «индивидуально: N».
* Правки применяются **только к ещё не начатым объектам** в открытых сменах
  (`night.refresh_free_section`): начатые и закрытые не перекраиваются, чтобы не потерять
  отметки батлера.

### Зоны

* Новая таблица **`night_zones`** (название, порядок, активность). Зоны **вырастают из
  прежних «категорий»** областей: `migrate_night_zones()` создаёт по зоне на каждое
  значение `night_areas.category` и проставляет `night_areas.zone_id`; миграция
  идемпотентна (тест `test_migraciya_zon_iz_kategoriy_idempotentna`).
* `night_areas.zone_id` — принадлежность объекта зоне; `category` сохранена (закрытые
  отчёты и прежние выгрузки не теряют группировку).
* Снимок зоны в отчёте: `night_area_sections.zone_id` + `zone_name`. Переименование зоны
  обновляет название только в **открытых** сменах; закрытые остаются снимком
  (тест `test_pereimenovanie_zony_ne_trogaet_zakrytuyu_smenu`).
* Отключение зоны мягкое: объекты и история сохраняются.
* Прогресс по зонам считается из уже сериализованных областей отчёта
  (`night.zones_progress`) — без дополнительных запросов к БД.

### API

```
GET    /api/night/zones                        зоны + число объектов и пунктов шаблона (видно всем ролям)
POST   /api/night/zones                        добавить зону                     (менеджмент)
PUT    /api/night/zones/{id}                   переименовать/порядок/активность  (менеджмент)
DELETE /api/night/zones/{id}                   отключить зону                    (менеджмент)
GET    /api/night/zones/{id}/items             шаблон чек-листа зоны + объекты зоны
POST   /api/night/zones/{id}/items             пункт шаблона (попадает во все объекты зоны)
PUT    /api/night/zone-items/{id}              правка пункта (текст уезжает в незакрытые смены)
DELETE /api/night/zone-items/{id}              мягкое удаление пункта шаблона
GET    /api/night/areas/{id}/checklist         эффективный чек-лист объекта (шаблон + правки + свои)
PUT    /api/night/areas/{id}/overrides/{zone_item_id}   индивидуальная правка (формулировка/отключение)
DELETE /api/night/areas/{id}/overrides/{zone_item_id}   сброс правки к шаблону зоны
```

Расширены существующие: `POST/PUT /api/night/areas` и `POST /api/night/areas/bulk`
принимают `zone_id`; `GET /api/night/areas` отдаёт `zone_id`, `zone_name` и
`effective_total`; `GET /api/night/reports/{id}` — список `zones` с прогрессом, а у
областей — `zone_id`/`zone_name`.

Права: новых не добавляли. Чтение — `night.view` (есть у всех ролей), правка справочников —
`require_manager` (admin/manager/supervisor). Побочно исправлено: флаг `can_edit` в
`/api/night/zones` и `/api/night/areas` теперь соответствует фактическому правилу записи
(`principal.is_manager`), раньше супервайзеру флаг приходил `false`, хотя API правку
разрешало.

### Уточнение к плану (19.10.2026, по итогам показа прототипа)

**Настройки Telegram и e-mail вынесены в ОБЩИЕ настройки приложения** — экран
«Настройки → Чаты и Почта» (`#/settings/notify`, группа «Служебное», право
`settings.edit`), а не в справочник ночного обхода. Название экрана выбрал владелец. Причина: владелец планирует ту же доставку и в других разделах
(электрокары, заявления, закрытие периода, отметки). Следствия для этапов 3–5:

* транспорт и учётные данные — общие: пакет `app/notify/`
  (`transports/telegram.py`, `transports/email.py`, `templates.py`, `dispatch.py`,
  `recipients.py`), который **не знает** про ночной отчёт;
* у каждого раздела своё: **шаблон сообщения** (хранится по доменам: `night`, `cars`, …),
  правило выбора получателей и экран отправки; у ночного отчёта получатели — ответственные
  службы, у других разделов будут свои;
* **журнал отправок общий**: таблица `notify_dispatches` с `domain` и `ref_id`
  (вместо `night_dispatches`) — один экран журнала с фильтром по разделу;
* права: чтение и правка общих настроек — `settings.edit`; отправка — как договорились,
  любой пользователь обхода (новое право не вводим);
* прототип обновлён под это решение: экран «Интеграции и шаблоны» переехал в
  «Настройки → Чаты и Почта», добавлена таблица «Кто использует доставку»,
  шаблоны переключаются по разделам, в журнале появилась колонка «Раздел».

Открытых вопросов по этапам нет; на этапе 4 понадобятся рабочие данные: токен бота
(и добавление бота в группы служб) и параметры коннектора Exchange (адрес релея, порт,
разрешённый отправитель).

## Хотфикс (19.10.2026): httpx — обязательная зависимость, «Чаты и Почта» больше не падает в 500

Боевой случай владельца: локальный запуск, экран «Настройки → Чаты и Почта», кнопки
«Проверить бота (getMe)» и «Обновить список чатов (getUpdates)» отвечали
«Internal Server Error», хотя экран открывался и токен сохранялся.

Причина: `httpx` — единственная библиотека, которую приложение импортирует для выхода
в сеть (транспорт Telegram Bot API), — была объявлена только в `requirements-dev.txt`
и `requirements.lock.txt`. `run.sh` ставит в venv основной список (`requirements.txt`)
и не переустанавливает ничего, если ядро уже импортируется; поэтому в venv, созданных
до этапа 4, пакета не было, и `import httpx` внутри отправителя падал
`ModuleNotFoundError` — наружу выходил 500 без объяснения.

Что сделано:

* `httpx>=0.27` добавлен в `requirements.txt` — транспорт обязан ставиться на каждую
  машину, dev-набор для этого не подходит;
* `app/notify/transports/telegram.py`: отсутствие httpx превращается в `TransportError`
  с инструкцией («./run.sh --reinstall или pip install -r requirements.txt»),
  API отдаёт её как 502, интерфейс показывает понятный текст вместо 500;
* `run.sh`: проверка ядра дополнена httpx (`import fastapi, uvicorn, sqlalchemy, docx,
  openpyxl, httpx`) — старое venv дозаказывает зависимости сам при следующем запуске;
* тесты: `test_otsutstvie_httpx_daet_ponyatnuyu_oshibku_ne_500` (имитация отсутствующего
  пакета: обе кнопки отдают 502 с подсказкой) и `test_httpx_obyavlen_v_obyazatelnyh_
  zavisimostyah` (зависимость транспорта объявлена в основном списке).

Лок-файл не менялся: httpx и так был зафиксирован в `requirements.lock.txt` (0.28.1).
