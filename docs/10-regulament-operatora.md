# 10. Регламент оператора

Для тех, кто следит за работающим сервером: как понять, что система здорова, что делать при сбоях, как
читать журналы и делать обновление и откат. Установка и переменные — [документ 3](03-ustanovka.md);
боевой стек, бэкапы и восстановление — [`deploy/README.md`](../deploy/README.md); безопасность —
[документ 5](05-bezopasnost.md). В командах ниже боевой профиль; для локального пропустите
`-f docker-compose.prod.yml`.

## 10.1 Из чего состоит система

| Сервис | Что делает | Если не работает |
|---|---|---|
| `nginx` | TLS и вход снаружи | сайт недоступен |
| `app` | интерфейс и API | сайт не открывается или отвечает ошибками |
| `worker` | фоновые задачи: создание ночных смен в 20:00, автозакрытие отчётов в 08:00, отправка уведомлений, чистка медиа | **ночные отчёты не закрываются и не создаются, уведомления не уходят**; сайт при этом работает |
| `gotenberg` | PDF из DOCX | PDF не собираются (кнопка объясняет причину); DOCX, печать и Excel работают |
| `db` | PostgreSQL | всё остановлено |
| `backup` | ежесуточная зашифрованная копия базы и копирование на второй сервер | копий нет — узнаете, только когда понадобятся |
| `migrate` | одноразовый: миграции, справочники, первый администратор | `app` не стартует, пока он не завершится успешно |

## 10.2 Как понять, что всё в порядке

```bash
docker compose -f docker-compose.prod.yml ps
```

У `db`, `app`, `worker`, `gotenberg` и `backup` должно быть **(healthy)**. Что означает проверка:

* `app` — отвечает `/api/health` и база доступна;
* `worker` — расписания его задач тикают (команда `python -m app.bootstrap.jobs_worker --check`; печатает
  `jobs: ok` либо причину). «unhealthy» значит, что воркер стоит или завис: ночные отчёты под угрозой;
* `gotenberg` — отвечает `/health`;
* `backup` — новейшая копия моложе двух интервалов и часа; иначе копии не делаются.

Дополнительно:

* `https://<адрес>/api/health` → `{"ok": true, …}`; `"ok": false` и код 503 — база недоступна;
* `https://<адрес>/api/selfcheck` (администратор видит перечень) — схема базы соответствует коду;
* экран «Настройки → Обзор» — «здоровье конфигурации»: ошибки проверок расчёта.

## 10.3 Метрики и оповещения

При `METRICS_ENABLED=1` приложение отдаёт `/metrics` для Prometheus (наружу nginx его не публикует — скрейпер
должен ходить во внутренней сети). Метрики:

| Метрика | Смысл |
|---|---|
| `tt_http_requests_total{method,route,status}`, `tt_http_request_duration_seconds` | запросы и время ответа по маршрутам |
| `tt_jobs_schedule_lag_seconds{job}` | на сколько секунд просрочено расписание задачи; 0 — в срок |
| `tt_jobs_overdue` | сколько расписаний просрочено больше чем на три периода — воркер, вероятно, стоит |
| `tt_jobs_queue{status}` | задач в очереди по статусам (`queued`, `running`, `done`, `failed`) |
| `tt_jobs_failed_24h` | окончательно проваленных задач за сутки |
| `tt_pdf_available` | 1 — сервис PDF отвечает, 0 — нет |

Готовые правила — [`deploy/prometheus-alerts.yml`](../deploy/prometheus-alerts.yml): приложение не отвечает,
**воркер остановлен**, задачи проваливаются, очередь копится, PDF недоступен, больше 5 % ошибок сервера,
медленные запросы. Подключите файл в `rule_files` и пропишите имя вашей задачи скрейпера (`job="butler"` в
правилах — замените, если оно другое). Состояние контейнеров (`unhealthy`, перезапуски) Prometheus не видит;
для них нужен мониторинг хоста (cAdvisor, статус docker) либо внешний монитор доступности на `/api/health`.

Бэкапы: метрики у `backup` нет, его здоровье — только статус контейнера. Раз в месяц проверяйте восстановление
(`deploy/restore_check.sh`, `deploy/README.md`, раздел 4).

## 10.4 Журналы

```bash
docker compose -f docker-compose.prod.yml logs --since 1h app          # приложение
docker compose -f docker-compose.prod.yml logs --since 1h worker       # фоновые задачи
docker compose -f docker-compose.prod.yml logs migrate gotenberg backup
```

При `LOG_JSON=1` лог запросов — по строке JSON: `ts`, `method`, `path`, `route`, `status`, `duration_ms`,
`request_id`, `ip`. Пользователь, у которого что-то не открылось, может назвать время и действие; вы находите
запрос по `request_id` (он же в заголовке ответа `X-Request-ID` и в логе nginx). Действия людей — в журнале аудита
(«Настройки → Журнал аудита»), там же выгрузка CSV.

## 10.5 Что делать при сбоях

**Сайт не открывается.** `docker compose … ps`: если `nginx` не работает — `logs nginx` (чаще сертификаты); если
`app` перезапускается — `logs app`, последняя строка называет причину («База данных не задана», «Нет прав на запись
в …» — [`deploy/README.md`](../deploy/README.md), раздел 6). Если `db` не healthy — раздел «База недоступна».

**Ночной отчёт не создался в 20:00 или не закрылся в 08:00.** Почти всегда стоит `worker`: `ps` покажет `unhealthy`,
`logs worker` — причину. Запустите `docker compose … restart worker`. После запуска расписания наверстаются в
пределах минуты: смена создастся, незакрытый отчёт закроется. Если задачи падают, строка с ошибкой лежит в таблице
`jobs_queue` (`status = 'failed'`, поле `last_error`).

**Не уходят уведомления в Telegram или почту.** Сначала воркер (выше). Затем «Настройки → Чаты и Почта»: «Проверить
бота», «Отправить тестовое письмо». Токен бота и пароль SMTP зашифрованы `NOTIFY_SECRET_KEY`: если ключ потерян или
заменён, экран попросит ввести их заново.

**PDF не собирается.** Сообщение пользователю называет причину («сервис PDF не отвечает» / «не настроен»). Проверьте
контейнер: `docker compose … ps gotenberg`, `logs gotenberg`, перезапуск `restart gotenberg`. Пока он стоит, DOCX,
«Печать» и Excel работают. Адрес — переменная `GOTENBERG_URL`.

**База недоступна.** `logs db`; место на диске (`df -h`, том `pg_data`); память. Не удаляйте том `pg_data`. Если база
повреждена, восстановите её из копии — `deploy/README.md`, раздел 4.

**Закончилось место на диске.** Больше всего занимают тома `pg_data`, `app_data` (фото и видео ночного обхода),
`./backups`. Очистка медиа идёт сама по сроку хранения (задача `media_cleanup`, раз в сутки); `docker system df` и
`docker image prune` освобождают старые образы. Копии `./backups` ротируются (последние 14).

**Пользователь не может войти.** «Слишком много попыток» — подождите 5 минут (лимит хранится в базе и общий для
всех процессов; 10 неудач на пару «адрес + логин»). «Учётная запись отключена» — сотрудник уволен или отключён
в карточке. Забыт пароль — администратор или менеджер: «Сотрудники» → «Изменить» → новый пароль (все сессии
пользователя закроются).

**Подозрение на утечку сессии или пароля.** Смените пароль пользователя (сессии закрываются автоматически); для всех
пользователей — перезапуск не нужен. Журнал аудита покажет входы (`login`) и действия.

## 10.6 Обновление и откат

Обновление: `git fetch && git checkout <тег>`, затем `docker compose -f docker-compose.prod.yml up -d --build`.
Сначала запускается `migrate`; пока он не завершился успешно, `app` не стартует. После обновления проверьте
`/api/health` (поле `version`) и `ps`. **Перед обновлением сделайте бэкап.** Откат схемы базы не поддерживается:
откатывайтесь восстановлением из копии (`deploy/README.md`, разделы 4–5). Откат кода без изменений схемы —
`git checkout <прежний тег>` и тот же `up -d --build`.

Версию справочников расчёта (правила, коды, окна) откатывать проще: «Настройки → Система → Версии справочников и
откат».

## 10.7 Регулярные дела

| Когда | Что |
|---|---|
| каждый день | `ps`: все сервисы healthy; оповещения Prometheus тихие |
| раз в неделю | `df -h`, `docker system df`; свежие копии в `./backups` и на втором сервере |
| раз в месяц | **проверка восстановления** (`deploy/restore_check.sh`); закрытый ключ копий на месте |
| при выходе новой версии | бэкап, обновление, проверка `/api/health` и «Обзор» в настройках |
| при смене сотрудников | увольнение закрывает сессии; новому — логин и пароль («Сотрудники» → «+ Добавить») |
