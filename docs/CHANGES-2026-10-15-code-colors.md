# Изменения 15.10.2026 (добавление к PR #25) — цвета кодов Табеля под тем же контролем

PR #25 закрыл инъекции через цвета сотрудников (`group_color`) и типов смен
(`color`): бэкенд-валидация `normalize_hex_color` + фронтовая `cssColor()` на всех
путях в `style="…"`. Оставался один путь того же класса: **цвета кодов Табеля**
(`day_code_policy`) — пишутся через экспертный редактор настроек
(`PUT /api/engine-settings`) без проверки формата и потреблялись сырыми в
`section_v4.js` (пилюли, таймлайн, `border-left:3px solid …`) и
`section_settings.js` (`color:…` в code-pill).

## Что сделано

- **Бэкенд** (`app/api/engine_settings_api.py`, точка записи версий настроек):
  цвет каждого кода проверяется `normalize_hex_color` — не-hex даёт 422 с
  понятным текстом («Цвет кода Табеля «Я»: …»); корректный цвет канонизуется
  (нижний регистр) до сохранения `payload_json` версии.
- **Фронтенд**: `v4CodeColor()` возвращает результат через `cssColor()` — одним
  движком закрываются все её стоки (ячейки v4, пилюли, таймлайн, бейджи);
  `settingsCodeColor()` = `cssColor(цвет_из_политики, статический_цвет_кода)` —
  некорректное значение из БД не прорывается в разметку, показывается статический
  цвет кода.
- **Тесты** `tests/test_code_colors.py`: 422 на инъекционных пейлоадах
  (`red"><a …>`, `url(…)`, `#12345`, `#gggggg`, `javascript:`), канонизация
  регистра в сохранённой версии, пустой цвет не трогается.
- Версия статики `2026-10-15c` (index.html ↔ sw.js SHELL).

Эксплуатация прежнего зазора требовала право `settings.edit` и некорректного
значения уже в БД — узкий контур, но класс уязвимости тот же, поэтому закрыт
тем же механизмом, без новых сущностей.
