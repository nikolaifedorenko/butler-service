## 1. P1 — границы фильтра аудита: −3 ч хардкод

**Проблема.** `audit_api._query`: `AuditLog.ts` хранится в UTC (`core/audit`
пишет `utcnow()`), а фильтр задаётся ЛОКАЛЬНЫМИ датами объекта. `date_from`
сдвигался на захардкоженные 3 часа (московский офсет), а `date_to` **не
конвертировался вовсе**: `ts < date_to+1 00:00` читалось как UTC-граница —
фильтр был асимметричен (по `date_to` захватывались ещё 3 часа следующих
локальных суток) и ломался при любом `APP_TZ ≠ Europe/Moscow`.

**Исправление.** `_utc_bound(d)` — локальная полночь даты `d` в `core/time.TZ`
→ наивный UTC; обе границы (`>= _utc_bound(date_from)`, `< _utc_bound(date_to + 1)`)
переводятся симметрично. Это тот же принцип, что закреплён батчем «долг №3»
(PR #61): время объекта — только через `core/time`, никаких ручных офсетов.

**Стражи.** Четыре записи вокруг локальных суток 01.01.2027 (23:59 / 00:00 /
23:59 / 00:00 МСК): фильтр за 01.01 возвращает ровно две средних — прежний код
включал четвёртую (чужие сутки по `date_to`); source-страж: в `audit_api.py`
нет `hours=3`.

## 2. P1 — `cc` в `resend()`: повторная отправка теряла копию письма

**Проблема.** Журнал `NotifyDispatch` — «снимок того, что ушло» (docstring
модели), но снимка копии (`email_copy` группы рассылки) в нём не было, а
`resend()` хардкодил `cc: tuple = ()`: повтор неудачной отправки письма
уходил БЕЗ адресатов копии.

**Исправление.**

* `notify_dispatches.cc_json` (Text, default '') — снимок копии; лёгкая
  идемпотентная миграция через общий механизм `additions` в `migrate_db()`
  (прецеденты — `car_night_checks`, `night_check_items`);
* `dispatch()` пишет `cc_json=json.dumps(list(cc))` в каждую строку журнала
  (telegram-строки — пустой список);
* `resend()` читает cc из снимка строки. У строк, сохранённых до миграции,
  снимка нет — повтор без копии, как и прежде (восстановить неоткуда).

**Стражи.** `resend` с перехваченным `deliver`: cc из снимка, статус/external_id/
attempts обновлены; source-стражи записи снимка в `dispatch()` и отсутствия
прежнего хардкода; идемпотентность миграции (два прогона `migrate_db()` —
колонка одна, не падает).

## 3. P1 — FK/unique-валидации до INSERT

**Проблема.** Часть эндпоинтов вставляла строки с клиентскими ссылками/именами
без проверки: на PostgreSQL битый FK или дубль уникального имени давали
`IntegrityError` → 500; на SQLite (FK не включены — `PRAGMA foreign_keys`
отсутствует) битая ссылка молча сохранялась сиротой, а дубли имён падали
тем же 500 (unique SQLite соблюдает).

**Инвентаризация.** Пройдены все `db.add`-точки интерфейсов. Большинство уже
валидировалось и не менялось: unique-имена зон/служб/департаментов/служб-
подразделений/кодов смен/видов заявлений (→ 409), `_check_service`, select-then-update
в override/двойных оплатах/настройках/чатах/шаблонах уведомлений,
`BlockAssignment` (existing-check в schedule и doomed-delete+склейка в
`touch_block`), username при создании сотрудника (fallback `+id`),
`department_id` при ПРАВКЕ сотрудника. Закрыты найденные дыры:

* **night**: `_check_zone()` по образцу `_check_service` (→ 400 «Зона обхода не
  найдена») в `create_area`, `create_areas_bulk`, `update_area`; уникальность
  имени области при ПЕРЕИМЕНОВАНИИ (`create_area` проверял, `update_area` — нет;
  `update_zone`/`update_service` проверяли и раньше) → 409 «Такая область уже есть»;
* **employees**: `create_employee` валидирует `department_id` до вставки → 422
  «Департамент не найден» (правка сотрудника уже валидировала — там прежнее
  мягкое поведение сохранено);
* **access**: `update_group` — уникальность имени при переименовании → 409
  (create проверял); `put_members` — существование ВСЕХ `user_ids` ДО удаления
  прежнего состава → 422 «Пользователи не найдены: …» (отказ не «съедает»
  текущий список участников).

**Стражи.** По HTTP-запросу на каждую точку: битая зона (обычное создание и
bulk), битый департамент, дубль имени области/группы при переименовании,
битый user в составе (+ проверка, что состав сохранён); все отказы — с
человеческим `detail`.

## 4. P1 — потоковое чтение медиа (лимит 500 МБ в память)

**Проблема.** Три точки загрузки читали файл ЦЕЛИКОМ в оперативную память:
`blob = await file.read(limit + 1)` при `limit = max_upload_bytes` (до
`HARD_MAX_MB = 500`): фото пункта ночного обхода, отметка кара, возврат кара.
Несколько параллельных загрузок видео с телефонов съедали память воркера
(uvicorn worker получал OOM-kill целиком, со всеми активными запросами).

**Исправление.** `core/media.py`:

* `read_upload_streaming(file, limit) -> UploadRef` — читает поток чанками по
  1 МБ сразу во временный файл; в памяти только первые 64 КБ (`SNIFF_BYTES`)
  для определения типа по магическим байтам; превышение лимита прерывает
  чтение СРАЗУ (`PayloadTooLarge` → 413, текст прежний — «Файл больше N МБ»);
  при любой ошибке временный файл удаляется;
* `UploadRef` (filename/tmp_path/size/head, `discard()`) — ссылка на файл во
  временном каталоге;
* `save_photo_ref(...)` — регистрация без чтения в память: sniff по `head`,
  лимит своего типа (413), перенос `shutil.move` в `data/uploads/YYYY/MM/`;
  при любом отказе временный файл удаляется;
* общая проверка типа/лимита — `_sniff_and_limit()`, путь каталога — `_upload_dir()`
  (дедупликация с `save_photo`); `save_photo(blob=…)` СОХРАНЁН — для тестов и
  мелких внутренних задач;
* интерфейсы: `night_api` (фото пункта, отметка кара) и `cars_api` (возврат
  кара) — стриминг + `try/finally discard`; в `cars.py` `return_car`/
  `check_car_night` параметр `blob_photos: list[tuple[str, bytes]]` заменён на
  `photo_refs: list[UploadRef]` (внутри — `save_photo_ref`);
* отметка кара: guard'ы («смена закрыта», «кар не найден») вынесены ДО чтения
  потока — отказ не тратит время и диск на загрузку фото. Побочное изменение
  порядка ошибок (осознанное): закрытая смена + огромный файл теперь даёт 409
  «Смена закрыта», а не 413.

**Стражи.** Юниты: `read_upload_streaming` — чанки на диск (size/head/файл),
обрыв по лимиту с удалением временного файла; `save_photo_ref` — перенос
(файл на диске, временного нет), отказ по типу (не-медиа) с удалением
временного; source-страж: в `night_api`/`cars_api` нет `await file.read(`.
HTTP-поведение (413 по лимиту типа, загрузка фото кара/возврата) стерегут
существующие `test_media_video`/`test_cars`/`test_review_p1_night_cars` —
проходят без правок.
