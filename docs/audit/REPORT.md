# Аудит «Батлер Сервис» (butler-service) — отчёт

**Коммит:** `main` `3801abf` (21.10.2026, PR #69). **Дата аудита:** 21.10.2026. **Режим:** только
чтение; новые файлы только в `docs/audit/`, коммитов нет.
**Принятая нагрузка:** один объект, десятки сотрудников, 2–5 одновременных пользователей в
пересменку, прод — 2 воркера uvicorn и PostgreSQL 16.
**Не проверялось запуском** (решение владельца): ESLint, UI-сценарии `tools/*_scenario.mjs`,
`npm audit`. **Дополнение 21.10.2026:** миграции и старт проверены на PostgreSQL 16.15 (Docker,
`docs/audit/scripts/pg_check.py`), DB-02 и различия диалектов из 15-db-engine.md переведены в
«Факт». Весь pytest прогнан на PostgreSQL на временной копии с минимальными правками
([15b-pytest-postgres.md](15b-pytest-postgres.md)): найдена новая ошибка DB-06.

## 1. Резюме

Ядро (движок v7.1, 803 зелёных теста, 14 контрактов импортов, строгая CSP, CSRF, PBKDF2,
отзыв сессий) сделано добротно. Рефакторинг 20–21.10 закрыл главные зацепки промпта:
ролевые зависимости удалены, `init_db` сериализован замком, GET больше не пишет в БД.
Самый большой риск — **путь данных в прод**:
(1) базы, не обновлявшиеся с 18.10, текущий код не поднимает (старт падает, проверено запуском);
(2) на PostgreSQL 16 текущий `main` не стартует даже на чистой базе: миграция сравнивает
boolean с integer (проверено запуском). Тесты и CI идут только на SQLite; прогон pytest на
PostgreSQL нашёл ещё одну ошибку: id чатов Telegram не влезают в INTEGER (DB-06);
(3) на пустой боевой базе сид создаёт `admin` и 11 учёток с паролем `demo1234`, а лимит попыток
входа в прод-конфигурации обходится подменой `X-Forwarded-For`.
Второй слой — права: имперсонация без проверки иерархии ролей (журнал записывает не того
человека), 8 ролевых проверок в обход каталога прав, ночной обход и фото без проверки права
раздела, отметка «за другого» молча ставится себе.
Третий — гонки на карах и при рассылке, загрузки больше 8 МБ в проде режет nginx, а два
источника часового пояса.
Модульная структура (ADR-0010) хорошая основа для расширения. Чтобы добавить модуль «Гости»,
сейчас нужно править около 12 мест вручную; см. TARGET-ARCHITECTURE.md.

### 4.1. Данные, миграции, PostgreSQL

**DB-01 · Critical · Факт (запуск)**
- Где: `app/bootstrap/migrations.py:757-758`.
- Что: `doomed = [r["id"] for r in con.execute(text(...))]`. В SQLAlchemy 2.x строка — кортеж,
  нужен `.mappings()`. Ветка выполняется у любой базы, где в `shift_types` осталась колонка
  `tzh_code`, то есть не обновлявшейся с 18.10. Базы, созданные кодом `d2e0ea2` (06.10),
  `66a264b` (11.10) и `206d948` (16.10), при старте текущего `main` падают с `TypeError`
  (04b-schema-diff.md). Сценарий: заказчик обновляет стенд, развёрнутый 16.10, и приложение не
  поднимается.
- Исправить: `.mappings()` (одна строка) + тест «обновление базы с прошлой схемы»: фикстура
  с SQL-дампом схемы 16.10 или прогон `schema_diff.py` в CI.
- S. ADR-0002.

**DB-02 · Critical · Факт (запуск на PostgreSQL 16.15)**
- Где: `migrations.py:252-260,263-269` (каждый старт), а также `:93-94,122,128,401,568-569,
  603,750-754` (при определённой старой схеме).
- Что: raw-SQL сравнивает boolean с integer (`e.active = 0`), вставляет `0/1` в boolean,
  использует тип `DATETIME`. Скрипт `docs/audit/scripts/pg_check.py` вызвал настоящие функции
  миграций на `postgres:16-alpine`, и все 9 сценариев упали. `init_db()` на **чистой** базе:
  `UndefinedFunction: operator does not exist: boolean = integer` (`migrations.py:207` →
  `:252`), то есть приложение на PostgreSQL не стартует. Остальные места дают
  `DatatypeMismatch … boolean but expression/default is of type integer` и
  `UndefinedObject: type "datetime" does not exist` (таблица в 15-db-engine.md §15.2).
- Сколько исправлять: на временной копии кода замена двух строк (`:256,268` → `FALSE`) хватила,
  чтобы `init_db()` прошёл на чистой PostgreSQL и при повторном старте; вход и 12 основных
  экранов отвечают 200. Остальные пять мест нужны для баз, созданных старым кодом.
- Исправить: `FALSE/TRUE`, `TIMESTAMP` (или SQLAlchemy Core) во всех raw-SQL; CI-джоб на
  `postgres:16` (DB-04).
- S (правка) + M (CI). ADR-0002.

**DB-04 · High · Факт**
- Где: `tests/conftest.py:38-39` (`os.environ["DATABASE_URL"] = "sqlite:///…"` без
  `setdefault`), `.github/workflows/ci.yml` (нет сервиса postgres).
- Что: прод работает на PostgreSQL, а 803 теста — только на SQLite. Различия диалектов (DB-02,
  поиск `ILIKE` по кириллице в журнале аудита `audit_api.py:57-62`, длина `VARCHAR`, `FOR
  UPDATE`, транзакционный DDL) не проверяются.
- **Прогон на PostgreSQL 16 (21.10.2026, временная копия, [15b-pytest-postgres.md](15b-pytest-postgres.md)):**
  без правок не стартует ни один тест (DB-02). После исправления двух строк миграции — **4
  failed, 799 passed**. Корни: `migrations.py:401` (DB-02) и `chat_id` INTEGER (DB-06); два

  То есть CI на PostgreSQL можно включать сразу после шага 1.2 плана.
- Исправить: `setdefault` в conftest и `test_api.py:12`; матрица CI `db: [sqlite, postgres16]`;
  для PostgreSQL — пересоздавать схему на сессию.
- M. ADR-0002.

**DB-06 · High · Факт (запуск на PostgreSQL 16)**
- Где: `app/modules/notify/adapters/orm.py:80` (`chat_id: Mapped[int] = mapped_column(Integer,
  unique=True, …)`), запись в `notify/application/chats.py:87-114` (`refresh_chats`) из

- Что: id групп и каналов Telegram (`-1001234567890`) и личных чатов (сейчас больше 2³¹) не

  Telegram через UI не настроить. Тест `test_katalog_chatov_iz_getupdates` падает на
  PostgreSQL и проходит на SQLite.
- Исправить: `BigInteger` в модели + шаг миграции
  `ALTER TABLE notify_chats ALTER COLUMN chat_id TYPE BIGINT` для существующих баз PostgreSQL
  (`create_all` тип колонки не меняет). Проверено на копии: после правки модели 803 passed.
- S.

**DB-07 · High · Факт (запуск, найдено при исправлении 21.10.2026, исправлено в ветке `fix/migrations-alembic`)**

- Исправить: шаг `ADD COLUMN doc_type VARCHAR(40) DEFAULT ''` в `migrate_db()` (путь старых
  баз). Сделано, см. `docs/CHANGES-2026-10-21-migrations-alembic.md`.
- S.

### 4.2. Безопасность

**SEC-01 · High · Факт (запуск)**
- Где: `access/interface/auth_routes.py:37-47`, `deploy/nginx.conf:48`
  (`X-Forwarded-For $proxy_add_x_forwarded_for`), `docker-compose.prod.yml:48,59`
  (`TRUST_PROXY_HEADERS=1`, `--forwarded-allow-ips "*"`).
- Что: nginx **дописывает** реальный IP справа к заголовку клиента, а приложение берёт **левый**
  элемент, то есть то, что прислал клиент. Перебор пароля с новым `X-Forwarded-For` на каждой
  попытке не получает 429 никогда (EXP-XFF: 30 попыток подряд — только 401). Заодно словарь
  `_login_failures` растёт без предела: каждый «новый IP» — новый ключ (`:33`), так что миллионом
  запросов можно раздуть память воркера.
- Исправить: в nginx `proxy_set_header X-Forwarded-For $remote_addr;` (затирать клиентский) **или**
  брать `X-Real-IP`; в приложении брать правый элемент после доверенного прокси. Лимит вести и
  по логину, а не только по IP. Чистить пустые ключи словаря.
- S. ADR-0005.

**SEC-02 · Critical · Факт**
- Где: `bootstrap/seed.py:44,110-165`; вызов из `main.py:86-93` при каждом старте.
- Что: если в `users` нет записей, сид создаёт `admin` (роль admin) и 11 сотрудников с учётками
  (`smirnov` — manager, `gromova` — supervisor и т.д.) с паролем `demo1234`, плюс случайные
  отметки и табель. Флага, отключающего сид, нет. Прод-профиль (`docker-compose.prod.yml`) на
  чистой PostgreSQL поднимет именно это; `deploy/README.md` о смене паролей не говорит (есть
  только в `docs/INSTALL.md:205`). Пароль известен из публичного репозитория. Вместе с SEC-01 это
  вход в систему с полными правами.
- Исправить: `DEMO_SEED=1` только для демо (`run.sh`, SQLite-compose); на проде создавать одного
  администратора командой `python -m app.bootstrap.create_admin` с паролем из env и признаком
  «сменить при первом входе».
- S–M.

**SEC-03 · Medium · Факт (код)**
- Где: `notify/application/config.py:24-26,111-150` (адрес Bot API и SMTP-хост — обычные
  настройки), `notify/interface/notify_api.py:105-136` (`PUT /config`, `POST /telegram/check`),
  `notify/adapters/transports/telegram.py:49-51`.
- Что: пользователь с `settings.edit` (manager по умолчанию или кто угодно по гранту) меняет
  `notify_telegram_api` на свой хост и жмёт «Проверить». Сервер шлёт запрос `{api}/bot{токен}/…`
  туда, токен бота утекает. Маскирование токена в UI теряет смысл. То же со SMTP-хостом и паролем.
  Это также SSRF во внутреннюю сеть (POST на произвольный URL).
- Исправить: адрес Bot API — только из env; при смене SMTP-хоста или пользователя требовать
  повторный ввод пароля; запретить хосты из приватных сетей.
- S.

**OPS-01 · High · Факт (конфиг)**
- Где: `deploy/nginx.conf:30-31` (`client_max_body_size 8m`) против `core/media.py:150-153`
  (фото 12 МБ, видео 50 МБ по умолчанию).
- Что: в проде любое фото больше 8 МБ и почти любое видео обхода получают 413 от nginx. Ответ —
  HTML-страница nginx, `multipartApi` показывает её текст в тосте (`core.js:186-189`). Комментарий
  в nginx («бланки — до 5 МБ») устарел после добавления видео 19.10.
- Исправить: `client_max_body_size 60m` (или из того же лимита), а `location` для загрузок с
  `client_body_timeout`; в JS разбирать не-JSON ответ 413 понятным текстом.
- S.

**OPS-02 · Medium · Факт**
- Где: `Dockerfile:5` (`pip install -r requirements.txt`), нет `USER`.
- Что: образ собирается с **плавающими** версиями (`>=`), а CI на 3.11 проверяет lock-файл. Прод
  получает непротестированное сочетание библиотек (CI-комментарий прямо описывает поломку
  starlette/httpx2). Контейнер работает от root.
- Исправить: `pip install -r requirements.lock.txt`; `RUN useradd -r app && chown …`, `USER app`.
- S.

**OPS-03 · Medium · Факт**
- Где: `docker-compose.prod.yml:88-116`.
- Что: `pg_dumpall` каждые сутки на тот же хост в `./backups`, без шифрования и без копии вне
  хоста. Отказ диска уносит и базу, и бэкапы. Проверки восстановления нет.
- Исправить: копия вне хоста (S3 или rsync), `gpg` или `age`, ежемесячная проверка
  восстановления скриптом.
- M.

**OPS-04 · Low · Факт**
- Где: `main.py:157-158` (`docs_url="/api/docs"`, `openapi_url="/api/openapi.json"`, `redoc_url`
  по умолчанию `/redoc`).
- Что: полная карта API (159 путей) доступна без входа. Сама по себе это не уязвимость, но
  облегчает разведку.
- Исправить: в проде `docs_url=None, redoc_url=None` или закрыть в nginx.
- S.

### 4.3. Авторизация

**AUTHZ-01 · High · Факт (запуск)**
- Где: `access/interface/auth_routes.py:227-240`, `core/audit.py:45`, комментарий
  `core/permissions.py:49-51`.
- Что: `impersonate` проверяет только право `employees.impersonate` и `emp.active`, но не
  `can_manage_user`, хотя комментарий называет его «вторым стражем». Супервайзер входит «как»
  менеджер (`smirnov`) и ставит за него отметку ухода (EXP-IMP-1: 200). В журнал пишется
  `actor_id` супервайзера и `actor_name = "Смирнов Алексей Владимирович (как сотрудник)"`. В UI
  журнала (`audit_api.py:70-73`) видно только имя, а фильтр по имени (`:61-62`) действия
  супервайзера не находит. Решение «impersonation включён по умолчанию» не оспаривается; речь об
  усилении.
- Исправить: `can_manage_user(principal, target_user)` в `impersonate`; в `audit()` при
  `impersonated` писать `«<кто вошёл> → как <сотрудник>»`; решить, разрешены ли действия от имени
  сотрудника (В-3).
- S.

**AUTHZ-02 · Medium · Факт (запуск)**
- Где: `timesheet/interface/punches.py:86-95,223-235`.
- Что: для отметки за другого `punch()` требует `punches.manage`, а `_resolve_employee` —
  `punch_for_others`. Если второго права нет (индивидуальный deny), функция **молча** возвращает
  самого пользователя: запрос «отметить Сидорова» поставил уход самой Громовой (EXP-PUNCHOTHER,
  ответ 200 «Отмечен уход»). Табель получает неверные данные, а оператор уверен, что отметил
  другого.
- Исправить: при `employee_id != self_id` без `punch_for_others` возвращать 403. Объединить
  проверки в одном месте.
- S.

**AUTHZ-03 · Medium · Факт (запуск)**
- Где: `employees/interface/employees.py:154` (`role: str = ROLE_EMPLOYEE`), `:270,305`, аудит
  `:316`.
- Что: `PUT /api/employees/{id}` без поля `role` понижает пользователя до employee (EXP-ROLE:
  supervisor → employee). Текущий UI роль отправляет всегда, но любой API-клиент и будущий экран
  сломают роли. В аудите правки сотрудника записано только ФИО: смена роли, логина и пароля в
  журнал **не попадает**, расследовать эскалацию нельзя.
- Исправить: `role: Optional[str] = None` (не менять, если не передано); в payload аудита —
  diff изменённых полей (без пароля, но с флагом «пароль изменён»).
