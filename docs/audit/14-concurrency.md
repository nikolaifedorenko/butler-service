# 14. Одновременная работа и несколько воркеров

Прод: `uvicorn --workers 2` (`docker-compose.prod.yml:57-60`), PostgreSQL. SQLite-профиль
(`docker-compose.yml`, `run.sh:103`) работает в одном воркере. ID → [REPORT.md](REPORT.md).

## 14.1. Статус зацепок промпта
| Зацепка | Статус | Доказательство |
|---|---|---|
| `init_db()` одновременно в каждом воркере | **исправлено**: всё тело под `startup_lock` (`main.py:65-77`; `core/startup_lock.py:57-150`) | запуск `--workers 2` на SQLite: второй воркер ждал замок, сид выполнен один раз, дублей ночных отчётов нет (00-inventory.md §0.6). На PostgreSQL — advisory-lock, «Вероятно», не запускали |
| Отметки: `threading.Lock` + `FOR UPDATE` | в PostgreSQL корректно: блокировка строки `employees` до commit, второй запрос видит отметку соседа (READ COMMITTED) — «Вероятно». В SQLite FOR UPDATE игнорируется, но там один воркер | `punches.py:223-244` |
| `sync_reports` на GET, свой `_last_sync` у каждого процесса | **исправлено**: GET только читают, обслуживание выполняет фоновый поток под неблокирующим `try_lock` (`bootstrap/night_sync.py:43-60`). `_last_sync` остался, но все вызовы идут с `force=True` | `night.py:206-245` |
| «Проверил → вставил» без constraint | частично: unique есть у `users.username`, `cars.number`, `night_reports.date`, `tabel_days(employee_id,date)`, `period_closings(employee_id,period_start)`, `access_group_members`, `departments.name`, `subdivisions.name`. **Нет**: «один сотрудник — один кар» (`cars.holder_user_id`), `access_grants(субъект, permission)` — возможны дубли грантов (безвредны: deny сильнее) | 04-schema.md |
| Конкурентная правка ячейки, справочника, настроек движка | **последний побеждает** везде; версии или ETag нет. Опаснее всего настройки движка: каждая публикация — новая версия с полным payload из черновика вкладки (CONC-03) | `engine_settings_api.py:56-60,87-123` |
| Закрытие и пересчёт периода параллельно | закрытие защищено уникальным ключом и превращается в 409 (`close_period.py:38-53`). Правка Табеля во время закрытия: снимок входа сохраняется атомарно с результатом, правка после снимка не попадёт в закрытый результат — по спецификации это нормально (RUL-CLOSED-PERIOD-IMMUTABLE) | — |
| Кары: взять, вернуть, передать с двух телефонов | **подтверждено** (CONC-01): оба «взять» успешны, в истории две записи `take`, держатель — последний | EXP-CARRACE |
| `async def` с синхронным IO | **подтверждено**, 4 обработчика (CONC-04): `docs_api.py:190-205` (`upload_template`: разбор DOCX до 5 МБ на event loop), `night_api.py:1032-1054` (`add_item_photo`: `db.get`, `save_photo_ref`, commit), `night_api.py:1162-1230` (`report_car_check`), `cars_api.py:291-334` (`car_return`) | строки из 01-routes.md |
| Синхронные Telegram и SMTP внутри запроса | подтверждено: `dispatch_defects` идёт по группам и каналам последовательно, `httpx.post(timeout=cfg.timeout)` и `smtplib.SMTP(timeout=…)` (20 с по умолчанию, до 300). Отметки «отправлено» и журнал коммитятся **после** всех отправок (CONC-02) | `night_notify.py:107-146`; `dispatch.py:162-182` |
| Пул соединений | `create_engine` без параметров пула (`core/db.py:10`): QueuePool 5 + 10 переполнения на процесс, то есть 30 на 2 воркера плюс соединения advisory-lock и фонового потока. Threadpool AnyIO — 40 потоков на воркер: при 40 одновременных синхронных запросах 25 ждут соединение до 30 с, потом 500. При целевой нагрузке (единицы одновременных) не проблема; `max_connections=100` PostgreSQL не превышается | — |
| `expire_on_commit=False` | объекты после commit не перечитываются. Это и даёт CONC-01: кар, прочитанный до коммита соседа, остаётся «свободным» в памяти запроса | `core/db.py:23` |

Второй источник пояса — HARD-01 | `timesheet/adapters/orm.py:271`, `night/adapters/orm.py:24` (комментарии «naive, как Punch.ts») |

## 14.2. Сценарии гонок, которые ещё не закрыты
1. **CONC-01. Кар.** Два запроса читают `cars` до коммита соседа. Оба проходят проверку
   `status in (free, charging)` и `_held_by` (`cars.py:200-213`), оба записывают держателя.
   Итог: два человека уверены, что кар у них; в истории два `take`; правило «один сотрудник —
   один кар» без constraint тоже обходится параллельными запросами на разные кары.
   Исправление: условный `UPDATE cars SET … WHERE id=:id AND status IN ('free','charging')` с
   проверкой `rowcount` (или `with_for_update()` при чтении) и частичный unique-индекс
   `cars(holder_user_id) WHERE holder_user_id IS NOT NULL`.
2. **CONC-02. Отправка недостатков.** Сначала сеть, потом commit. Два нажатия (или повтор после
   клиентского таймаута 20 с, UI-03) одновременно выбирают ещё не помеченные пункты
   (`defects_of`) и отправляют их дважды. Если процесс упадёт после отправки, но до commit, пункты
   останутся «не отправленными», и следующая отправка их продублирует. Исправление: в начале
   транзакции заблокировать отчёт (`SELECT … FOR UPDATE` строки `night_reports`) и пометить
   пункты «отправляются», а сеть вынести из запроса в фоновую очередь (outbox-таблица
   `notify_dispatches` уже есть) или хотя бы закоммитить журнал до отправки.
3. **CONC-03. Настройки движка.** Две вкладки редактора открыты от одной версии, каждая
   публикует полный payload — изменения первой молча теряются. Исправление: поле
   `base_version_id` в `SettingsIn` и 409, если базовая версия на дату уже не последняя.
4. **Повтор POST при обрыве связи** (телефоны в PWA): у отметок есть защита — повторный «пришёл»
   даёт 409, дубль автокнопки в течение 60 с отсекается. У каров, ответов обхода и закрытия
   области защиты нет, но они идемпотентны по смыслу («last write wins»).
5. **CONC-04. Event loop.** В `async def` синхронные `db.get`, `flush`, `commit`, `shutil.move` и
   разбор DOCX выполняются на event loop воркера. Пока один телефон загружает фото обхода, все
   прочие запросы этого воркера ждут; на SQLite ожидание блокировки (`busy_timeout=10000`)
   замораживает воркер до 10 с. Исправление: объявить обработчики `def` и читать загрузку через
   `file.file` синхронно (Starlette уже буферизует `UploadFile` во временный файл) либо обернуть
   синхронную часть в `run_in_threadpool`.

## 14.3. Состояние в памяти процесса
См. 00-inventory.md §0.7. При 2 воркерах реально мешает только лимит входа: фактический порог
— 10 неудач на воркер, то есть до 20, плюс неограниченный рост `_login_failures` при подмене
IP (SEC-01). Это допустимо по ADR-0005 для одного объекта, если закрыть SEC-01.
