# Изменения 21.10.2026 — батч review-P1: таймшит/движок

Третий батч по внешнему ревью `REVIEW-2026-10-20.md` (продолжение P0, PR #65 и
P1 «ночь/кары», PR #66; план батчей — §8 `docs/archive/changes/CHANGES-2026-10-20-review-p1-night-cars.md`).
Закрыты семь находок P1 в модуле **timesheet**. Ключевое решение владельца
(21.10.2026): находка «`fmt_hours` на не-15-минутном плане» исправлена по

Новые стражи: `tests/test_review_p1_timesheet.py` (17).

## 1. P1 — конкурентное закрытие периода: IntegrityError → 409; атомарность mgmt-закрытия

**Проблема.** Повторная проверка права внутри `UnitOfWork` (`close_period`) —
check-then-act: два конкурентных закрытия оба проходили проверку, гонку ловил
только уникальный ключ `uq_closing_emp_period` на `flush()` — `IntegrityError`
не ловился ни use case'ом, ни mgmt-обёрткой `_run_action` (там только
DomainError/ApplicationError/ValueError) → 500 вместо конфликта. Спека 7.3:
«повторное и конкурентное закрытие одного периода невозможно»; тест-план п.15:
«атомарность закрытия — сбой между записями → ничего не сохранено».

**Исправление.**

* `ports/unit_of_work.py` — контрактное исключение **`StorageConflictError`**
  («нарушение уникальности при записи»): слой портов не знает ни sqlalchemy,
  ни домена (§3), application не знает исключений инфраструктуры;
* `adapters/sql_closings.py::save_result` — `flush()` под переводом
  `IntegrityError → StorageConflictError`; `adapters/sql_uow.py` — тот же перевод
  на `commit()` (страховка отложенного flush) + rollback;
* `application/close_period.py` — блок UoW под `except StorageConflictError →
  PeriodAlreadyClosedError`: одиночное закрытие → 409 «Период уже закрыт»
  (центральный хэндлер), mgmt bulk → запись в `errors` (массовая семантика 200
  сохранена, §11.1). Откат UoW оставляет сессию usable для следующих
  сотрудников цикла.

**Стражи.** Фейковые порты: конфликт → `PeriodAlreadyClosedError`, ничего не
сохранено; инъекция сбоя МЕЖДУ записями (`fail_on="save_closing_bank"`) →
результат откатывается. Реальная БД: строка соперника + окно READ COMMITTED
(патч `_row`) → `StorageConflictError` из `save_result`; то же на `commit()`
в UoW. HTTP-семантику «повторное закрытие → errors» стережёт `test_v4_api`
(не дублируется).

## 2. P1 — `order_by` в `put_manual_shift`: ноты на своих интервалах

**Проблема.** После `save_schedule_day` (delete+insert manual-строк) роутер
перечитывал строки `ScheduleShift` БЕЗ `ORDER BY` и расставлял `note`/`updated_by`
`zip`'ом по интервалам запроса. Порядок строк без ORDER BY не гарантирует даже
PostgreSQL — ноты могли лечь на чужие смены.

**Исправление.** `.order_by(ScheduleShift.id)`: id назначаются в порядке вставки
одним flush в `save_manual`, т.е. порядок id = порядок `intervals` запроса
(`start` не годится — интервалы могут прийти вне хронологии).

**Страж.** PUT /api/schedule/shift с интервалами НАРОЧНО вне хронологии
(«вечер» 18:00–22:00 первым, «утро» 08:00–12:00 вторым) — ноты на своих строках;
SQL-страж: повторная выборка manual-строк содержит ORDER BY (защита от «БД
случайно вернула в нужном порядке»).

## 3. P1 — `fmt_hours` на не-15-минутном плане (строгий вариант)

**Проблема.** Доменный `fmt_hours` бросает сырой `ValueError`, если план
непредставим (не кратен 15 — CHK-PLAN-FORMAT, §3.3). Конвейер отбраковывает такие
строки на стадии 1 типизированно, запись в Табель валидирует кратность
(`save_timesheet_day → check_plan_minutes`), НО дисплейные пути читают строки БД
напрямую: сетка Табеля (`tabel_api`), Гант «Факт/Месяц» (`fact_api`), сетка и
оконные хелперы Графика (`schedule.py` ×3), `covers_window` (`engine_common`).
Легаси/повреждённая строка (план 50 мин) роняла GET вкладки в 500.

**Исправление (решение владельца — строгий вариант).**

* домен НЕ смягчён: `fmt_hours`/`value_of` строги как прежде (канонический ключ
  CFG-WINDOWS, §3.3);
* `interface/formatting.py` — `fmt_hours_strict(minutes, employee_id, day)`:
  переводит `ValueError` в **`TimesheetRowCorruptError`** (ApplicationError → 409)
  с указанием сотрудника, дня и значения («…план 50 мин не кратен 15 минутам
  (CHK-PLAN-FORMAT) — исправьте значение в разделе «Табель»»);
* все шесть дисплейных/лукап-вызовов переведены на него (`covers_window` —
  в application — бросает ту же ошибку напрямую);
* приблизительное отображение («0,83») ОТКЛОНЕНО: вкладка честно сообщает о
  повреждении, битые данные не маскируются.

**Стражи.** Посаженная строка plan=50 → GET /api/tabel, /api/schedule,
/api/fact/month — 409 с текстом «не кратен 15» и датой; домен по-прежнему бросает
`ValueError` (строгость конвейера); `covers_window` — типизированно.
Write-path (422 CHK-PLAN-FORMAT) стерегут существующие `test_validation` /
`test_application` — не дублируется.

## 4. P1 — `presence_board` по UTC-дню: Settings месяца локального «сегодня»

**Проблема.** Доска «Отметки» грузила Settings для календарного месяца UTC-дня
(тот же предзагруз был в `presence_api.board()`). Спека 16.2: «Settings …
загружаются для календарного месяца, содержащего „сегодня“» (`today_of(now, st)`,
§4.4). На границе месяцев (01.11 00:30 МСК = 31.10 21:30 UTC) доска брала
tz/версию/гранулярность справочников прошлого месяца.

**Исправление.** Двухшаговое уточнение (паттерн `mgmt_api::/periods`) вынесено
в общий хелпер `application/months.settings_for_now(now, ports) -> (st, today)`:
месяц по UTC-дню даёт tz → локальное «сегодня» → итоговая версия для его месяца.
В обычном случае (месяцы совпали) второго `load` нет вовсе — бюджет «≤ 5
батч-запросов» (16.1 п.5) не растёт даже у порта без кэша; на границе — второй
load (в проде несколько точечных запросов версии, в пределах BOARD_BUDGET=20).
Применён в `presence_board` (use case), `presence_api.board()` (ответ «today» —
тот же день, что использует use case) и `/periods` (дедупликация — поведение
идентично прежнему inline-паттерну). Уточнение однократное, без цикла до
неподвижной точки (смена tz МЕЖДУ версиями на самой границе — крайний случай,
достаточный по прецеденту /periods).

**Стражи.** Фейковые порты с записью: граничный момент 2026-10-31 22:30 UTC →
загружены октябрьская, затем ноябрьская версия; `active_employees` вызван с
локальным 01.11; `assemble_board` получила ноябрьские Settings (tz другой).
HTTP-смоук под freeze (вход внутри заморозки — сессия не истекает): версия
справочников с 01.11 → доска 200, «today» = 2026-11-01. Регресс бюджета —
существующие `test_board_query_budget_max_five` и `test_board_query_budget`.

## 5. P1 — `ZoneInfo(tz)` в `settings_codec`: битый tz → ConfigError CFG-TZ

**Проблема.** `from_payload` строил `ZoneInfo(tz)` из строки сохранённого payload;
несуществующий часовой пояс давал `ZoneInfoNotFoundError` (подкласс **KeyError**,
не ValueError): на пути загрузки справочников её не ловил никто — КАЖДЫЙ запрос
любой вкладки падал 500-й; в редакторе настроек она тонула в нетипизированной
ветке `(KeyError, ValueError, TypeError)`. Импорт `zoneinfo` жил внутри функции.

**Исправление.** `from_payload` — `except (ZoneInfoNotFoundError, ValueError) →
ConfigError([("CFG-TZ", {"tz": …})])`; импорт поднят наверх модуля. По доктрине
§5.3: GET вкладок → 409 «Ошибка настроек: Некорректный часовой пояс (tz)…
«Mars/Olympus» — укажите существующий (например, Europe/Moscow)… [CFG-TZ]»
(центральный хэндлер), PUT редактора → существующий локальный catch ConfigError
→ 422 («редактор валидирует ВВОД»). `formatting.py` — заголовок и ветка текста
`CFG-TZ` с битым значением.

**Стражи.** Юнит `from_payload`; HTTP: посаженная версия справочников с битым tz
→ GET /api/mgmt 409 c «CFG-TZ» и значением (не 500); PUT /api/engine-settings
с битым tz → 422.

## 6. P1 — `assert` на горячем пути `deserialize`

**Проблема.** `_reason` проверял шаг записи `assert d["step"] in ALL_STEPS` —
путь горячий (каждое чтение закрытого периода, 7.2/RUL-CLOSED-PERIOD-IMMUTABLE,
вызывается из `sql_closings.load_result`). Под `python -O` assert'ы вырезаются —
проверка молча исчезала; без `-O` — нетипизированный `AssertionError` → 500.

**Исправление.** Явная проверка → **`StoredResultCorruptError`** (ApplicationError,
код `STORED_RESULT_CORRUPT`): «Сохранённый результат закрытого периода повреждён:
неизвестный шаг расчёта «…» — выполните «Пересчитать» либо обратитесь к
администратору». 409 центральный хэндлер; в mgmt-вкладке — ошибка в payload
строки (200 + «error», существующая семантика `_row`). Протечка
adapters→interface (`sql_closings → deserialize`) не расширялась — её распутывание
остаётся в батче 6 (P2, «порты/DTO»).

**Стражи.** Юнит; subprocess `python -O` (типизированная ошибка бросается и с
вырезанными assert'ами); HTTP: посаженный `PeriodClosing` с битым `result_json`
→ GET /api/mgmt 200 + error строки «повреждён … Пересчитать» (не 500 на период).

## 7. P1 — `saved[0]` без проверки в `view_period`

**Проблема.** Контракт порта — `load_result → tuple | None`; при `state.closed =
True`, но исчезнувшей строке (гонка с удалением, рассинхрон хранилища)
`view_period` обращался к `saved[0]` вслепую → `TypeError` → 500.

**Исправление.** Явная ветка `saved is None → StoredResultCorruptError`
(«…отсутствует (сотрудник, период с …)») — та же доктрина, что п.6: один
типизированный отказ на «нет/битый сохранённый результат».

**Страж.** Фейковый порт: закрытие штатно, затем `load_result → None` →
`view_period` бросает типизированную ошибку (не TypeError).
