## 1. SEC-02 — демо-учётки с паролем `demo1234` на боевой базе

На пустой базе сид создавал `admin` и 11 сотрудников с известным паролем. Теперь:
* `DEMO_SEED=1` — прежние демо-данные (`./run.sh`, тесты, `tools/run_*.sh`, шаг selfcheck CI);
* без него — только справочники (правила, словарь смен, департаменты) и `admin` с паролем
  из `ADMIN_PASSWORD`; без пароля старт громко отказывает, как при пустом `SECRET_KEY`.
  Базы, где пользователи уже есть, это не затрагивает.
* `MIN_PASSWORD_LEN` перенесён в `core/security.py` — одно правило для всех паролей.

## 2. SEC-01 — подмена `X-Forwarded-For` обходила лимит входа

nginx дописывает настоящий адрес справа, а приложение брало левый (клиентский).
`_client_ip` берёт правый. Словарь неудач чистит адреса без свежих попыток.

## 3. SEC-03 — токен бота и пароль SMTP уходили на любой хост

* `POST /api/notify/telegram/check` принимал адрес Bot API в теле и слал на него
  сохранённый токен, даже без сохранения настроек. Поле убрано, используется только
  настроенный адрес.
* Адрес Bot API из интерфейса не меняется (400). Задаётся переменной `NOTIFY_TELEGRAM_API`;
  уже сохранённое значение продолжает работать.
* Смена сервера или пользователя SMTP при сохранённом пароле требует ввести пароль заново.

## 4. OPS-01 — видео обхода не загружались в проде

`client_max_body_size` 8m → 60m (видео до 50 МБ по умолчанию). Не-JSON ответ об ошибке
(HTML-страница nginx при 413/502) показывается понятным текстом, а не разметкой:
`parseBody` в `core.js` для `api()` и `multipartApi()`.

## 5. OPS-02 (частично) — Dockerfile ставил плавающие версии

Зависимости в образе ставятся с `-c requirements.lock.txt`: версии ровно те, что проверены
CI, dev-пакетов в образе нет (проверено сборкой). **Отложено:** запуск не от root — у
существующих томов `data/` и `templates/` владелец root, нужен отдельный шаг `chown`.
