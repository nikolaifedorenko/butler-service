## 2. В-4 — фото закрытого ночного отчёта не удаляется

`core/media.delete_photo` спрашивает модуль-владельца (`media.set_delete_guard`, регистрирует
`bootstrap/registry.wire`, как и лимиты медиа). Модуль ночи (`night.photo_delete_blocker`)
запрещает удаление фото пунктов обхода и проверок каров, пока отчёт закрыт: «переоткройте его,
чтобы удалить фото».

## 3. В-8 — чистка медиа по сроку хранения раз в сутки

* Окно кандидатов — по **самому короткому** положительному сроку, каждый файл сверяется со
  своим (было `max`: при фото 30 / видео 180 дней фото жили 180).
* Чистка раз в сутки в фоновом потоке `bootstrap/night_sync.py` под `try_lock("media-cleanup")`
  (один процесс из нескольких воркеров); раньше она шла только при старте сервера.
* **При выкатке** файлы старше срока удалятся при первой суточной чистке (решение владельца:
  без предварительного отчёта). Запись о фото остаётся, пропадает только файл.

## 4. В-12 — зашифрованные бэкапы на второй сервер

* `deploy/backup.sh` + `deploy/backup.Dockerfile` (postgres:16-alpine + age, rsync,
  openssh-client): `pg_dumpall | gzip | age -r <открытый ключ>` → `./backups/*.sql.gz.age`,
  14 последних, затем `rsync` по SSH на второй сервер (только зашифрованные файлы, строгая
  проверка ключа хоста). `set -o pipefail`: сбой `pg_dumpall` даёт «backup FAILED», а не пустой
  файл.
* Без `BACKUP_AGE_RECIPIENT` сервис не стартует — незашифрованных копий больше нет.
* `deploy/restore_check.sh` — ежемесячная проверка восстановления там, где лежит закрытый ключ:
  временный PostgreSQL, восстановление, число пользователей, сотрудников, отметок, ревизия схемы.
* `deploy/README.md` §4 — ключи, второй сервер, проверка и восстановление; `.env.example`,
  `docker-compose.prod.yml`, `.gitignore` (`backups/`, `deploy/backup-ssh/`).
