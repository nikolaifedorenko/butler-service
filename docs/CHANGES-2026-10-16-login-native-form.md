# Изменения 16.10.2026 (батч 5) — вход нативной формой: менеджеры паролей предлагают сохранить сразу

Владелец: плашка «Сохранить пароль?» (Safari / «Пароли» macOS) всё равно
появлялась не после входа, а при первом же клике по разделу («Настройки»);
требование — система должна предлагать сохранить пароль **сразу после
успешного логина**.

## Причина

Вход в SPA шёл через `preventDefault()` + `fetch('/api/auth/login')`: браузерные
менеджеры паролей фиксируют учётные данные по событию submit, но решение
«показать плашку» привязывают к навигации/загрузке страницы, которых в SPA нет,
— и откладывают промпт до следующего «похожего на навигацию» события (у владельца
— перерисовка при открытии «Настроек»). Очистка поля пароля после входа (батч 4)
не помогает: учётные данные менеджер успевает захватить в момент submit.

## Решение: классическая связка «submit → POST → 303»

* форма логина получила `action="/api/auth/login-form" method="post"` и
  отправляется **нативно** (fetch-обработчик submit удалён);
* новый эндпоинт `POST /api/auth/login-form` (form-urlencoded): та же проверка
  учётных данных (`_authenticate`: rate-limit, постоянный хеш для несуществующего
  логина, ленивый rehash, аудит), при успехе — сессионная cookie и `303 → /`,
  при ошибке — `303 → /?login_error=auth|rate|disabled` (пароль в URL не
  попадает); SPA на старте читает код и показывает сообщение, очищая URL
  (`history.replaceState`);
* `_CSRF_EXEMPT_PATHS` пополнен путём login-form с тем же обоснованием, что и
  JSON-вход (CSRF-cookie у клиента ещё нет; login-CSRF — отдельная, принятая
  поверхность); проверено при `CSRF_ENABLED=1`;
* JSON-вход `/api/auth/login` сохранён для API, тестов и сценариев;
* jsdom-харнесы (норматив, слои, настройки, смоук, снимки) логинятся JSON-эндпоинтом
  и перезапускают SPA через `bootApp()` (нативный submit в jsdom не реализуется);
  `boot()` стал именованной `bootApp()`.

После редиректа менеджер паролей видит канонический успешный form-login и
показывает плашку сразу — до каких-либо кликов по разделам.
