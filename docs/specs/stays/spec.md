# Модуль «Шахматка» (stays) — спецификация

**Статус:** норматив
**Редакция:** 1.0 от 03.11.2026

Консолидированная спецификация модуля: части 1–4 и дополнение к части 1 сведены в один
документ по состоянию кода на 03.11.2026 (HEAD a3304a9) с учётом аудита
(`stays-audit-parts2-4.md` — части 2–4 чистые; находки L1, P2, C1 части 1 исправлены и
отражены здесь как норма). Исходные дизайн-документы частей — в
[`docs/archive/specs-stays/`](../../archive/specs-stays/), планы реализации — в
[`docs/archive/plans-stays/`](../../archive/plans-stays/); они описывают ход работ на свои
даты и не правятся. Действующие решения владельца — в
[`decisions.md`](decisions.md) (S-нумерация; на S8–S10 ссылаются комментарии в коде).

Модуль подключается манифестом (ADR-0012): роутеры, модели, права, действия аудита, меню,
экраны Настроек; JS-файлы регистрируются через `registerModule`.

## 1. Наззначение и состав

Шахматка — рабочий инструмент поверх Fidelio (источник правды по броням): фонд и его
версии, гости и семейные связи, брони с составом во времени, автораспределение по объектам,
покрытие гостей батлерами, сопровождение по правилам и VIP-коды, OOO и блоки, экраны
(шахматки, табло дня, загрузка, брони, гости, «Мои гости»), выгрузки Excel.

**Входит:** перечисленное выше, предпросмотр «что будет, если» для всех операций, три
уровня видимости персональных данных, журнал изменений, демо-данные (`DEMO_SEED=1`).

**Не входит (следующие подпроекты):** импорт CSV и чтение из базы Fidelio; уведомления
батлерам; личный лимит батлера; перетаскивание полос мышью (перенос — через диалог с
предпросмотром); сохранённые сценарии из нескольких изменений; полное удаление или
обезличивание профиля гостя по запросу; печатные формы; ограничения категорий (min stay,
close-to-arrival); статусы уборки номеров.

Единицы времени: локальные даты объекта. Каждая дата делится на половины — AM (до выезда)
и PM (с заезда); позиция на общей шкале — `ordinal*2 + half` (`domain/halfday.py`).
Занятость — отрезок с включёнными границами: выезд утром и заезд днём в тот же объект в
один день не пересекаются. Покрытие, нагрузка и «Мои гости» считаются по ночёвкам.

## 2. Модель данных

### 2.1 Фонд и версии

* **Категория** — постоянный `id`; в версии фонда: код Fidelio (VEG, FWV, DLX…), название,
  вид (справочник `stays_category_kinds`), вес нагрузки, признак сопровождения, порядок.
  `UNIQUE (version_id, code)`.
* **Узел дерева** — постоянный `id`; в версии: название, родитель (в той же версии),
  порядок. Одно дерево групп; объект лежит ровно в одном узле; остальные признаки — флаги.
* **Объект** — постоянный `id`; в версии: обозначение («4003»), категория, узел, этаж,
  флаги. `UNIQUE (version_id, label)`. Отсутствие объекта в снимке версии = его нет в
  фонде на эти даты (признака «активен/выведен» нет).
* **Флаг** — справочник `stays_unit_flags` (название, цвет, порядок, архив) НЕ
  версионируется; версионируется привязка флага к объекту (да/нет, `stays_unit_state_flags`).
  Использованный флаг — только в архив (пропадает из выбора, у объектов остаётся).
* **Lineage** — `stays_unit_lineage (unit_id, predecessor_id, version_id)`: «из чего
  получился объект» при делении/объединении.
* **Версия фонда** — `stays_fund_versions (valid_from UNIQUE, status draft|published,
  base_version_id, author_id, note, created_at, published_at)`. Подход А: версия — целый
  снимок фонда, действует с даты до начала следующей. Полный снимок (~440 объектов +
  ~1000 флагов) дешевле хранения разницы и даёт «фонд на дату» одним запросом.

**Постоянен только внутренний id.** Версионируется всё остальное: у объекта — обозначение,
категория, узел, этаж, флаги, присутствие в фонде; у категории — в том числе код Fidelio;
само дерево. Брони, назначения, OOO/блоки, пожелания ссылаются на постоянные id, поэтому
смена версии их не ломает.

**Переименование категории** (DTG → DKG, те же номера) — та же категория (тот же id):
с даты меняются код и название, распределение не меняется. **Новая категория** (часть
номеров переделана) — новый id; объектам меняется категория с даты; броням не хватает
объектов — предпросмотр показывает и предлагает массовый перевод (§3.3).

**Фонд на дату D** — опубликованная версия с наибольшей `valid_from ≤ D`; ровно одна версия
действует в любой день (исходная — `valid_from = 2000-01-01`, из миграции). **Граница в
половинках суток:** версия с `valid_from = D` действует с вечера D (PM) — ночь с D на D+1
и далее; утро D принадлежит прошлой версии. Так «фонд на дату» совпадает с ночёвками.

Чтение фонда — только через `application/fund_versions.py`: `fund_for(db, first, last) ->
FundTimeline` (≤ 6 запросов на диапазон), `FundTimeline.on(day) -> FundSnapshot`
(категории, узлы с путём, объекты, флаги). Прямые `select(Unit)`/`select(Category)` вне
`fund_versions` и `fund` запрещены тестом архитектуры.

### 2.2 Гости

* **Профиль** — фамилия, имя, отчество, пол (`m | f | ''`), телефон (единый формат),
  email, дата рождения, ◆ «Особый гость», VIP-код профиля, предпочтения (текст по
  разделам), особые даты (дата + что), значения настраиваемых полей, примечание,
  внешний идентификатор и источник (для будущего импорта), `created_by_employee_id`
  (батлер, который завёл профиль — делает гостя «своим», §10), `search_text` и
  `name_text` (служебные поля поиска, миграция 0020).
* **Связь гостей** — одна строка, показывается в обоих профилях с правильной подписью.
  Семейные (хранят родство): `parent` (у ребёнка не больше двух родителей), `spouse`
  (с признаком «бывшие»). Прочие виды — не семейные: ассистент, охрана, водитель, няня,
  `relative` (степень неизвестна), коллега, другое. `child` заменён на `parent`.
* **Родство вычисляется** обходом графа «родитель/супруг» (`domain/kinship.py`, чистая
  функция): родители, дети, братья/сёстры, бабушки/дедушки, внуки, прабабушки/прадедушки,
  правнуки, дяди/тёти, племянники, двоюродные; свойственники через брак (свёкор, свекровь,
  тесть, тёща, зять, невестка, деверь, золовка, шурин, свояченица, свояк). Название — по
  полу, без пола — нейтрально. Глубина — до прародителей и правнуков, дальше —
  «родственник (N-я степень)». «Бывшие» супруги свойственников не дают.
* **Проверки дерева:** нельзя стать своим предком; родителей не больше двух; супругом
  нельзя сделать предка или потомка; нарушение — 422 с объяснением. Один действующий супруг.

### 2.3 Брони

* **Бронь** — номер (Fidelio; не обязан быть уникальным — совместные брони), статус,
  заезд, выезд, ранний заезд (РЗ), поздний выезд (ПВ), категория, «оплата за»
  (`paid_category_id` — категория, если отличается; пометка «апгрейд: оплачена DKG»),
  метка, заказчик, примечание, VIP-код (§7), режим сопровождения (§7), настраиваемые
  поля, внешний идентификатор и источник, группа совместного проживания (необязательно),
  `version` (оптимистическая блокировка — 409 при конфликте). «Повод визита» удалён — это
  примечание.
* **Статусы:** предварительная → подтверждена → заселён (`in_house`) → выехал; отменена;
  не заехал (no-show). Меняет менеджер вручную. Отменённая и no-show не занимают объект и
  не требуют батлера. No-show ставится на дату заезда или позже: объект освобождается,
  строки покрытия удаляются с записью в журнал; гость приехал позже — возврат в
  «подтверждена» с новой датой заезда (с предпросмотром). No-show — отдельная группа на
  табло дня, учитывается в статистике.
* **Проживающий** — бронь, гость, свои даты с–по в пределах брони, роль (главный/
  проживающий). Смена главного: запись прежнего закрывается датой, новая открывается;
  главный на дату — у кого роль «главный» на эту дату. Состав меняется во временем;
  история проживания — и по броням, и по гостям.
* **Переезд** — дата и новая категория. **Сегменты** — части проживания между переездами;
  назначения сегментов на объекты — `stays_assignments (reservation_id, seg_index,
  unit_id, «закреплено вручную»)`.
* **Сопровождающие** — разовые люди брони без профиля (тип: охрана, водитель, няня,
  животное, другое + описание). Постоянные — профили со связью.
* **Логистика** — рейсы, трансферы, автомобили: тип, дата, время, описание.
* **Группа совместного проживания** — несколько броней в одном объекте, каждая на своего
  гостя; внутри группы брони не конфликтуют; автораспределение ставит группу в один объект.

### 2.4 Покрытие батлерами

* **Строка покрытия** — дата, батлер (сотрудник из модуля «Сотрудники»), кого ведёт: вся
  бронь, вся группа или выбранные проживающие; пометки «шаблоном/вручную», «остаётся на
  ночь», комментарий. Объект на день НЕ хранится — вычисляется по гостям.
* Единица покрытия — календарный день: на день у гостя один ответственный батлер (дневная
  смена). Ночью — дежурная служба либо дневной остаётся (пометка дня).
* **Батлер ведёт гостей, а не объект:** при переезде продолжает вести гостя в новом
  объекте; один объект могут вести несколько батлеров (один — главного, другой — супругу).
* **«Сопровождают гостей»** — собственный список модуля (сотрудник, активен); изначально —
  сотрудники с должностью «батлер», дальше вручную.
* Явный список гостей другого батлера сильнее строки «вся бронь/группа».

### 2.5 OOO и блоки

* **OOO** — один объект, половинки суток (AM/PM с–по), название; ставится поверх брони —
  бронь переезжает (§4) или остаётся без объекта; переселяет и заселённого (один раз, до
  конца проживания). Пересечение OOO того же объекта — 409 (включая кромки половинок).
  Диапазон — не длиннее 10 лет.
* **Блок** — даты с–по, название и сетка «категория × ночь → количество» (остаток).
  Больше ничего: ни статуса, ни опциона, ни «держателя». Блоков может быть много, в том
  числе на одни категории и даты. Блок — на любую категорию. Ночей в блоке — не больше
  366, остаток 0..500, даты 2000–2200 (`_sane`).
* Блок раскладывается по объектам **только автоматически**, по ночам; старается держаться
  одного объекта (слоты — непрерывные ночи одного номера слота; соседние блоки одной
  категории тянутся в один объект). Закрепления блока нет. Брони к блокам в программе не
  привязываются (остаток уменьшает Fidelio; здесь правят вручную).
* Блоку батлер не нужен: он не участвует в покрытии, дырах и нагрузке. Блоки и OOO видны
  всем уровням, с названиями — персональных данных в них нет.

### 2.6 VIP-коды и правила сопровождения

* **VIP-код** (`stays_vip_codes`) — только арабские цифры, 1–8 знаков (нормализация;
  «03» ≠ «3»), название, коэффициент веса 0.1–99, признак «сопровождение», архив.
  Не версионируется (изменение коэффициента действует на все даты). Архивный код остаётся
  там, где стоит, заново не выбирается (422 при выборе). Справочник переживает «заменить
  всё» (KEEP, не WIPE).
* **«Особый гость»** — флаг профиля (вместо прежних уровней обычный/VIP/VVIP — они
  удалены вместе с «отказом от батлера» и надбавками, миграция 0018).
* **Режим сопровождения брони** — «по правилам» (по умолчанию) / «требуется» /
  «не требуется (гость отказался)»; ручная отметка перекрывает правила в обе стороны.

### 2.7 Настройки и настраиваемые поля

* **Настройки модуля** (`stays_settings`, строка id=1 из миграции 0008 — гарантия замка на
  SQLite): дневной лимит нагрузки батлера (один на всех; личный — позже), переключатель
  «Шахматка в эксплуатации» (выключает «заменить всё»; обратно — только администратор,
  с аудитом).
* **Настраиваемое поле** — к чему (гость/бронь), код, название, тип (текст/список/да-нет/
  дата), варианты, «искать по полю», порядок. Значения — в записи гостя или брони
  (`fields_json`).
* **Метка брони** — название и цвет полосы; цвет — только `#RRGGBB`
  (`normalize_hex_color`, защита от HTML-инъекции в style).

## 3. Версии фонда: черновик, предпросмотр, публикация

### 3.1 Правила черновика

* Любая правка фонда — через **черновик «с даты D»**, открытый копией версии, действующей
  на D (`base_version_id`). **D ≥ сегодня** (прошлое не меняется; если D наступила —
  публикация только после сдвига даты). **Черновик один на весь фонд** (второй — 409).
* Удалить можно черновик и опубликованную версию, чья `valid_from` ещё не наступила;
  действующую, прошедшие и исходную — нельзя. Удаление версии — с предпросмотром.
* Все записи — под замком модуля `lock_module` и с проверкой версии черновика
  (оптимистическая, 409 при одновременной правке).

### 3.2 Действия в черновике

Изменить объект (категория, обозначение, узел, этаж, флаги) · новый объект · вывести ·
**разделить** (выводит исходный, заводит N новых, пишет lineage) · **объединить** (выводит
выбранные, заводит один новый, lineage; разные узел/категория — спрашивает) · категории
(добавить/изменить, включая код-переименование/вывести — нельзя, пока в снимке есть её
объекты) · дерево (добавить, переименовать, перенести без циклов, порядок, вывести —
нельзя, пока есть объекты или подузлы) · флаги объектов (матрица с галочками, массовая
отметка по узлу). Справочник флагов правится вне черновика — сразу.

### 3.3 Предпросмотр и публикация

Публикация идёт через общий механизм операций (§6): что поменялось в фонде («было →
стало»); брони, которые сменят объект с D и которые останутся без объекта; закреплённые
(📌), чьё закрепление стало неверным; брони категорий, которых нет в фонде с D; новые
предупреждения. **Массовый перевод броней на категорию** — действие в предпросмотре с
выбором галочками; применяется в той же транзакции; для уже живущей на D брони
переводится сегмент с D (переезд), а не вся бронь; в журнал и аудит — «было → стало».

Публикация: черновик → `published`, `run_allocation`, аудит (`fund_version:{id}`, полная
разница). Публикация и удаление версии — под гейтом овербукинга (§4.5).

**Перенос в поздние версии** (после D есть опубликованные): спросить «Применить и к
версиям с 01.12?», по умолчанию — да. Правило для каждой поздней версии V, поле за полем:
V не меняла поле (равно базе черновика) → записывается значение черновика; V меняла сама →
её значение оставляется (строка в предпросмотре); добавленный элемент добавляется в V без
конфликта (занятое обозначение → не переносится, строка в предпросмотре); выведенный —
выводится из V, если там не менялся. Перенос — в той же транзакции и предпросмотре.

## 4. Автораспределение

Чистые функции домена (`domain/allocate.py`); вход — интервалы объектов
`UnitSpan(unit_id, category_id, group_path, label, start_pos, end_pos)` между границами
версий, брони сегментами/частями, OOO, слоты блоков, закрепления. Результат
детерминирован: порядок обхода — `natural_key` + `_order`.

### 4.1 Приоритеты при нехватке объектов (часть 2 §4.2)

1. OOO;
2. замороженные части и заселённые (`in_house`) — hold: заселённая держит объект строки,
   пока он в фонде и не под OOO;
3. перемещённые заселённые (потерянный объект → `lost` → переезд) — **до слотов**: блок
   не оставляет живущего без объекта;
4. слоты блоков;
5. закреплённые брони;
6. подтверждённые (rank 0);
7. предварительные (rank 1) — первыми остаются без объекта.

Блок главнее брони, даже если бронь появилась раньше; блок никогда не переселяет
заселённого (его объект недоступен блоку до выезда). Блоки и OOO никогда не уменьшаются и
не удаляются автоматически. **Прошлое заморожено:** части, закончившиеся до сегодня, —
с объектом и без — не перераспределяются (находка L1 аудита).

### 4.2 Выбор объекта при равных возможностях

закрепление → непрерывность (объект предыдущей части сегмента; после переезда — другой
объект, ближе по дереву: тот же узел, иначе ближайший общий предок) → **пожелания**
(`prefs`, сумма priority, больше — лучше) → **HK** (не в объект с выездом в день заезда,
если есть свободный со вчера) → порядок. Пожелание важнее HK (код: prefs-фильтр до
`hk()`; тест `test_preferences_win_over_hk`).

### 4.3 Границы версий

Сегмент, пересекающий границу версии, режется на части; у частей правило непрерывности
**обратное переезду**: предпочитается тот же объект — если объект на границе не изменился,
бронь визуально остаётся в нём. Закрепление сегмента переходит на его части; с D
закреплённый объект не подходит (сменил категорию, выведён) — предупреждение `pin_invalid`
для частей после D (до D закрепление сохраняется), решает менеджер. Категории нет в фонде
с D — предупреждение у каждой затронутой брони, сегмент остаётся «без объекта». Индексы
частей (`seg_index`): публикация версии пересчитывает назначения через `run_allocation`,
закрепления переносятся на части по пересечению половинок суток. Нагрузка и сопровождение
на каждый день берут вес и признак категории из версии этого дня.

### 4.4 «Без пинг-понга»

Лоскутов из разных объектов внутри части нет: не хватило одного объекта на часть —
овербукинг (самыми длинными кусками, которые покрывает остаток по фонду). Закончившийся
овербукинг не мешает следующей брони. Группа совместного проживания занимает объект как
одна бронь. Отменённая бронь и no-show не занимают объект.

### 4.5 Овербукинг

Бронь без объекта — `overbooked`, ярко подсвечивается; для батлеров живёт как обычная
(сопровождение, дыры, нагрузка). Создать или изменить бронь/OOO/блок/пожелания с **новым**
овербукингом может только сотрудник с правом `stays.overbook`; импорт из Fidelio (когда
появится) — без проверки права. Гейт централизован в `run_operation`:
`may_overbook = after.overbooked − before.overbooked` (только НОВЫЙ овербукинг; работает и
при `window=None`); публикация/удаление версии фонда идут через тот же гейт. Отказ в
овербукинге не ломает публикацию фонда; закрепление без объекта сохраняется.

### 4.6 OOO поверх брони

Гость не заселён — бронь целиком в другой объект; заселён — переезд с даты OOO до конца
проживания (один раз). Закреплённая бронь — то же правило; закрепление до даты OOO
сохраняется.

## 5. Покрытие, нагрузка, предупреждения, кандидаты

### 5.1 Шаблоны и строки

Шаблоны заполняют дни периода у брони, группы или выбранных гостей: **«пара посменно»**
(A, B) — каждый день ведёт тот, кто по Графику на смене; оба на смене — A; никого — дыра;
**«один на весь срок»** (X) — X каждый день; дни вне смены X — «вне смены — переработка» с
кнопкой «добавить смену в График»; **«вручную»** — по дням. Шаблон заполняет только пустые
дни; ручные строки не трогает, пока не выбрано «заменить». Пересечение охватов: явный
список гостей сильнее строки «вся бронь/группа»; один гость в день у двух батлеров с
явным указанием — предупреждение. Переезд не требует действий (объект строки вычисляется).
Строки на дни, когда гостей уже нет (ранний выезд, отмена, изменение дат), удаляются
автоматически с записью в журнал.

«Добавить смену в График» — существующая запись ручной смены Графика; нужны `stays.assign`
и право на правку Графика; две записи в журнале (шахматки и Графика); Табель не меняется.

### 5.2 Нагрузка (часть 3)

**Место** = объект (бронь без объекта — своё место). Вес места в ночь = вес категории
(версии дня) × наибольший коэффициент VIP-кодов местa × коэффициент «Особого гостя»
(один раз на место). Коэффициенты **перемножаются, а не складываются**. Две брони в одной
вилле — вес виллы один, умножается на наибольший коэффициент кода. Вес делится поровну
между ведущими батлерами; отдельных надбавок батлеру нет. Нагрузка батлера на день = сумма
мест; сравнивается с лимитом; перегруз — предупреждение, не запрет. Брони в овербукинге —
с весом категории брони.

### 5.3 Предупреждения (не запрещают сохранить)

Не хранятся — вычисляются при каждом чтении против **актуального** Графика (смены и
отсутствия одним запросом на диапазон; кэша нет): дыра (в объекте с сопровождением живут
гости без батлера, кроме «отказался»); батлер вне смены или в отсутствии; перегруз; бронь
не получила объект; поздний выезд против заезда в тот же объект; «нужна подмена»
(назначенный в отпуске/на больничном); `pin_invalid`; `block_short` (группируется по
ночам, ordinal-даты в тексте); «категории нет в фонде с D».

### 5.4 Кандидаты и подмена (`domain/candidates.py`)

Кандидаты — из списка «сопровождают гостей», **на смене** по Графику, не в отсутствии
(коды-замены исключаются), нагрузка после назначения ≤ лимита. Порядок: (1) знает гостя
(вёл кого-то из этих гостей); (2) тот же объект; (3) тот же узел дерева; (4) иначе ближе
по дереву (длиннее общий префикс пути); (5) меньше нагрузка; (6) младший id. Пометка
«есть отлучка в смене». Список «нужна подмена» собирает дни из §5.3 с кандидатами.

## 6. Предпросмотр — операции одним путём

Каждая операция, меняющая брони, покрытие, фонд, OOO/блоки или пожелания, вызывается в
двух режимах: **предпросмотр** и **сохранение** — `preview.run_operation`: `lock_module`
до первого чтения состояния, снимок «до» → операция тем же кодом в транзакции → снимок
«после» → diff → откат. **Предпросмотр ≡ сохранение** (результат не может разойтись);
после предпросмотра в базе ничего не изменилось. Ответ: объекты «было → станет» (включая
сдвиги других броней), новые и исчезнувшие предупреждения, дельта покрытия (кто теряет и
получает гостей по дням, новые дыры, «вне смены», нагрузка против лимита), право на
овербукинг (§4.5). Ограничение: предпросмотр одной операции; цепочку «примеряют» по шагам.

## 7. Сопровождение и VIP-коды

### 7.1 Нужен ли батлер (`domain/escort.escort_need`)

Сопровождение нужно, если выполнено **любое** из условий: (1) категория объекта — с
сопровождением; (2) объект — в узле дерева с сопровождением (узел действует на всю ветку;
исключений внутри ветки нет — галочку ставят на нужные дочерние узлы); узел с
сопровождением и категория без — «или», нужно; (3) у брони VIP-код с отметкой
«сопровождение» (архивный код тоже считается); (4) среди проживающих **в брони или в
любой брони её группы** есть «Особый гость» — на его дни проживания. Ручная отметка брони
перекрывает правила в обе стороны; «не требуется (гость отказался)»— дыры нет, в карточке
«сопровождение: отказался» (действует и для «Особого гостя», и для любого кода). Бронь без
объекта — правила без узла; с объектом — учитывается и узел.

### 7.2 VIP-код брони

Как в Fidelio: живёт в брони, берётся из профиля главного гостя. Ручной выбор побеждает.
При создании брони и при смене главного гостя код копируется из профиля главного и поверх
ручной правки — с предпросмотром; архивный код профиля принимается (он уже стоит у гостя —
это не новый выбор). `set_main_code` поднимает `version` брони — открытые формы получают
409. Формат кода — только `[0-9]{1,8}`.

## 8. Видимость и персональные данные (§8 исходной спеки)

Три уровня (`application/visibility.py`); **сервер не отдаёт** поля, которые уровню не
положены (фильтрация в сериализаторах, а не в интерфейсе):

* **occupancy** (`stays.occupancy`) — занятость: объекты, даты, статусы, РЗ/ПВ, число
  гостей; ни фамилий, ни уровня, ни номера брони, ни метки. Фильтр «с сопровождением» —
  только атрибуты фонда (`unit_escorted`) — не оракул персональных данных.
* **names** (`stays.view`) — для работы службы: + номер брони, метка, короткое имя
  главного гостя, ◆ «Особый гость», VIP-код брони, батлеры дня; режим сопровождения —
  как статус табло.
* **full** (`stays.guests` + `stays.view`) — + заказчик, «оплата за», примечания,
  настраиваемые поля, логистика.

**Поиск ниже полного уровня — только по ФИО и номеру брони** (S8): ни телефона, ни почты,
ни полей, ни заказчика — иначе по ответу подбирается чужой телефон. Колонка
`stays_guests.name_text` (миграция 0020) — поиск по ней; `search_text` (полный уровень) —
по всем полям. Подбор гостя (`mine=1` — только свои) — те же правила.

**Выгрузки:** обезличенная (объект, даты, статус, число гостей, категория) —
`stays.occupancy`; полная — `stays.export` + `stays.guests`; все выгрузки — в журнал
аудита. Ячейки Excel экранируются от формульных инъекций (`safe_sheet_cell`, OWASP).
Полное удаление/обезличивание профиля по запросу — вне первого выпуска.

Открытие профиля в аудит **не пишется** (осознанное решение владельца); журнал — только
изменения.

## 9. Гости: справочник, семья, слияние

* **Вкладка «Гости»** — право `stays.guests` (+`stays.view`); уровню occupancy вкладки
  нет. Список: ФИО, ◆, телефон (только полный уровень), последний заезд, число
  проживаний; поиск (фамилия, телефон — при `stays.guests`, номер брони); фильтры: ◆,
  «был в периоде», «ДР в ближайшие 30 дней»; сортировка; по 200.
* **Карточка гостя:** профиль, предпочтения, особые даты, поля, примечание, семейное
  дерево (§2.2) и прочие связи, история проживаний (все брони, где гость жил: объект по
  фонду дня, даты, роль, кто вёл — «вёл я дд.мм–дд.мм» или с именем другого батлера),
  пожелания к объекту со статусом исполнения.
* **Семейный редактор** — визуальное дерево в карточке (гость в центре; «+ родитель»,
  «+ супруг(а)», «+ ребёнок» — поиск существующего или новый человек: фамилия, имя, пол);
  связь и новый гость создаются **одной записью** (`create_link`/`add_links`) под замком
  модуля; отказ любой проверки — rollback целиком; аудит на создание гостя и каждую связь.
* **Объединение дублей** (`POST /guests/merge`): выбрать двух → «объединить в …»;
  предпросмотр «что перенесётся» ≡ сохранению; под `lock_module`; все проверки до первой
  записи; брони, проживания, связи (без дублей), предпочтения, особые даты, поля
  переносятся; второй профиль удаляется; нарушение дерева — 409; капы пожеланий/связей;
  автор профиля остаётся, только если он у обоих один (S10).
* **Пожелания к объекту** (часть 2 §5): вид (узел дерева / флаг / объект — тот же
  постоянный id или его наследник по lineage), ссылка, priority; учитываются пожелания
  главного гостя (первый main по дате); бюджет SQL задокументирован. Правка — через общий
  путь операций (пересчёт, предпросмотр, право на овербукинг).

## 10. Батлер — «Мои гости» (часть 4)

* **«Свой гость»** — у батлера есть хоть одна строка покрытия (назначение на день) в
  прошлом, сейчас или в будущем — **без ограничения срока** (строгое требование ИБ;
  решение владельца). Подменный батлер — так же: гости подмены остаются его навсегда.
  Плюс гости, которых батлер сам завёл через семейное дерево (`created_by_employee_id`).
  «Свои» брони — где у батлера есть строки; предварительные — тоже свои, с пометкой.
* **Права:** `stays.mine` (экран «Мои гости»; полный профиль своих гостей и их брони на
  чтение), `stays.mine_guest_edit` (правка профиля: свободные поля — предпочтения,
  пожелания с предпросмотром, особые даты, семья и прочие связи, поля, примечание; ФИО,
  телефон, email, ДР, пол, ◆, VIP-код — заперты, 403), `stays.mine_res_edit` (правка
  брони: состав — кроме главного, логистика, сопровождающие, примечание, поля брони;
  LOCKED-поля — номер, даты, РЗ/ПВ, категория, метка, заказчик, «оплата за», группа,
  `vip_code`, `escort_mode`, переезды, закрепления — 403; проверка «побайтово равны»).
  Прежнее `stays.edit_mine` заменено двумя правами (миграция 0019 выдаёт оба его ролям).
  `stays.view` — теперь всем (было: старший и выше).
* **Состав брони батлером:** новый проживающий — только родственник проживающего по
  семейному дереву (в том числе вычисленный: бабушка жены, внук) или его прямая связь
  (ассистент, охрана, няня…). Гость без связи — 403. **S9:** если прежний чужой
  проживающий становится «своим» в результате правки (сдвиг дат, вторая запись) — 403
  (`check_no_gained_guests`, внутри операции — и в предпросмотре). Правка брони выехавшего
  гостя — без срока.
* **Связи батлера:** вторая сторона — только свой гость или новый человек (заведённый им
  человек сразу «свой»); связь своего с чужим существующим — 403 (иначе через состав
  брони батлер открыл бы себе чужой профиль); новый человек со вторым родителем-чужим —
  403, записи не создаются.
* **Принадлежность проверяется на каждом запросе**; чужая бронь/гость/профиль — 403
  («Это не ваша бронь: вы не ведёте её гостей»).
* **Экран «Мои гости»** (телефон; макет «В» согласован 27.10.2026):
  * **«Сегодня»** — карточки гостей, которых батлер ведёт сегодня: ◆, VIP-код, объект
    (номер по версии дня), заезд/выезд, логистика на сегодня/завтра, предпочтения,
    ближайшие особые даты (ДР в пределах 7 дней); выезжающие сегодня гости прошлой ночи;
    примечание брони на карточке; пустой состав — только у брони без проживающих.
  * **«Мой месяц»** — личная мини-шахматка: строки — объекты своих броней месяца, полосы
    по половинкам суток; ◀ ▶ месяц (общий с Табелем); полоса нагрузки по дням (один гость/
    несколько/выше лимита); отсутствия по Графику — «О»; предварительные — бледной
    пунктирной полосой; своя бронь без объекта — строка «без объекта» внизу, полоса
    красная; клик по полосе — карточка брони и гостей.
  * **«Все мои гости»** — поиск по фамилии среди своих за всё время (S8 — только ФИО);
    карточка — профиль и история проживаний; последний заезд и число проживаний — только
    начавшиеся; следующий заезд — отдельное поле.
* **Шахматка и табло у батлера** — уровень «с фамилиями», только чтение (ни создания
  броней, ни назначений, ни OOO/блоков); ◆ и VIP-коды чужих гостей видны (как всем на
  этом уровне); свои брони выделены рамкой, клик по своей — полная карточка, по чужой —
  карточка уровня «с фамилиями». Табло дня — целиком (включая «Требуют внимания»,
  назначения коллег, подбор кандидатов с их нагрузкой), но без кнопок назначения и
  подмены. Родня проживающих в карточках — только связи их семей.
* **Бюджет SQL (§7 части 4):** постоянное число запросов на экран (mine_today/month/
  guests/card); история батлера — пакетами; `MAX_MONTH_DAYS=62`, `GUESTS_PAGE=50`; бюджет
  не зависит от длины истории.

## 11. Экраны и виды

1. **Шахматка объектов** — объекты × дни, полосы по половинкам суток, переезды, блоки/
   OOO, цвет метки, ◆ и VIP-код (уровень names+); под фамилией — кто ведёт сегодня.
   Строки по умолчанию группируются по дереву (разделы сворачиваются; свёрнутые в DOM не
   рисуются; по умолчанию развёрнуты виллы, корпус свёрнут); внутри узла — по порядку
   категории, затем натурально по обозначению. Граница версии внутри месяца: «нет в фонде»
   — серым; смена номера/категории — подписью («4003 → 4103 с 15.11»); строка — постоянный
   объект. Сортировки: по дереву (по умолчанию), номер ↑↓, категория ↑↓, этаж ↑↓,
   загрузка за месяц ↑↓; переключатель «группировать по дереву».
2. **Шахматка батлеров** — батлеры × дни; фон дня — смена по Графику; в ячейке — объекты и
   гости, нагрузка/лимит; красным — перегруз и «вне смены»; клик — назначить, заменить,
   «добавить смену» (по правам).
3. **Табло дня** — дата ◀ ▶; итоги; вкладки «Заезды / Выезды / Проживают / Требуют
   внимания»; группа no-show на дату заезда; строка — время (РЗ/ПВ), объект, гости
   (главный + связанные, родня среди проживающих), статус сопровождения (ведёт: кто —
   кого / ⚠ не назначено + кандидаты / ↔ нужна подмена + кандидаты / отказался / не
   требуется), детали. Удобно с телефона.
4. **Загрузка** — строки — узлы дерева (фильтр «Где») + «Итого по выбранному»; узел
   сворачивается; переключатель «% / штуки»; цвет от 50/80/100 %. Строки дня: всего
   объектов (фонд на D), проживают (ночь D→D+1), гостей, ▲ заезды, ▼ выезды, свободно
   (всего − проживают − OOO − блоки, ≥ 0), OOO, блоки. Загрузка % = (проживают + блоки) /
   (всего − OOO); знаменатель 0 — «—». День «выезд + заезд в тот же объект» — в обоих
   счётчиках, в «Проживают» — один раз. Уровень occupancy видит вкладку целиком. За
   прошлые ночи — записанные блоки. Клик по «Проживают» — шахматка узла с этого дня.
5. **Брони** (вкладка) — список с фильтрами (§11.7), период по умолчанию — месяц; режим
   попадания: проживание пересекает (по умолчанию) / заезд / выезд / создана; колонки: №,
   главный гость (◆, код), заезд, выезд, ночей, категория, объект («4003 → 4105»),
   статус, метка, батлер(ы), РЗ/ПВ, создана; сортировка кликом (по умолчанию заезд ↑, №);
   клик — карточка брони; серверные фильтр/сортировка, выдача по 200 «Показать ещё»;
   права — names уровень (occupancy не показывается — список броней без фамилий сам по
   себе оракул); выгрузка — `stays.export`, в аудит.
6. **«Мои гости»** — §10.
7. **Фильтры (одна панель на все виды):** Где (дерево, галочки по узлам — узел включает
   ветку), категории, флаги, вид объекта, сопровождение, ◆/код, батлер, статус, поиск.
   Внутри измерения — «или», между измерениями — «и»; **флаги — всегда «и»**. Узлы,
   категории и флаги проверяются на каждый день **по версии фонда этого дня**. Сохранённые
   наборы — в `localStorage` (с try/catch). API: `group_ids`, `category_ids`, `flag_ids`,
   `kinds` — списками (`building` и одиночный `category_id` ушли); фильтрация — по уже
   загруженному `FundTimeline`, объём запросов от фильтров не растёт.
8. **Карточка гостя и брони** — §9; бронь — состав по датам, сопровождающие, логистика,
   покрытие по дням, лента изменений «было → стало».
9. **Настройки → Фонд и категории:** шапка «Фонд на дату» (действующая/черновик/любая из
   истории), кнопки «Флаги объектов», «Изменить с даты…», «Выгрузить фонд», «Загрузить
   фонд»; плашка черновика (дата, изменения, «Предпросмотр», «Опубликовать», «Удалить»);
   слева дерево, справа объекты узла с действиями («Изменить», «Разделить», «Сменить
   номер», галочки «Объединить», массовая смена узла); подсветка изменений черновика;
   вкладки «Объекты», «Флаги объектов», «Категории», «Виды» (справочник видов: название,
   порядок, «раскрывать на шахматке по умолчанию», архив; права `stays.setup`); история
   версий. Вне черновика экран только показывает фонд.
   Прочие экраны Настроек: «Сопровождение» (список «сопровождают гостей», правила, лимит,
   VIP-коды), «Настраиваемые поля», «Метки броней».

Формы: бронь (состав, группа, переезды, логистика), гость (со связями), назначение
(шаблон/по дням/подбор). **Каждая форма изменения и действие «Перенести» показывают
предпросмотр (§6) до кнопки «Сохранить».** Месяц общий с Табелем и Графиком
(`state.year/state.month`); ◀ ▶ и «Сегодня» как в Табеле; API принимает `first/last`,
лимит 62 дня; гонки быстрой смены месяца — `loadGenerationFor`.

## 12. Файл фонда (Excel) и начальная загрузка

### 12.1 Файл фонда

Листы и колонки (выгрузка текущего фонда на выбранную дату — готовый заполненный пример):
**Категории** (ID, код, название, вид, вес, сопровождение, порядок) · **Дерево** (ID,
название, родитель — полный путь, порядок; сопровождение узла) · **Флаги** (ID, название,
цвет) · **Объекты** (ID, номер, категория-код, узел-путь, этаж, «Из чего» — ID через
запятую, по колонке на флаг) · скрытый лист **«Списки»** — пути дерева для выпадающих
списков колонок «Родитель» и «Узел» (для новых узлов список не обновляется сам — путь
вводится руками). Ссылки между листами — по коду категории и пути узла (у новых строк ID
ещё нет); ID — «кто это», код и путь — «куда положить». ID серые, защищены от правки;
в Настройках — «#57». «/» в названии узла запрещён.

**Правила строки:** ID заполнен — та же сущность, меняется изменённое; ID пуст — новая;
ID есть в фонде, строки нет — выводится с даты (в предпросмотре — список «будут выведены»);
ID неизвестен или повторяется — ошибка; «Из чего» у новой строки — деление/объединение
(lineage). **Проверка файла** — все ошибки списком с листом и строкой; пока есть хоть одна
— ничего не применяется. Файл, выгруженный и загруженный без правок, — пустой черновик.
Неизвестное название вида — ошибка файла (новые виды файлом не заводятся); вид — по
названию.

**«Загрузить как черновик с даты»** (`stays.setup`) — файл превращается в черновик со всем
циклом §3; черновик уже есть — отказ с предложением открыть или удалить. Кнопками и
файлом делается одно и то же, результат и предпросмотр одинаковы.

### 12.2 Начальная загрузка («заменить всё»)

Только администратор (`stays.reset`, ADMIN_ONLY) и только пока выключен переключатель
«Шахматка в эксплуатации» (включённый — 409; кнопка убирается). Порядок (`initial_load`):
замок модуля → 409 «в эксплуатации» → 422 без слова подтверждения **«ЗАМЕНИТЬ»** → **409
при несовпадении отпечатка** предпросмотра (`fingerprint`: данные изменились после
предпросмотра — повторите) → 422 по ошибкам файла → **копия до удаления**
(`data/backups/stays/stays-ГГГГММДД-ЧЧММСС.xlsx`: листы для чтения — фонд на сегодня,
брони, гости — и по листу на каждую удаляемую таблицу, включая будущие версии, черновик,
блоки и OOO, назначения, переезды, логистику; запись через временный файл → fsync →
rename; копию не удалось записать — 409, ничего не удалено; скачивается сразу) → удаление
всех данных шахматки → исходная версия фонда из файла (`valid_from = 2000-01-01`) →
распределение (броней нет) → аудит `stays_reset` (кто, когда, сколько удалено/загружено,
имя копии). **Одна транзакция.** Настройки модуля, метки, настраиваемые поля, список
«сопровождают гостей», лимит, **справочник VIP-кодов** — сохраняются (KEEP); сотрудники,
График, Табель и журнал не трогаются. ID в файле игнорируются (предпросмотр предупреждает,
если заполнены). Скачивание копии — только имя, matching `stays-\d{8}-\d{6}\.xlsx`
(path traversal отклоняется). Брони и гости в начальную загрузку не входят — после замены
шахматка пустая. Демо-данные в проде не появляются (сид — только `DEMO_SEED=1`;
детерминирован: `random.Random(23)`, идемпотентен).

## 13. Права

Матрица — в манифесте модуля (`app/modules/stays/manifest.py`, источник истины; ADR-0012):

| Право | Что даёт | По умолчанию |
|---|---|---|
| `stays.occupancy` | загрузка без персональных данных; обезличенная выгрузка | непрофильные службы (роль «Загрузка без гостей») |
| `stays.view` | шахматки, табло, загрузка, «Брони» с фамилиями (без телефонов и ДР) | **все** (с части 4; было: старший и выше) |
| `stays.edit` | брони, состав, блоки/OOO, статусы | старший и выше |
| `stays.overbook` | сохранять изменения с новым овербукингом | старший и выше |
| `stays.assign` | назначения, шаблоны, подбор и подмена | старший и выше |
| `stays.guests` | профили гостей целиком: телефоны, ДР, предпочтения, история, связи; вкладка «Гости» | старший и выше |
| `stays.mine` | экран «Мои гости»; полный профиль своих гостей и их брони на чтение | все |
| `stays.mine_guest_edit` | правка профиля своих гостей (свободные поля) | все |
| `stays.mine_res_edit` | правка броней своих гостей (состав, логистика, сопровождающие, примечание) | все |
| `stays.setup` | фонд и версии, категории и виды, флаги, настраиваемые поля, «сопровождают гостей», лимит, метки, VIP-коды | менеджер и выше |
| `stays.export` | выгрузка в Excel (пишется в аудит) | менеджер и выше |
| `stays.reset` | «заменить всё» и переключатель «в эксплуатации» | только администратор |

Роли: «Руководство: только просмотр» (`stays.view`, `stays.guests`); «Загрузка без
гостей» (`stays.occupancy`). Принадлежность брони/гостя батлеру сервер проверяет на
каждом запросе. Замечание аудита (C-1): `POST /guests/merge` требует `stays.edit`, тогда
как единственный UI-путь (вкладка «Гости») — `stays.guests`; на дефолтных ролях разницы
нет — статус решения см. `decisions.md`.

## 14. Аудит и журнал

Все изменения броней, гостей, фонда (публикация `fund_version:{id}` с полной разницей,
удаление версии, правки справочников), покрытия, OOO/блоков, слияния, начальной загрузки
(`stays_reset`), переключения «в эксплуатации», выгрузок — в общем журнале аудита с
разницей полей «было → стало». История брони — записи журнала с целью «бронь №…»;
история проживания гостя — записи «проживающий» по всем его броням. Открытия профилей в
аудит не пишутся (§8). «Добавить смену в График» — две записи (шахматки и Графика).

## 15. Устойчивость, производительность, бюджеты

* Конфликт двух менеджеров на одной брони/черновике — проверка `version`: второе
  сохранение — 409 «изменилась — обновите».
* Распределение — по событиям модуля (сохранение брони, переезд, блок, статус, публикация
  версии), не по таймеру; валидации покрытия считаются при чтении.
* Предупреждения — против актуального Графика при каждом чтении; отменили смену —
  следующее открытие шахматки показывает «вне смены».
* Бюджет запросов шахматки на 440 объектов — ≤ 30 на месяц (31 день); «Мои гости» —
  постоянное число запросов на экран; `fund_for` — ≤ 6 запросов на диапазон версий.
  Объекты, которых нет в фонде часть месяца, в DOM свёрнутых разделов не рисуются.
* Известное ограничение (находка P-1 аудита, принято): `list_ooo`/`list_blocks` и экспорт
  «Броней» грузят диапазон без SQL-пагинации — при многолетней истории потребуется
  SQL-фильтр и пагинация.
* Все пишущие пути под `lock_module` (замок — строка `stays_settings(id=1)`); писатели вне
  `run_operation` (слияние, связи, VIP-коды, черновики, сброс, «в эксплуатации») берут
  замок сами.

## 16. Тесты (критерии приёмки)

Обязательные группы (детальные перечни — в архивных спеках частей, §«Тесты»):

* **Домен:** половинки суток и сегменты (5 рабочих примеров PoC — обязательные тесты);
  автораспределение (приоритеты, «без пинг-понга», границы версий, HK, пожелания,
  слоты блоков); родство (все названия по полу и без, пример владельца «сын → правнук
  бабушки Ивана», запреты); escort_need (все четыре правила, ручная отметка, declined);
  веса и деление нагрузки; кандидаты («знает гостя» первым, смены, отсутствия, лимит).
* **API:** матрица прав (менеджер, старший, батлер на своей/чужой брони, руководство,
  непрофильная служба, names-роль); уровень occupancy не получает ни одного поля гостя ни
  в одном ответе (свип всех GET-маршрутов с маркерными словами — `test_pd_leaks`);
  батлер не открывает чужих (свип); preview ≡ save для каждой операции, после
  предпросмотра БД не изменилась; 409-гейты (версии, черновик, отпечаток, пересечение
  OOO); no-show (объект освобождается, покрытие снимается с журналом, возврат с новой
  датой); бюджет SQL на 440 объектах и «Мои гости»; «добавить смену» требует оба права и
  пишет в аудит Графика.
* **Файл фонда:** выгрузка → загрузка без правок = пустой черновик; «Родитель» в любом
  порядке строк; нет родителя — ошибка со строкой; глубина 6+; ошибки файла — списком;
  ширина шапки листа = ширина строки («Брони», «Гости»); скачивание копии отклоняет
  path traversal.
* **Актуальность:** отменили смену в Графике — следующее чтение показывает «вне смены»;
  поставили отпуск — «нужна подмена».
* **Интерфейс:** UI-сценарии (бронь → назначение шаблоном → конфликт → «добавить смену» →
  табло; версии фонда; «Мои гости»: «Сегодня», «Мой месяц» ◀ ▶, поиск, правка профиля;
  семейный редактор; вкладка «Гости»; «Виды»); смоук всех экранов под ролями.
* **CI проекта:** манифест и пробный модуль, `doc_links`, линтеры, OpenAPI, PostgreSQL 16
  (отдельный job — raw-SQL миграции и типы колонок ломаются только на PG).
