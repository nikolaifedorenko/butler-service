# 2. Архитектура

Решения и их обоснование — в [ADR-0013](adr/0013-celevaya-arhitektura.md) (целевая
архитектура) и ADR-0010…0012 (модульный монолит, роли, манифест). Здесь — как это устроено в
коде сейчас.

## 2.1 Состав

* Python 3.15, FastAPI, SQLAlchemy 2, Alembic; PostgreSQL 18 — единственная СУБД, в том числе
  локально и в тестах.
* Один образ приложения запускается тремя ролями: `app` (HTTP), `worker` (очередь фоновых
  задач) и одноразовый `migrate` (схема, справочники, первый администратор). Рядом — контейнер
  Gotenberg (PDF из DOCX, раздел 2.8). В проде перед ними nginx с TLS и контейнер бэкапов
  ([документ 3](03-ustanovka.md)).
* Интерфейс — статика без сборки: ES-модули, `lit-html`, CSS-токены ([документ 6](06-interfeys.md)).
* Модульный монолит: каталог `app/` — `core/` (инфраструктура), `modules/` (предметные
  модули), `bootstrap/` и `main.py` (сборка).

## 2.2 Правила одного отеля

Отель один; чтобы второй добавлялся без переделки, соблюдаются четыре правила (ADR-0013, раздел 1):

1. часовой пояс и гостиничные сутки читаются через `app/core/time.py` (`local_date`,
   `local_now`, `from_local`, `local_midnight`), а не из настройки напрямую;
2. гости, сотрудники, учётные записи и права не содержат ничего, что относится к одному отелю;
3. всё, что относится к объекту размещения (фонд, брони, блоки, недоступность), достижимо от
   корня фонда;
4. внешний идентификатор записи — тройка «система, экземпляр, id» (`core/external.py`,
   колонки `ext_system`, `ext_instance`, `ext_id` у гостя и брони, уникальны вместе): два
   экземпляра Fidelio различимы, повторный импорт обновляет запись.

Настройки, табель, ночной отчёт и электрокары общие на систему.

## 2.3 Время и данные

* Момент — `timestamptz`, в базе UTC (тип `Moment` в `core/time.py`). Длительность — целое число
  минут. Гостиничная дата — `date`. Местное время получается из момента и часового пояса
  `APP_TZ`.
* JSON — `JSONB` (тип `Json` в `core/db.py`). Где порядок ключей — порядок показа, используется
  `OrderedJson`: он пишет порядок под служебным ключом `_key_order`.
* Запрет двойной занятости объекта дублируется ограничением базы (`EXCLUDE` по диапазону).
* Схема — одна начальная ревизия Alembic (`app/bootstrap/alembic/versions/0001_baseline.py`);
  дальше обычные ревизии. Старые базы не обновляются: боевых данных не было, демо-базу
  создают заново.

## 2.4 Слои внутри модуля

```
interface  →  application  →  domain
                  ↓
              ports  ←  adapters
```

* `interface` — роутер: разбирает запрос, проверяет право, вызывает прикладную функцию.
* `application` — прикладные операции. Операция помечена `@transactional` (`core/db.py`): всё
  её тело — одна транзакция, запись аудита внутри; операция в операции — точка сохранения.
* `domain` — чистые функции без базы и фреймворка.
* `ports` — интерфейсы, которые модуль объявляет сам; `adapters` — их реализации (ORM,
  внешние сервисы). Адаптеры чужих модулей подключает `bootstrap`.
* Ошибки — наследники `ServiceError` (`core/errors.py`); класс задаёт статус HTTP, тело
  ответа `{"detail": …}`.
* Модель ответа наследует `ApiModel` (`core/schemas.py`): поле, которого нет в модели, — ошибка.
  Ключ присутствует всегда, пустое значение — `null`.

## 2.5 Модули и их слои

Модуль описывает манифест `modules/<имя>/manifest.py` (`core/manifest.py`): имя, слой, пункты
меню, экраны Настроек, права, задачи, сверки для «Настройки → Обзор». Модуль импортирует только
модули слоёв ниже; соседи по слою друг друга не импортируют; циклов нет. Приватные слои модуля
(`domain`, `adapters`, `interface`) снаружи не импортируются — публичны `application` и `ports`.
Контракт import-linter (`.importlinter`) частично генерирует `tools/gen_importlinter.py` из
манифестов; то же проверяют `tests/test_modules_architecture.py` и
`tests/engine/test_architecture.py`.

| Слой | Модули | Назначение |
|---|---|---|
| ядро | `core` | база, конфигурация, время, ошибки, вход и сессии, права, аудит, наблюдаемость, медиа |
| 1 | `people`, `exchange`, `jobs` | сотрудники и периоды работы; файловые форматы (XLSX, DOCX, PDF, CSV); очередь задач |
| 2 | `timesheet`, `cars`, `notify`, `audit`, `fund` | учёт времени (движок v7.1); электрокары; Telegram и почта; журнал; фонд объектов версиями |
| 3 | `night`, `guests` | ночной отчёт; гости |
| 4 | `employees`, `access`, `stays`, `docs` | карточки и жизненный цикл сотрудников; вход и права; брони, блоки, OOO, размещение; заявления |
| 5 | `settings`, `board` | настройки и «Обзор»; шахматка, «Сегодня», сводки (только чтение, своих таблиц нет) |

Что нижнему модулю нужно от верхнего, он получает без импорта: функцию подключает `bootstrap`
либо модуль объявляет её в манифесте.

## 2.6 Движок расчёта

Модуль `timesheet` — детерминированный движок v7.1 ([документ 9](09-raschet-v7-1.md)): чистые
функции «данные → данные», пять слоёв (`domain / application / ports / adapters / interface`),
справочники CFG-*, правила RUL-*, инварианты INV-*, трассируемость каждого действия. Вкладки
учёта независимы: открытие одной не запускает расчёт другой; тяжёлый конвейер
(`settle()` + `evaluate_flags()`) запускает только «Управленческий табель». Четыре режима
работы с периодом: просмотр, чтение закрытого, закрытие, пересчёт (таблица 7.2 документа 9).
Приёмочные примеры EX-01…EX-55 и все инварианты — в `tests/engine/`.

## 2.7 Фоновые задачи

Очередь на PostgreSQL (модуль `jobs`) с повторами и расписанием; исполняет сервис `worker`
(`app/bootstrap/jobs_worker.py`). Задачи объявляют манифесты модулей (`JobSpec`):

| Задача | Модуль | Период |
|---|---|---|
| `night_sync` | `night` | `NIGHT_SYNC_SECONDS` (60 с): досоздание смен, автозакрытие отчётов в 08:00 |
| `notify_outbox` | `notify` | 60 с: доотправка исходящих уведомлений |
| `media_cleanup` | `core` | сутки: чистка медиа |

В GET-запросах фоновой работы нет. Воркер приводит расписание к списку задач из манифестов
при старте.

## 2.8 PDF

PDF из DOCX делает Gotenberg по сети (`modules/exchange/adapters/gotenberg.py`, порт `PdfConverter`
в `exchange/ports`): прикладная функция `docx_to_pdf` отдаёт `(байты | None, причина)`, а
вызывающий модуль решает, отказать ли с `501` и подсказкой. Готовность сервиса проверяется
`/health` и запоминается на 15 секунд. Адрес — `GOTENBERG_URL`; в тестах преобразователь
подменяется (`documents.set_pdf_converter`), а при заданном `GOTENBERG_URL` (в CI это контейнер)
выполняется настоящая конвертация.

## 2.9 Вход и сессии

Пароли — argon2id; сессия — случайный токен в cookie и запись в таблице `user_sessions`;
лимит попыток входа — таблица `login_attempts`. Подробно — [документ 5](05-bezopasnost.md).

## 2.10 Не сделано из ADR-0013

Раздел 6 ADR-0013 описывает больше, чем реализовано. Сейчас в коде нет:

* конвейера импорта из Fidelio (сырые строки → сопоставление → проверка → предпросмотр →
  фиксация) и порта источника броней с адаптерами «файл» и «база»; внешний идентификатор для
  него уже есть;
* синхронных доменных событий «после фиксации транзакции»;

Это решения на будущие шаги; ADR остаётся целевым.

## 2.11 Структура репозитория

```
app/                  приложение (core/, modules/, bootstrap/, main.py)
static/               интерфейс: index.html, sw.js, css/, js/ (app.js, core.js, registry.js, ui/, modules/), vendor/
tests/                pytest: по модулям (engine/, stays/, fund/, …) и сквозные
e2e/                  сценарии Playwright
tools/                проверки и сценарии (bump_version, doc_links, export_openapi, run_*_scenario.sh, …)
deploy/               прод: nginx, бэкапы, README
docs/                 документация (этот набор), adr/, openapi.json, archive/
assets/ templates/    шрифты для PDF; шаблоны документов
docker-compose.yml        локальный профиль (db, app, worker)
docker-compose.prod.yml   боевой профиль (db, migrate, app, worker, nginx, backup)
```
