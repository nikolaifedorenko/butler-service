# Изменения 14.10.2026 — безопасность и робастность (батч «Security») + исправления ревью

Батч закрывает класс типовых уязвимостей веб-приложения (OWASP Top 10) и несколько
robustness/performance-дефектов, найденных при внутреннем аудите. Расчётная модель
не тронута — движок v7.1 не менялся. После первого прогона CI и ручного ревью
в батч внесены исправления (раздел «Исправления ревью» ниже).

## CSRF-защита (double-submit cookie)

- **Middleware** (`app/main.py`): mutating-запросы (POST/PUT/PATCH/DELETE) требуют
  пару «cookie `tt_csrf` + заголовок `X-CSRF-Token`». Сессия остаётся в httponly-cookie
  (`SameSite=Lax`) — кросс-сайтовый запрос не может прочитать cookie чужого origin,
  поэтому подделать пару нельзя. Сравнение токена — побайтовое
  (`secrets.compare_digest`), постоянное по времени.
- **Порядок проверки**: токен валидируется **до вызова обработчика** — отклонённый
  запрос (403) не производит побочных эффектов. На 403-ответ cookie тоже выдаётся:
  «обновите страницу и повторите» действительно лечится обновлением.
- **Исключение**: `POST /api/auth/login` — точка входа, CSRF-cookie у клиента ещё нет
  (login-CSRF — отдельная поверхность с низкой критичностью, осознанное решение).
- **Фронтенд** (`static/js/core.js`): `api()` и `multipartApi()` автоматически
  добавляют `X-CSRF-Token` для mutating-запросов; сырые `fetch` печати заявления
  и загрузки бланков (`static/js/app.js`) — тоже.
- **Флаг** `CSRF_ENABLED` (по умолчанию `1`): в pytest и сценарных харнесах защита
  отключается (`tests/conftest.py`, `tools/run_*_scenario.sh`) — харнесы ходят в API
  из node без браузерной пары cookie+заголовок. Смоук интерфейса
  (`tools/run_ui_check.sh`) работает **с включённой** защитой: он идёт через jsdom и
  настоящий `api()`, проверяя всю цепочку. Механизм покрыт `tests/test_csrf.py`,
  включая проверку «403 не создаёт отметку» и не-ASCII заголовок (403, не 500).

## SECRET_KEY: отказ стартовать со слабым ключом

- `_check_secret_key()` (`app/main.py`) до инициализации БД: пустой ключ, короче
  16 символов или начинающийся с `change-me` — `RuntimeError`, старт невозможен.
  С таким ключом cookie-сессию может подделать кто угодно.
- Escape-hatch только для локальной разработки: `ALLOW_INSECURE_DEV_SECRET=1`
  (предупреждение в лог вместо отказа).
- `./run.sh` при первом запуске создаёт `.env` из `.env.example` со сгенерированным
  `secrets.token_hex(32)` — локальный старт остаётся «из коробки».
- **Breaking для деплоя**: docker-compose больше не подставляет `change-me-in-production`
  по умолчанию — существующие окружения обязаны задать `SECRET_KEY` (или
  `ALLOW_INSECURE_DEV_SECRET=1` на время миграции). Тестовые харнесы переведены на
  ключи ≥16 символов.

## Rate-limit входа

- `POST /api/auth/login`: не более 10 неудачных попыток с одного IP за 5 минут,
  далее 429. Счётчик сбрасывается после успешного входа. Несуществующий логин по-
  прежнему считает хеш (timing-атака на перечисление логинов закрыта ранее).
- Ограничение: счётчик in-memory — при нескольких воркерах/инстансах нужен общий
  стор (Redis/БД); за reverse-proxy без доверенного `X-Forwarded-For` лимитится
  адрес прокси. Для одноворкерного развертывания достаточно.

## Пароли новых учётных записей

- Общий дефолт `demo1234` **удалён**: новая учётная запись без явно заданного пароля
  получает случайный 12-символьный (алфавит без визуально похожих 0/O/1/l/I),
  который возвращается администратору ровно один раз в поле `initial_password`
  ответа создания и показывается в toast. Демо-сид по-прежнему использует
  `demo1234` (только для локальной демо-БД).
- Поля пароля в карточке сотрудника: `type=password`, `autocomplete=new-password`.

## Эскалация прав и каталог прав

- `can_manage_user` (`app/auth.py`): manager управляет учётными записями, но **не**
  назначает роль `admin` и не меняет учётные записи администраторов (иначе это
  эскалация до `access.manage`). Значение роли — только из известного набора (422).
  Фронтенд фильтрует список назначаемых ролей по роли текущего пользователя.
- Массовый перевод эндпоинтов с ролевых стражей (`require_manager`,
  `current_principal`) на каталог прав `require_perm(...)`: employees, schedule,
  tabel, cars, night, punches, mgmt. Область доступа по умолчанию не изменилась
  (supervisor входил в `require_manager` и имеет эти права в `ROLE_DEFAULTS`),
  но права стали **настраиваемыми** через группы и индивидуальные гранты
  (раздел «Настройки → Права доступа»).
- Отметки: POST `/api/punches` за себя требует `me.punch`; за другого сотрудника
  или задним числом (`ts`) — `punches.manage`. Отмена отметки — `punches.manage`.

## Инъекции и лимиты загрузки

- **CSV/Excel formula injection** (OWASP): `safe_sheet_cell()` (`app/deps.py`)
  предваряет апострофом значения, начинающиеся с `= + - @ TAB CR`; применяется во
  всех выгрузках с пользовательскими строками — audit CSV, mgmt XLSX, schedule XLSX.
- **Загрузка бланков**: `upload_template` читает не более 5 МБ + 1 байт (раньше
  `read()` буферизовал тело любого размера до проверки); `_check_zip_size`
  (`app/doc_render.py`) — защита от zip-бомбы: ≤50 МБ в распакованном виде,
  ≤2000 записей, корректный zip-контейнер.

## Валидация входа и идемпотентность

- `year 1..9999` / `month 1..12` — 422 вместо 500 в Табеле, Графике, mgmt.
- `POST /api/schedule/range-absence`: `last ≥ first`, период ≤366 дней,
  ≤500 сотрудников за раз.
- `number_to_words` (`app/doc_render.py`): отрицательные и ≥1000 больше не роняют
  рендер заявления (IndexError → 500); «N тысяч» — запасная формулировка.
- `POST /api/employees/{id}/deactivate`: переключатель заменён явным параметром
  `?active=` (по умолчанию `false`). **Breaking для внешних API-клиентов**: повторный
  запрос при сетевом ретрае больше не инвертирует состояние. Веб-интерфейс
  эндпоинт не использует.
- Электрокары: передать кар может только текущий держатель либо
  supervisor/manager/admin (`handover_car` в `app/cars.py`).

## Производительность

- Индексы `ix_sched_shifts_start` (`schedule_shifts.start_utc`) и
  `ix_sched_abs_start` (`schedule_absences.start_utc`) — модель + миграция
  `CREATE INDEX IF NOT EXISTS`: доска «кто на работе» и статус смены фильтруют по
  `start_utc` без `employee_id` (полный скан растущих таблиц).

  загруженные периоды трудоустройства вместо повторных `is_employed` на каждый день
  (стартовый сид и «Продолжить/Сбросить»).

## Исправления ревью (после первого прогона CI)

- **B1 — порядок CSRF-проверки**: в первой версии middleware сначала выполнял
  запрос (`call_next`), затем проверял токен и подменял ответ на 403 — побочные
  эффекты отклонённого запроса уже были закоммичены (воспроизведено: отметка
  создавалась несмотря на 403). Исправлено: проверка до обработчика; тест
  `test_csrf_requires_token_header` теперь утверждает отсутствие побочных эффектов.
- **B1.1 — не-ASCII заголовок**: `secrets.compare_digest` для str с не-ASCII бросает
  `TypeError` (→ 500 от управляемого клиентом заголовка). Сравнение переведено на
  байты; добавлен тест.
- **B2 — сырые fetch без токена**: печать заявления (`/api/docs/render`) и загрузка
  бланков (`/api/docs/templates`) в `app.js` не добавляли `X-CSRF-Token` и в проде
  получили бы 403 (а загрузка бланка ещё и выполнилась бы). Добавлен заголовок.
- **B3 — красный CI**: (а) ruff I001 в 4 файлах — порядок импортов исправлен;
  (б) `gen_js_globals.py --check` — `getCookie` внесена в `tools/js_globals.json`;
  (в) харнес-скрипты `tools/*.sh` стартовали сервер с ключами 14–15 символов —
  новая проверка SECRET_KEY их роняла; ключи удлинены; (г) сценарии
  (settings/norms/layers) и snapshot-харнес постуют в API напрямую — для них
  `CSRF_ENABLED=0` (как в pytest), смоук интерфейса оставлен с включённой защитой.
- `app/security.py`: `new_csrf_token()` подключён в middleware (был мёртвым кодом).
