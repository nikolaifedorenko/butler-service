# Шахматка (stays), часть 1: дерево фонда, версии фонда с даты, флаги, месячный вид — дизайн

**Статус:** черновик на ревью владельца, 26.10.2026, редакция 2 (27.10.2026: постоянен только
id, фильтры и сортировка, вкладка «Брони», выгрузка и загрузка фонда). Согласован по разделам в обсуждении
(brainstorming). Дополняет и частично заменяет дизайн модуля
`2026-10-23-stays-chessboard-design.md` (§3.1 «Фонд», §6 «Экраны» — период видов).

Доработка модуля разбита на четыре части, у каждой своя спека, план и PR:

1. **эта спека** — дерево групп фонда, версии фонда с даты, флаги объектов, месячный вид,
   фильтры и сортировка, вкладка «Брони», выгрузка и загрузка фонда Excel-файлом;
2. OOO по половинкам суток и блоки по категориям с количеством по дням;
3. сопровождение по правилам (категория, группа, VIP-код брони, VIP/VVIP-гость);
4. батлер: «свои гости» без окна, отдельные права на профиль и бронь, «Мой месяц».

Части 2–4 опираются на модель фонда из части 1 и здесь не проектируются.

## 1. Зачем

* **Фонд меняется с даты, и меняться может что угодно.** После реновации коннект 12134
  становится двумя DLX 1213 и 1214; вилла меняет категорию; номер меняет обозначение;
  после реконструкции вилла становится удобной для колясок. Сейчас фонд в модуле один на
  все даты: правка категории переписывает и прошлое, а будущие изменения ввести нельзя.
* **Корпуса мало.** Нужна многоуровневая группировка: «Винные виллы → Семейная → Первая
  линия», «Корпус → Блок B → Вид на море». Она нужна для разделов шахматки, фильтров,
  сводной загрузки, а в частях 2–3 — для правил сопровождения и предпочтений при
  распределении.
* **Свойства объектов** («вид на море», «рядом с рестораном», «удобно для колясок») — да
  или нет у каждого объекта, тоже с даты.
* **Шахматки и загрузка смотрятся по календарному месяцу**, как Табель, а не на 7/14 дней.

**Fidelio** оперирует только категориями: бронь ставится на категорию, объект назначается
в последний момент. Категория остаётся тем, на что ставятся брони; дерево и флаги — рабочий
слой отеля поверх неё.

## 2. Решения владельца (зафиксировано в обсуждении)

* Брони (и в части 2 — строки блоков) ставятся **только на категорию**.
* **Одно дерево групп**; объект лежит ровно в одном узле. Остальные признаки — флаги.
* Флаг объекта — **да/нет**; привязка флага к объекту меняется с даты.
* **Подход А:** версии фонда целиком, каждая действует с даты до начала следующей.
* **Постоянен только внутренний id.** Версионируется всё остальное: у объекта —
  обозначение (номер), категория, группа, флаги, присутствие в фонде; у категории —
  в том числе **код Fidelio** (DTG → DKG); само дерево.
* В шахматке и списках — фильтры по дереву, категориям, флагам и т. д. с сортировкой;
  отдельная вкладка **«Брони»** — список бронирований с фильтрами.
* Реальный фонд вносится **выгрузкой-загрузкой Excel-файла с колонкой ID**; первоначальная
  загрузка полностью заменяет тестовые данные шахматки.
* Объединение/деление объектов — новой версией фонда («вывести один, завести два»). Слоя
  физических помещений в этой части нет: объект — неделимая единица.
* Поле «корпус» у объекта заменяется деревом. Приложение не в проде — перенос данных
  корпуса не нужен.
* Шахматки и загрузка — календарный месяц, ◀ ▶ и «Сегодня», как в Табеле.

## 3. Модель данных

### 3.1 Что постоянно, а что в версии

**Постоянен только внутренний `id`** категории, объекта и узла дерева. Он отвечает на один
вопрос: «та же это сущность или новая». Брони, назначения, OOO/блоки, пожелания гостей
ссылаются на id, поэтому смена версии их не ломает.

Тот же ли это id, решает пользователь выбором действия (§4.2):
* **«Изменить»** — тот же id, история непрерывна: 4003 → 4103 (смена номера), вилла
  VEG → FWV (смена категории), категория DTG → DKG (переименование);
* **«Вывести» + «Новая» / «Разделить» / «Объединить»** — новые id и связь «из чего
  получилось» (12134 → 1213 + 1214).

От этого выбора зависит, как сводятся отчёты за период и за чем остаются пожелания гостей.

Не версионируются: справочник флагов (подпись; версионируется привязка флага к объекту);
брони, гости, назначения, OOO и блоки — у них свои даты и журнал «было → стало».

**В версии** — всё, что может меняться с даты:

| Сущность | Свойства в версии |
|---|---|
| Категория | **код Fidelio**, название, вид (вилла / имение / апартаменты / номер), вес нагрузки, сопровождение, порядок |
| Узел дерева | название, родитель, порядок |
| Объект | обозначение («4003»), категория, узел дерева, этаж, флаги |

**Отсутствие в снимке версии = нет в фонде** на эти даты. Признак «активен / выведен» не
нужен: выведенного объекта (категории, узла) в снимке просто нет.

**Смена категории Fidelio — два разных случая:**
1. **Переименование.** Те же номера, другая кровать, Fidelio с даты называет категорию DKG
   вместо DTG и переводит брони. У нас это **та же категория** (тот же id): с даты меняются
   код и название. Брони показывают DTG на прошлые даты и DKG с даты; распределение не
   меняется, переводить ничего не нужно.
2. **Новая категория.** Часть номеров переделали (10 DTG стали DKG), часть осталась. В
   черновике заводится новая категория DKG, у 10 объектов категория меняется с даты; DTG
   живёт с оставшимися. Брони DTG после даты остаются DTG; если им не хватает объектов,
   предпросмотр это покажет и предложит **массовый перевод броней на категорию** (§4.3).

Выведенный код категории, как и номер объекта, можно использовать снова позже — id отличит
новую категорию от старой.

### 3.2 Таблицы

```text
stays_categories          id                                      — постоянная часть
stays_units               id                                      — постоянная часть
stays_fund_groups         id                                      — постоянная часть
stays_unit_flags          id, title UNIQUE, color, sort_order, archived
                          — справочник флагов, НЕ версионируется

stays_fund_versions       id, valid_from DATE UNIQUE, status (draft|published),
                          base_version_id NULL, author_id, note, created_at, published_at

stays_category_states     PK (version_id, category_id)
                          code, title, kind, weight, escorted, sort_order
                          UNIQUE (version_id, code)

stays_group_states        PK (version_id, group_id)
                          parent_id NULL → stays_fund_groups, title, sort_order
                          FK (version_id, parent_id) → stays_group_states

stays_unit_states         PK (version_id, unit_id)
                          label, category_id, group_id NULL, floor
                          UNIQUE (version_id, label)
                          FK (version_id, category_id) → stays_category_states
                          FK (version_id, group_id)    → stays_group_states

stays_unit_state_flags    PK (version_id, unit_id, flag_id)
                          FK (version_id, unit_id) → stays_unit_states ON DELETE CASCADE
                          FK flag_id → stays_unit_flags ON DELETE RESTRICT
                          INDEX (version_id, flag_id)

stays_unit_lineage        PK (unit_id, predecessor_id), version_id
                          — «из чего получился объект» (деление, объединение)
```

* Составные внешние ключи держат снимок версии самосогласованным: объект не может ссылаться
  на категорию или узел, которых нет в той же версии; родитель узла — в той же версии.
* Ссылки на категорию из броней (`Reservation.category_id`, `Move.category_id`) и на объект
  (`Assignment.unit_id`, `Hold.unit_id`) — на постоянные таблицы, как сейчас.
* `UNIQUE (version_id, label)` и `UNIQUE (version_id, code)` запрещают два одинаковых
  обозначения объектов и кода категорий в одном фонде; выведенное обозначение можно
  использовать снова в поздней версии — id (и `stays_unit_lineage`) отличают новый 12134
  от старого.
* Флаг: строка в `stays_unit_state_flags` — «да», нет строки — «нет». Справочник флагов не
  версионируется: переименование флага видно во всей истории (это подпись, а не свойство
  объекта). Использованный флаг не удаляется, а уходит в архив: пропадает из выбора,
  у объектов остаётся.
* Объём: полный снимок ≈ 440 объектов + ~1000 флагов на версию — ничтожно; копия проще
  хранения разницы и даёт «фонд на дату» одним запросом.

Из `stays_units` уходят `label`, `category_id`, `building`, `floor`, `active`, `sort_order`;
из `stays_categories` — всё, кроме `id`.

### 3.3 Фонд на дату

**Фонд на дату D** — опубликованная версия с наибольшей `valid_from ≤ D`. Ровно одна версия
действует в любой день: миграция заводит исходную версию с `valid_from = 2000-01-01`.

**Граница в половинках суток.** Версия с `valid_from = D` действует с **вечера D** (PM):
ночь с D на D+1 и далее. Утро D (выезд после ночи D−1) ещё принадлежит прошлой версии.
Так «фонд на дату» совпадает с ночёвками — единицей, по которой считаются покрытие,
нагрузка и «Мои гости».

Приложение читает фонд одним модулем `application/fund_versions.py`:

* `fund_for(db, first, last) -> FundTimeline` — версии, пересекающие диапазон (обычно 1–2),
  загруженные пакетно: ≤ 6 запросов независимо от числа версий в диапазоне;
* `FundTimeline.on(day) -> FundSnapshot` — снимок на день (бинарный поиск по границам);
* `FundSnapshot` — категории, узлы (с путём от корня), объекты, флаги объекта.

Остальной код модуля (`context`, `allocation`, `views`, `boards`, `export`, `coverage`) больше
не читает `Category`/`Unit` напрямую — только через `FundTimeline`. Это проверяется тестом
архитектуры (прямые `select(Unit)` / `select(Category)` вне `fund_versions` и `fund`).

## 4. Черновик и публикация

### 4.1 Правила

* Любая правка фонда идёт через **черновик «с даты D»**. Черновик открывается копией
  версии, действующей на D (`base_version_id`).
* **D ≥ сегодня.** Прошлое не меняется. Если черновик пролежал и D наступила — опубликовать
  можно только сдвинув дату на сегодня или позже.
* **Черновик один на весь фонд.** Второй менеджер видит существующий черновик и работает в
  нём или ждёт. Защищает от двух параллельных правок фонда.
* **Удалить** можно черновик и опубликованную версию, чья `valid_from` ещё не наступила.
  Действующую и прошедшие — нельзя. Исходную версию — нельзя.
* Все записи — под модульным замком `lock_module` (как сейчас для фонда, влияющего на
  распределение) и с проверкой версии черновика (оптимистическая защита, 409 при
  одновременной правке одного черновика).

### 4.2 Действия в черновике

| Действие | Что делает в снимке черновика |
|---|---|
| Изменить объект | категория, обозначение («сменить номер»), узел, этаж, флаги |
| Новый объект | добавляет объект в снимок |
| Вывести объект | убирает объект из снимка |
| **Разделить** | выводит объект, заводит N новых (обозначения любые, по умолчанию узел и флаги исходного), пишет `lineage` новые ← старый |
| **Объединить** | выводит выбранные объекты, заводит один новый, пишет `lineage` новый ← выбранные; если у выбранных разные узел/категория — спрашивает |
| Категории | добавить / изменить (в т. ч. код — переименование) / вывести (нельзя, пока в снимке есть её объекты) |
| Дерево | добавить узел, переименовать, перенести (смена родителя, без циклов), порядок, вывести (нельзя, пока в узле есть объекты или подузлы) |
| Флаги объектов | таблица «объекты × флаги» с галочками, массовая отметка по узлу |

Справочник флагов (название, цвет, порядок, архив) правится вне черновика — сразу.

### 4.3 Предпросмотр

Тот же механизм, что у броней (`run_operation`: снимок «до» → операция → снимок «после» →
diff → откат): публикация выполняется в транзакции, затем откатывается. Показывает:

* что поменялось в фонде (объекты, категории, узлы, флаги — «было → стало»);
* брони, которые **сменят объект** с даты D, и которые **останутся без объекта**;
* закреплённые (📌) брони, чьё закрепление стало неверным;
* брони категорий, которых нет в фонде с D (например, CONN после деления коннектов);
* новые предупреждения.

**Массовый перевод броней на категорию.** В предпросмотре для броней, оставшихся без объекта
или в выведенной категории, — действие «перевести брони X с заездом с D → категория Y» с
выбором броней галочками. Перевод применяется вместе с публикацией (та же транзакция и тот же
предпросмотр), в журнал каждой брони и в аудит пишется «было → стало». Для брони, уже
живущей на дату D, переводится сегмент с D (переезд по категории), а не вся бронь.

### 4.4 Публикация и поздние версии

Публикация: черновик → `published`, запускается `run_allocation`, в аудит пишется разница
«было → стало» (`fund_version:{id}`).

**Если после D уже есть опубликованные версии** (черновик с 01.11, версия с 01.12):
предпросмотр и диалог публикации спрашивают «Применить эти изменения и к версиям с 01.12?»,
по умолчанию — да. Правило переноса для каждой поздней версии V, поле за полем:

* значение поля в V **равно значению в базе черновика** (V это поле не меняла) →
  в V записывается значение из черновика;
* V поле меняла сама → поле в V не трогается, в предпросмотре строка «в версии с 01.12
  оставлено её значение»;
* добавленный в черновике объект/узел/категория добавляется в V, если там нет конфликта
  (занятое обозначение → не переносится, строка в предпросмотре);
* выведенный в черновике элемент выводится из V, если в V он не менялся.

Перенос входит в ту же транзакцию и тот же предпросмотр.

## 5. Автораспределение на границах версий

Сейчас `allocation.compute` строит один список объектов `UnitRef` на всё окно. Теперь доступность
объекта зависит от дня:

* **Вход распределителя.** Вместо `UnitRef(id, category_id, building, …)` — интервалы
  `UnitSpan(unit_id, category_id, group_path, label, start_pos, end_pos)`: объект с этой
  категорией и узлом на отрезке половинок суток между границами версий. Объект без смен
  на всём окне — один интервал.
* **Подходит ли объект сегменту:** есть интервал объекта нужной категории, покрывающий
  сегмент целиком.
* **Сегмент, пересекающий границу версии,** режется на ней на части. У частей правило
  непрерывности обратное переезду: **предпочитается тот же объект** (у переезда — другой).
  Поэтому если объект на границе не изменился, бронь визуально остаётся в нём.
* **Закрепления.** Закрепление сегмента переходит на его части. Если с D закреплённый
  объект не подходит (сменил категорию, выведен) — предупреждение `pin_invalid` для частей
  после D, закрепление до D сохраняется. Решает менеджер.
* **Категории нет в фонде с D** — предупреждение «категории CONN нет в фонде с 01.12» у
  каждой затронутой брони; сегмент остаётся «без объекта».
* **Прошлое не перераспределяется:** сегменты (и части), закончившиеся до сегодня, —
  заморожены и с объектом, и **без** объекта. Это закрывает находку L1 аудита модуля
  (ретро-размещение прошлого сегмента).
* **«Тот же корпус» при переезде** (сейчас сравнение `building`) → «тот же узел дерева,
  иначе ближайший общий предок». То же в подборе кандидатов-батлеров
  (`rank_candidates`: «тот же объект → тот же узел → меньше нагрузка»).
* Индексы сегментов в `stays_assignments` (`reservation_id, seg_index`): границы версий
  добавляют части, поэтому публикация версии пересчитывает назначения через
  `run_allocation`, а закрепления переносятся на части по пересечению половинок суток.

**Нагрузка и сопровождение** на каждый день берут вес и признак сопровождения категории
из версии этого дня.

Чистые функции домена (`domain/allocate.py`, `domain/candidates.py`) остаются чистыми: им
передаются готовые интервалы и пути узлов.

## 6. Месячный вид

* **Месяц общий с Табелем и Графиком** (`state.year / state.month`): открыл октябрь в
  Табеле — шахматка тоже на октябре, и наоборот.
* **Шапка видов** «Шахматка объектов», «Шахматка батлеров», «Загрузка»: ◀ месяц ▶ и
  «Сегодня» (переключает на текущий месяц, докручивает к колонке дня, подсвечивает — как в
  Табеле). Выпадающие «7 / 14 / 31 дн.» убираются. «Табло дня» — на одну дату, как сейчас.
* **API не меняется:** эндпоинты принимают `first / last`, фронт передаёт границы месяца;
  лимит 62 дня остаётся защитой. Фильтры — §7 (фильтр `building` уходит).
* **Строки шахматки объектов по умолчанию группируются по дереву:** разделы сворачиваются;
  внутри узла объекты — по порядку категории, затем натурально по обозначению (своего
  порядка у объекта нет; другие сортировки — §7). Категория видна в строке объекта,
  флаги — значками. По умолчанию развёрнуты виллы, основной корпус свёрнут; строки
  свёрнутого раздела в DOM не рисуются.
* **Граница версии внутри месяца:** объект, которого нет в фонде часть месяца, на эти дни
  закрашен серым «нет в фонде»; смена номера или категории видна подписью у строки
  («4003 → 4103 с 15.11»). Строка шахматки — постоянный объект.
* **Сводная загрузка:** строки — узлы дерева с итогами по ветке, внутри узла разворачиваются
  категории. «Всего объектов» на каждый день — по фонду этого дня.
* **Производительность:** бюджет запросов шахматки на 440 объектов остаётся ≤ 30 на месяц
  (31 день). Объём HTML: пустые половинки — фоном строки, а не клетками, если замер на
  440 × 62 покажет торможение прокрутки.
* Гонки быстрой смены месяца — `loadGenerationFor` (как в PR #95/#99).

## 7. Фильтры и сортировка

Одна панель фильтров на все виды: шахматка объектов, сводная загрузка, табло дня, вкладка
«Брони» (§8). Состав фильтров вида — то, что к нему применимо.

| Измерение | Выбор | Пример |
|---|---|---|
| Где (дерево фонда) | галочки по узлам, несколько; узел включает всю ветку | «Корпус» + «Винные виллы»; только «Блок B / Вид на море» |
| Категории | несколько | VEG, FWV |
| Флаги объектов | несколько | «Вид на море» и «Удобно для колясок» |
| Вид объекта | несколько | вилла, номер |
| Сопровождение, VIP/VVIP, батлер, статус брони | как сейчас | |
| Поиск | фамилия, № брони, объект, телефон, настраиваемые поля | |

**Сочетание:** внутри измерения — «или» («Корпус» или «Виллы» → оба), между измерениями —
«и» («Виллы» и флаг «Вид на море» → только виллы с видом на море). **Флаги — всегда «и»:**
отмечено два флага — у объекта должны быть оба. «Вид на море в любом блоке» одной галочкой —
это флаг, а не узел.

Узлы, категории и флаги на каждый день проверяются **по версии фонда этого дня**: объект,
получивший флаг с 15.11, попадает в фильтр с 15.11.

**Сохранённые наборы:** собранный фильтр сохраняется под именем («Виллы с видом на море») и
выбирается из списка. Хранятся у пользователя в браузере (`localStorage`, с try/catch —
без хранилища просто нет сохранённых наборов).

**API:** `group_ids` (несколько), `category_ids`, `flag_ids`, `kinds` — списками; прежние
`building` и одиночный `category_id` уходят. Объём запросов от фильтров не растёт: фильтрация —
по уже загруженному `FundTimeline` и броням диапазона.

**Сортировка строк шахматки объектов:** по дереву (по умолчанию), по номеру ↑↓, по
категории ↑↓, по этажу ↑↓, **по загрузке за месяц** ↑↓ (занятые ночи / ночи в фонде — сначала
самые занятые или самые свободные). Переключатель **«группировать по дереву»**: сортировка
внутри разделов или по плоскому списку. Номер и категория для сортировки — по версии на
первый день месяца.

## 8. Вкладка «Брони»

Новая вкладка модуля рядом с «Объекты / Батлеры / Табло дня / Загрузка» — **список
бронирований** с фильтрами и сортировкой.

* **Период:** по умолчанию текущий месяц (общий с Табелем), ◀ ▶ «Сегодня»; можно задать
  произвольный диапазон дат. Режим попадания в период: **проживание пересекает период**
  (по умолчанию) / **заезд** в периоде / **выезд** в периоде / **создана** в периоде.
* **Фильтры** — §7 (дерево, категории, флаги — по объекту брони на её даты), плюс статус
  брони, метка, «без объекта», «есть предупреждения».
* **Колонки:** № брони, главный гость (★ VIP/VVIP), заезд, выезд, ночей, категория, объект
  (при переезде — «4003 → 4105»), статус, метка, батлер(ы), РЗ/ПВ, дата создания.
* **Сортировка:** клик по заголовку колонки, повторный — обратное направление; по умолчанию —
  заезд ↑, затем № брони.
* Клик по строке — карточка брони (как с шахматки).
* **Объём:** сортировка и фильтры на сервере, выдача по 200 строк с «Показать ещё»;
  бюджет запросов не зависит от числа строк.
* **Права и персональные данные:** вкладка — `stays.view` (уровень «с фамилиями»: без
  телефонов и дат рождения). Уровню `stays.occupancy` вкладка не показывается: список броней
  без фамилий бесполезен и сам по себе оракул. Поиск по телефону — только при `stays.guests`.
* **Выгрузить список в Excel** — текущий фильтр и сортировка, лист «Бронирования»; право
  `stays.export`, пишется в аудит (как существующая выгрузка).

## 9. Выгрузка и загрузка фонда (Excel)

Фонд целиком вносится и массово меняется **Excel-файлом**, который приложение само выгружает
и принимает обратно. Это и первоначальная загрузка реального фонда вместо демо, и массовые
изменения позже (реновация).

### 9.1 Файл

Листы и колонки (выгрузка текущего фонда на выбранную дату — готовый заполненный пример):

| Лист | Колонки |
|---|---|
| Категории | ID, код, название, вид, вес, сопровождение (да/нет), порядок |
| Дерево | ID, путь узла («Корпус / Блок B / Вид на море»), порядок |
| Флаги | ID, название, цвет |
| Объекты | ID, номер, категория (код), узел (путь), этаж, «Из чего» (ID через запятую), по колонке на каждый флаг (да/нет) |

* **ID** — постоянный id сущности (§3.1). Колонка серая и защищена от правки; в заголовке —
  «не менять; пусто — новая запись». В «Настройках → Фонд» id видны мелким серым «#57».
* **Ссылки между листами — по коду категории и пути узла**, а не по ID: у новых строк ID ещё
  нет. Внутри версии код и путь уникальны, ссылка однозначна. ID отвечает «кто это», код и
  путь — «куда положить».
* У узла дерева путь включает его название; родитель — путь без последнего звена.
* Флаг объекта — колонка листа «Объекты» с названием флага; новая колонка создаёт флаг в
  справочнике.

### 9.2 Правила для строки

| В строке | Значит |
|---|---|
| ID заполнен | та же сущность; меняется всё, что изменено в строке (номер, категория, узел, флаги, код категории — переименование) |
| ID пуст | новая сущность, id присвоит система |
| ID есть в фонде, строки с ним в файле нет | сущность выводится с даты; в предпросмотре — отдельным заметным списком «будут выведены» |
| ID неизвестен или повторяется | ошибка |
| «Из чего» у новой строки | деление / объединение: `lineage` новый ← перечисленные (их строки обычно удалены — выводятся) |

Пример деления коннекта: строка `57 | 12134 | CONN` удалена, добавлены `— | 1213 | DLX | из 57`
и `— | 1214 | DLX | из 57`.

**Проверка файла** — все ошибки списком с листом и строкой (неизвестная категория, повтор
номера или кода, путь к несуществующему родителю, цикл, «да/нет» с опечаткой, неизвестный
ID). Пока есть хоть одна ошибка — ничего не применяется.

### 9.3 Режимы загрузки

**«Загрузить как черновик с даты»** (`stays.setup`). Файл превращается в черновик версии
фонда с датой D — со всем, что в §4: предпросмотр (что изменится, какие брони сменят объект,
массовый перевод броней), перенос в поздние версии, публикация. Если черновик уже есть —
отказ с предложением открыть или удалить его (черновик один). Кнопками интерфейса и файлом
делается одно и то же, результат и предпросмотр одинаковы.

**«Начальная загрузка (заменить всё)»** — для перехода с тестовых данных на реальные.
* Доступна **только администратору** (новое право `stays.reset`, ADMIN_ONLY) и **только пока
  в настройках модуля выключен переключатель «Шахматка в эксплуатации»**. Включённый
  переключатель убирает кнопку; выключить его обратно может только администратор, с записью
  в аудит.
* ID в файле игнорируются (после очистки старые id ничего не значат) — предпросмотр
  предупреждает, если они заполнены.
* **Предпросмотр:** «будет удалено: N объектов, N броней, N гостей, назначения батлеров,
  OOO и блоки, версии фонда; будет загружено: N категорий, N узлов, N флагов, N объектов».
* **Подтверждение** — ввести слово «ЗАМЕНИТЬ».
* **Перед заменой** — полная выгрузка текущих данных модуля в Excel: сохраняется на сервере в
  каталог резервных копий и сразу предлагается к скачиванию.
* **Одна транзакция:** удаляются все данные шахматки (фонд и версии, брони с переездами,
  составом, логистикой и сопровождающими, гости и связи, покрытие батлеров, OOO и блоки), из
  файла создаётся **исходная версия** фонда (`valid_from = 2000-01-01`). Настройки модуля —
  метки броней, настраиваемые поля, список «сопровождают гостей», надбавки и лимит — **не
  удаляются**: это конфигурация, её правят на месте. Сотрудники, График, Табель и журнал аудита не трогаются;
  замена пишется в аудит (кто, когда, сколько удалено и загружено, имя файла копии).
* Брони и гости в начальную загрузку не входят — после замены шахматка пустая. Импорт броней
  из Fidelio — отдельная задача.

Демо-данные в проде не появляются вообще (сид — только при `DEMO_SEED=1`); «заменить всё»
нужно для тестовой установки и пробного периода.

## 10. Экран «Настройки → Фонд»

Макет согласован в обсуждении 26.10.2026.

* **Шапка:** «Фонд на дату» — переключатель «действующая версия / черновик / любая версия
  из истории»; кнопки «Флаги объектов» (справочник), «Изменить с даты…», «Выгрузить фонд»,
  «Загрузить фонд» (§9).
* **Плашка черновика** — всегда видна, пока черновик есть: дата, число изменений и их список,
  кнопки «Предпросмотр», «Опубликовать», «Удалить».
* **Слева дерево групп:** клик по узлу показывает объекты узла и всех его подузлов; «+» —
  новый узел; перетаскивание — порядок узлов и смена родителя (в черновике).
* **Справа объекты узла:** обозначение, категория, флаги-значки, действия «Изменить»,
  «Разделить», «Сменить номер», галочки для «Объединить» и массовой смены узла. Изменения
  черновика подсвечены («с 01.12», «изменён», «новый · из 12134», «выведен с 01.12»).
* **Вкладки справа:** «Объекты», «Флаги объектов» (матрица с галочками), «Категории».
* **История версий:** дата «с», статус (черновик / будущая / действует / архив), автор,
  примечание; удаление будущих.
* Вне черновика экран только показывает фонд — любое изменение предлагает выбрать дату.

## 11. Права и аудит

* Черновик, публикация, удаление версий, справочник флагов — `stays.setup` (менеджер и
  выше), как категории и объекты сейчас.
* Чтение фонда (дерево, флаги, версии) — тем же, кто видит шахматку (`stays.view`,
  `stays.occupancy`): в фонде нет персональных данных.
* Выгрузка фонда и «Загрузить как черновик» — `stays.setup`; «Начальная загрузка (заменить
  всё)» и переключатель «Шахматка в эксплуатации» — `stays.reset` (только администратор, §9.3).
* Вкладка «Брони» — `stays.view`; её выгрузка в Excel — `stays.export` (§8).
* Аудит: публикация (`fund_version:{id}`, полная разница, перенос в поздние версии, массовый
  перевод броней), удаление версии, правки справочника флагов, загрузка файла фонда,
  начальная загрузка, переключение «в эксплуатации».

## 12. Миграция

Ревизия `0010_stays_fund_versions`:

* создаёт таблицы §3.2, заводит исходную версию `valid_from = 2000-01-01` из текущих
  категорий и объектов (активных); корпуса не переносятся — объекты попадают в «Без группы»;
* убирает перенесённые колонки из `stays_units` и `stays_categories`;
* downgrade возвращает колонки из исходной версии; при нескольких версиях — guard, как у
  0007/0002 (откат с потерей истории фонда только явно).

Демо-сид заполняет дерево (виллы по видам, корпус → блоки → виды), флаги и одну будущую
версию с делением коннекта — чтобы на демо были видны граница версии и «нет в фонде».

## 13. Тесты

* **Модель:** фонд на дату (включая границу PM дня D), исходная версия, `UNIQUE` обозначения
  и кода категории в версии, переименование категории (тот же id, брони показывают код по
  дате), составные FK (объект на категорию из другой версии — ошибка), флаг в архив
  вместо удаления.
* **Черновик:** D в прошлом — 422; второй черновик — 409; удаление действующей — 409;
  одновременная правка черновика — 409 по версии.
* **Действия:** разделить (lineage, обозначения любые), объединить (разные узлы → вопрос),
  сменить номер (строка шахматки та же), сменить категорию, флаг с даты.
* **Перенос в поздние версии:** поле не менялось → перенесено; менялось → оставлено;
  конфликт обозначения → не перенесён и показан.
* **Распределение:** сегмент через границу режется, при неизменном объекте остаётся в нём;
  объект сменил категорию → бронь переезжает с D; закрепление после D → `pin_invalid`;
  категории нет в фонде → предупреждение; прошлый сегмент без объекта не размещается (L1).
* **Предпросмотр ≡ публикация** и «после предпросмотра в БД ничего» — как у броней;
  массовый перевод броней на категорию (вся бронь и сегмент с D).
* **Фильтры и сортировка:** «или» внутри измерения, «и» между ними, флаги через «и»; фильтр
  по флагу/узлу с даты версии; сортировки строк шахматки, «группировать по дереву».
* **«Брони»:** режимы попадания в период, сортировка по колонкам, пагинация, бюджет
  запросов; уровень occupancy — 403; поиск по телефону без `stays.guests` — не ищет.
* **Файл фонда:** выгрузка → загрузка без правок = пустой черновик; ID пуст → новая; строка
  удалена → выводится; неизвестный/повторный ID, неизвестный код, путь без родителя, цикл —
  ошибки с листом и строкой, ничего не применено; «Из чего» → lineage; новая колонка флага →
  флаг в справочнике.
* **Начальная загрузка:** только `stays.reset`; при «в эксплуатации» — 403; без слова
  «ЗАМЕНИТЬ» — 422; копия создана до удаления; удалены только данные шахматки (сотрудники,
  График, Табель, аудит на месте); ошибка в файле — не удалено ничего.
* **Виды:** месяц с границей версии (серые дни, подпись смены номера), группировка по
  дереву, фильтр по узлу и флагам, загрузка по узлам; бюджет запросов на месяц ≤ 30.
* **Архитектура:** `Unit`/`Category` читаются только через `fund_versions`/`fund`.
* **jsdom-сценарии:** ◀ ▶ «Сегодня» и общий месяц с Табелем; экран «Фонд»: черновик,
  разделение, предпросмотр, публикация; панель фильтров и сохранённые наборы; вкладка
  «Брони»: сортировка по колонке, «Показать ещё».

## 14. Вне этой части

* OOO по половинкам и блоки по категориям — часть 2 (здесь `Hold` не меняется, кроме
  того, что OOO на дни, когда объекта нет в фонде, даёт предупреждение).
* Правила сопровождения и VIP-коды — часть 3 (`escorted` категории пока работает как сейчас,
  но уже из версии дня).
* «Мои гости», права батлера — часть 4.
* Пожелания гостей по узлам и флагам — с частью 2 (распределение).
* Физические помещения (одновременная продажа люкса и его частей) — не делаем; объединение
  и деление — версиями фонда.
