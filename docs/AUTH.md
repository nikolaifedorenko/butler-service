# Аутентификация и безопасность Батлер Сервис

## 1. Общая схема
Батлер Сервис использует **классическую серверную сессию в подписанной cookie** (без внешних
зависимостей вроде JWT-библиотек или OAuth):

```
логин+пароль → PBKDF2-проверка → токен сессии (HMAC-подпись) → HttpOnly-cookie
                ↓                              ↓
           таблица users              каждый запрос API: подпись + срок → Principal(роль, сотрудник)
```

* Учётная запись (`users`) привязана к сотруднику (`employees`) через `employee_id`;
  у администратора привязки может не быть.
* Роли: `admin`, `manager`, `supervisor`, `employee`.
  - `admin` — полный доступ; сам в график не встаёт и не работает;
  - `manager` — права как у admin, но сам может стоять в графике и отмечаться;
  - `supervisor` — права как у manager (просмотр всех событий, графики, табель, добавление
    обычных пользователей), но **не может создавать/удалять/изменять supervisor, manager, admin**;
  - `employee` — только свои отметки, описания переработок и история своих действий.
  Группа «менеджеры» = {admin, manager, supervisor}.

## 2. Пароли
* Хранение: `pbkdf2$<итерации>$<salt-hex>$<digest-hex>` — PBKDF2-HMAC-SHA256,
  **120 000 итераций**, соль 16 байт (модуль `app/security.py`, только stdlib).
* Сравнение — `hmac.compare_digest` (защита от timing-атак).
* Пароль никогда не логируется; смена пароля — «Сотрудники» → «Изменить» (поле «Новый пароль»)
  или `PUT /api/employees/{id}`; действие пишется в аудит.
* Демо-пароль `demo1234` — только для демо-базы; в бою меняйте сразу (инструкция в INSTALL.md).
* Политики сложности нет (осознанно: внутренний инструмент); при желании добавляется поверх.

## 3. Сессии
* Токен: `base64url(JSON{uid, emp_id, imp, exp}) + "." + HMAC-SHA256(secret, payload)[:32]`.
  Подпись идёт серверным `SECRET_KEY` из `.env` — подделать токен без ключа нельзя.
* Cookie: `tt_session`, флаги **HttpOnly** (недоступна JS/XSS), **SameSite=Lax**
  (не отправляется на кросс-сайт запросах → базовая защита от CSRF), `Path=/`,
  срок = `SESSION_TTL_HOURS` (по умолчанию 14 суток).
* `COOKIE_SECURE=1` добавляет флаг **Secure** (cookie только по HTTPS) — включайте после
  настройки TLS (INSTALL.md §2.5).
* Токен **stateless**: сервер не хранит сессии, отзыв одной сессии не предусмотрен
  (отзыв = смена `SECRET_KEY` или `logout`). Для боевого режима при желании добавляется
  таблица-блок-лист — точка расширения описана в SPEC.md.
* Выход: `POST /api/auth/logout` — cookie удаляется.
* Истёкший/подделанный токен → API отвечает `401`, SPA показывает экран входа.

## 4. Авторизация (кто что может)
| Возможность | employee | senior | manager | admin |
|---|---|---|---|---|
| Свои отметки «Пришёл/Ушёл», своя история, описание переработок | ✓ | ✓ | ✓ | ✓ |
| График, ячейки, массовые заполнения, копирование | – | ✓ | ✓ | ✓ |
| Посещения (кто на смене, точные времена) | – | ✓ | ✓ | ✓ |
| Табель, пересчёт, выгрузки CSV/XLSX | – | ✓ | ✓ | ✓ |
| Сотрудники (создание/правка/деактивация) | – | ✓ | ✓ | ✓ |
| Отметка за другого сотрудника / задним числом | – | ✓ | ✓ | ✓ |
| Удаление ошибочной отметки | – | ✓ | ✓ | ✓ |
| Словарь смен (любые часы), правила расчёта, пересчёт всего месяца | – | – | – | ✓ |
| Подразделения (создание) | – | – | – | ✓ |
| Журнал аудита | – | ✓ | ✓ | ✓ |

Реализация: FastAPI-зависимости `current_principal`, `require_manager`, `require_admin`
(`app/auth.py`); каждый защищённый эндпоинт объявляет требуемый уровень.
Данные сотрудника дополнительно фильтруются: сотрудник видит в `/api/punches` только свои строки.

## 5. Демо-режим «войти как сотрудник» (impersonation)
* Менеджер: «Сотрудники» → «Открыть как сотрудник» → `POST /api/auth/impersonate`.
* В токен пишется флаг `imp=1` и `emp_id` цели; в шапке — жёлтый индикатор и кнопка «Вернуться».
* Все действия в этом режиме пишутся в аудит с пометкой «(как сотрудник)».
* Отключается глобально: `ALLOW_IMPERSONATION=0` в `.env`.

## 6. Журнал аудита
Таблица `audit_log`: кто, когда, что (`login`, `logout`, `impersonate`, `schedule_set`,
`schedule_fill_pattern`, `punch_in/out`, `punch_in_backfill`, `punch_delete`, `punch_note`,
`settings_update`, `employee_*`, `shift_type_*`, `recalc_all`…) + payload в JSON.
Смотреть: «Настройки» → «Журнал изменений» или `GET /api/timesheet/audit`.

## 7. Что учтено и что осознанно оставлено простым
Учтено:
*_pbkdf2_ с солью и итерациями, постоянное время сравнения;
* HttpOnly + SameSite=Lax (+ Secure по флагу); подпись токена HMAC; срок действия;
* ролевая модель на каждом эндпоинте; аудит критичных действий;
* отметки задним числом и удаления — только менеджером и только с аудитом.

Осознанно просто (внутренний инструмент, при выходе в «дикый» интернет усилить):
* **CSRF-токена нет** — защита SameSite=Lax; при необходимости добавить заголовок
  `X-Requested-With`/token на мутации (точка расширения в SPEC.md);
* **rate-limit нет** — ставить на nginx (`limit_req`) или fail2ban;
* **отзыв сессии** — только сменой SECRET_KEY;
* **блокировка после N неудачных входов** — нет (ставится на прокси);
* **2FA** — нет (при желании — TOTP поверх `users`).

## 8. Чек-лист перед боевым запуском
- [ ] `SECRET_KEY` = случайные 32+ байта (`openssl rand -hex 32`), хранится только в `.env`;
- [ ] HTTPS настроен, `COOKIE_SECURE=1`;
- [ ] демо-пароли заменены, демо-доступы на экране входа не мешают (их список статичен в JS —
      при желании уберите блок из `static/index.html`);
- [ ] `ALLOW_IMPERSONATION=0`, если режим «как сотрудник» не нужен;
- [ ] бэкапы БД и `.env` по расписанию;
- [ ] nginx: `limit_req`, ограничение тела запроса, скрытие `Server`-заголовков по политике;
- [ ] доступ к `/api/docs` закрыт снаружи (или оставлен только для VPN).
