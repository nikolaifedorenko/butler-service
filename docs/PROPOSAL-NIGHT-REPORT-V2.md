# Ночной отчёт v2 — зоны, объекты, ответственные службы и рассылка недостатков

Проектная записка к прототипу `docs/archive/prototypes/night-report-v2.html` (19.10.2026; реализован, прототип в архиве).
Описывает, как запрошенный сценарий укладывается в текущую архитектуру `butler-service`:
что меняется в данных, какие появляются сущности, как устроена доставка уведомлений.
Этап 1 реализован — см. `docs/CHANGES-2026-10-19-night-report-v2.md`.

**Решения владельца (19.10.2026), учтены в прототипе и в этой записке:**
1. чек-лист **общий на зону**, но с **индивидуальными правками объекта** (своя формулировка,
   своя служба, отключить пункт, добавить свой);
2. лимиты и срок хранения **видео задаются в настройках**, как у фото;
3. отправлять недостатки может **любой** пользователь обхода, отправленное **помечается**;
4. отправка **только вручную** (никакой автоотправки при закрытии объекта/смены);
5. личные уведомления сотрудникам **не нужны**; в теле сообщения указываются **ночные батлеры
   смены** (плейсхолдер `{duty}`); `{deadline}` — убран;
6. **«Не отмечено» включается** в консолидированный отчёт (отдельный блок «Не проверено»);
7. **Электрокары — отдельный шаг**, в зоны не переносим;
8. **список чатов получаем в настройках Telegram** (getUpdates), а **закрепляем найденный чат
   в карточке службы**;
9. почта — **через MS Exchange**: приложение позже включат в домен (релей без авторизации
   или SMTP AUTH, в перспективе Graph/EWS);
10. если недостаток **исправили после отправки — ничего не отправляем** (ни «исправлено»,
    ни отзыва сообщения);
11. размер видео — **50 МБ** (лимит Telegram Bot API);
12. общих чатов у нескольких служб не предполагаем; если так вышло — **просто отправляем всем**
    (каждая служба шлёт своё сообщение, без объединения и дедупликации);
13. **настройки Telegram и почты — ОБЩИЕ для приложения** («Настройки» → «Чаты и Почта»,
    `#/settings/notify`), а не внутри ночного отчёта: доставка понадобится и другим разделам
    (электрокары, заявления, закрытие периода, отметки).

## 1. Что меняется для пользователя

Сейчас раздел «Ночной отчёт» — это плоский список «областей» (Вилла VEG 4001, Спа, Офис…),
сгруппированный подписями категорий, и шаг «Проверка электрокаров». При десятках однотипных
объектов список становится длинным: прокрутка, поиск глазами, невозможно понять прогресс
по группе вилл целиком.

Предлагается трёхуровневая иерархия и контур уведомлений:

```
ЗОНА (Семейные виллы)                ← прогресс по всей группе, 12 объектов
  └─ ОБЪЕКТ (Вилла 4001)             ← статус, кто ведёт, перехват
       └─ ЧЕК-ЛИСТ (Витражи закрыты) ← ОК / Не ОК + комментарий + фото/видео
            └─ ОТВЕТСТВЕННАЯ СЛУЖБА  ← Техническая служба → чат и/или письмо
                 └─ НЕДОСТАТОК       ← попадает в консолидированный отчёт смены
```

Экраны прототипа:

| № | Экран | Что делает |
|---|---|---|
| 1 | **Зоны** | 6 карточек зон с прогрессом, счётчиком замечаний и «в работе»; кнопка «Недостатки: N» |
| 2 | **Объекты зоны** | 12 вилл: статус, кто ведёт, прогресс пунктов, «Взять в работу / Продолжить / Завершить» |
| 3 | **Чек-лист объекта** | пункты с ОК/Не ОК, комментарий, медиа (съёмка фото/видео или из галереи), бейдж ответственной службы |
| 4 | **Недостатки смены** | всё «Не ОК» за смену, сгруппировано по службам и каналам; «отправить всё» или выбрать вручную; предпросмотр текста; результат по каналам |
| 5 | **Журнал отправок** | кто, когда, кому, что ушло, статус, «повторить» |
| 6 | **Настройки → Зоны и объекты** | CRUD зон, объектов, мастер «серия» (Вилла 4001…4012) |
| 7 | **Настройки → Пункты чек-листа** | шаблон пунктов зоны + ответственная служба у каждого пункта; ниже — панель «Индивидуальные особенности объекта»: своя формулировка, своя служба, отключить пункт, добавить свой |
| 8 | **Настройки → Ответственные службы** | название, чекбоксы «чат» / «письмо», e-mail, список чатов Telegram |
| 9 | **Настройки → Интеграции** | токен Telegram-бота (маскирован) + «Проверить токен» (getMe), **общий список чатов** («Обновить список чатов» → getUpdates) с пометкой, за кем закреплён, SMTP, шаблон сообщения, лимиты и срок хранения фото/видео |

Механика обхода (взять объект в работу, перехват с подтверждением, закрытие с неотмеченными
пунктами, автозакрытие смены в 08:00, снимок справочников в отчёте, шаг «Проверка
электрокаров») сохраняется как есть — меняется навигация и добавляется контур ответственности.

## 2. Модель данных

### 2.1 Новые сущности

```python
class NightZone(Base):
    """Зона обхода: «Семейные виллы», «Офисы». Первый уровень навигации."""
    __tablename__ = "night_zones"
    id, name (unique), sort_order, active
    default_service_id  → responsibility_services.id   # служба по умолчанию для пунктов зоны
    created_at, updated_at

class ResponsibilityService(Base):
    """Ответственная служба: куда уходит недостаток и каким способом."""
    __tablename__ = "responsibility_services"
    id, name (unique), sort_order, active
    notify_chat:  bool          # чекбокс «Чат (Telegram)»
    notify_email: bool          # чекбокс «Письмо (e-mail)»
    email: str                  # основной ящик
    email_cc: str               # копия (через запятую)
    chats_json: str             # [{"id": "-1001234567890", "title": "Техслужба · Мрия"}]
    created_at, updated_at

class ChecklistItemOverride(Base):
    """Индивидуальные особенности объекта: шаблон зоны остаётся общим.

    item_id = NULL  → свой пункт только этого объекта;
    disabled = True → пункт шаблона у этого объекта не проверяется;
    text / service_id → своя формулировка / своя ответственная служба.
    """
    __tablename__ = "checklist_item_overrides"
    id, area_id → night_areas.id, item_id → checklist_items.id (nullable)
    text: str            # переопределение формулировки ('' = как в шаблоне)
    service_id → responsibility_services.id (nullable = как в шаблоне)
    disabled: bool, sort_order: int

class NotifyDispatch(Base):
    """ОБЩИЙ журнал отправок приложения (не редактируется, только добавляется).

    Один журнал на все разделы: domain + ref_id указывают, откуда отправка
    (night → night_reports.id, cars → car_history.id и т. д.).
    """
    __tablename__ = "notify_dispatches"
    id, domain: str                          # night | cars | schedule | …
    ref_id: int                              # id исходной записи раздела
    ts, actor_user_id, actor_name
    recipient_id, recipient_name             # снимок получателя (служба, руководитель…)
    channel: "telegram" | "email"
    target: str                              # chat_id или e-mail
    items_json: str                          # снимок отправленного
    message: str                             # текст/тема как ушли
    status: "sent" | "failed" | "pending"
    error: str, external_id: str             # telegram message_id / SMTP Message-ID
    attempts: int
```

### 2.2 Расширение существующих

| Таблица | Колонки | Зачем |
|---|---|---|
| `night_areas` (объекты) | `zone_id → night_zones.id` | объект принадлежит зоне (`category` остаётся на время миграции) |
| `checklist_items` (шаблон) | `zone_id → night_zones.id`, `service_id → responsibility_services.id`; `area_id` остаётся nullable, но для шаблонов больше не используется | шаблон пунктов задаётся **на зону**; индивидуальные правки объекта — в `checklist_item_overrides` (свой пункт, своя формулировка, своя служба, отключение) |
| `night_check_items` (ответы в отчёте) | `service_id`, `service_name`, `dispatch_id → night_dispatches.id`, `dispatched_at` | снимок ответственной службы (правка справочника не меняет историю) + отметка «уже отправлено» |
| `night_area_sections.snapshot_json` | `{"id", "text", "service_id", "service_name", "override_id"}` | при создании отчёта шаблон зоны прогоняется через правки объекта — в отчёт попадает **эффективный** чек-лист; дальнейшие правки справочников закрытую смену не меняют |
| `photos` | `media_type: "photo" \| "video"`, `duration_sec`, `mime` | видео наравне с фото; kind остаётся `night_item` |

### 2.3 Миграция (без потерь, идемпотентно, как принято в `app/migrations.py`)

1. `night_zones`: создать зону на каждое distinct-значение `night_areas.category`
   (пустая категория → зона «Без зоны»), проставить `night_areas.zone_id`.
2. Шаблон пунктов: для каждой зоны взять набор пунктов её объектов, привести к общему
   знаменателю (одинаковый `text` в пределах зоны → одна запись с `zone_id`),
   уникальные для одного объекта оставить как `area_id`-пункты этого объекта.
   `checklist_items.area_id`/`zone_id` — оба nullable, `item_id` в ответах остаётся валидным.
3. `responsibility_services`: посев «Батлер-сервис», «Хозяйственная служба»,
   «Техническая служба», «IT-департамент» (без каналов — настраивает владелец),
   у существующих пунктов `service_id = NULL` → в UI «не назначен».
4. `night_dispatches`, новые колонки — через `Base.metadata.create_all` + `additions` в `migrate_db()`.
5. Старые отчёты не трогаем: они уже хранят снимок (`snapshot_json`, `NightCheckItem.text`).

Проверки: `/api/selfcheck` (полнота схемы) + `tests/test_selfcheck.py::test_migraciya_idempotentna`.

## 4. Уведомления

### 4.0 Общий слой доставки (решение 13)

Telegram и почта — **инфраструктура приложения**, а не принадлежность ночного отчёта:
позже отправку подключат электрокары (замечания при возврате), График и Табель (заявления,
закрытие периода), отметки (опоздания). Поэтому:

```
app/notify/                     # общий слой: не знает про ночной отчёт
  transports/telegram.py        #   Bot API: sendMessage, sendMediaGroup, getMe, getUpdates
  transports/email.py           #   SMTP / MS Exchange (релей или SMTP AUTH), позже Graph/EWS
  templates.py                  #   рендер текста по шаблону раздела и плейсхолдерам
  dispatch.py                   #   троттлинг, ретраи, статусы, запись в общий журнал
  recipients.py                 #   порт «кто получает»: правило задаёт сам раздел
```

* **учётные данные и транспорт — общие**, настраиваются в «Настройки» → **«Чаты и Почта»**
  (`#/settings/notify`, группа «Служебное», право `settings.edit`): токен бота, каталог
  чатов (getUpdates), SMTP/Exchange, шаблоны по разделам, проверки «Проверить бота»,
  «Тестовое сообщение», «Тестовое письмо»; лимиты медиа — в правилах объекта
  (`photo_max_mb`, `video_max_mb`, сроки хранения);
* **у каждого раздела своё**: шаблон сообщения, правило выбора получателей и экран отправки
  (ночной отчёт — службы и их каналы; электрокары — ответственные за парк и т. д.);
* **журнал отправок общий**: `notify_dispatches` с колонками `domain` (`night`, `cars`, …) и
  `ref_id` — один экран журнала на приложение с фильтром по разделу;
* подключение нового раздела = «получатели + шаблон + экран отправки»; транспорт, ретраи,
  маскирование токенов и журнал переиспользуются.

### 4.1 Telegram (Bot API)

* `POST https://api.telegram.org/bot<TOKEN>/sendMessage` — текст недостатков (parse_mode=HTML);
* `sendMediaGroup` — до 10 фото/видео одним альбомом к сообщению;
* `sendPhoto` / `sendVideo` / `sendDocument` — если медиа больше 10 или смешанные типы;
* лимит загрузки через Bot API — **50 МБ на файл** (видео больше — только ссылкой или через
  локально поднятый Bot API server; в прототипе — предупреждение и отказ);
* троттлинг: ≤ 20 сообщений/мин на группу, ≤ 1 msg/s на чат — простая очередь
  (`asyncio.Semaphore` + задержка), при `429 retry_after` — повтор;
* **список чатов — общий каталог** в «Настройках → Интеграции» («Обновить список чатов»):
  бот добавляется в группу, кто-то пишет в неё сообщение → `getUpdates` отдаёт
  `message.chat.id/title`; там же видно, за какой службой закреплён чат;
* **закрепление чата за службой — в карточке службы** (выбор галочками из найденного списка);
  резервный ввод `chat_id` вручную спрятан под ссылкой «нет нужного чата?»;
* каталог хранится в `settings.telegram_chats_json` (`[{id,title}]`).

Зависимости: HTTP-клиент. Варианты: `httpx` (уже есть в lock-файле как зависимость
TestClient) или stdlib `urllib.request` в воркере (ноль новых зависимостей — ближе
к консерватизму проекта). Решение за владельцем.

### 4.2 E-mail (SMTP → MS Exchange)

* stdlib `smtplib` + `email.message.EmailMessage` — без новых зависимостей;
* **адресат — MS Exchange**: приложение включат в домен, поэтому основной режим — отправка через
  внутренний релей (коннектор Exchange: host + 587 STARTTLS, авторизация не нужна,
  отправитель разрешён на коннекторе); резервный режим — SMTP AUTH (логин/пароль);
* в настройках — переключатель режима («внутренний релей Exchange» скрывает логин/пароль);
* задел на будущее: режим Microsoft Graph / EWS (OAuth-приложение в Entra ID) — поля настроек
  не меняются, добавляется транспорт;
* обязательны SPF/DKIM для адреса отправителя, иначе письма уйдут в спам;
* тема: `Ночной отчёт 19.10.2026 — замечания (Техническая служба)`;
* тело: HTML-таблица недостатков (объект, пункт, комментарий, кто, когда) + подписи;
* вложения: фото/видео до суммарного лимита (по умолчанию 20 МБ); сверх — ссылки
  `/api/photos/{id}/file` (требуют входа) или архив.

### 4.3 Шаблон и отправка

* шаблон текста хранится в `settings` (`night_dispatch_template`) с плейсхолдерами
  `{date} {shift} {service} {items} {duty} {author} {time}` — редактируется в «Интеграциях».
  `{duty}` — ночные батлеры смены (авторы отметок и те, за кем были закреплены объекты);
  `{deadline}` убран по решению владельца. Блок «Не проверено» (неотмеченные пункты)
  добавляется в `{items}` отдельным разделом;
* отправка **только вручную** с экрана «Недостатки смены»: «отправить всё скопом» или выбрать
  пункты (включая «не проверено») и каналы;
* одна отправка = одна запись `NightDispatch` **на канал и получателя** (чат/ящик),
  внутри — снимок недостатков (`items_json`) и текст как ушёл;
* отправка асинхронная по каналам, статусы `pending → sent|failed`, ретраи (3, экспоненциально);
* пункт, попавший в успешную отправку, помечается `dispatch_id`/`dispatched_at`
  и по умолчанию больше не предлагается (фильтр «не отправленные»);
* **исправление после отправки уведомлений не порождает** (решение владельца): ни сообщения
  «исправлено», ни отзыва (Telegram `deleteMessage` не используем). В обходе такой пункт
  помечается бейджем «исправлено после отправки» — это видно супервайзеру, но наружу не уходит;
* **общие получатели не дедуплицируются**: отправка идёт по принципу «служба → её каналы → её
  получатели». Если один чат закреплён за несколькими службами, каждая служба отправит своё
  сообщение (ситуация нештатная: ожидается «одна служба — несколько чатов»);
* все действия пишутся в `audit` (`night_dispatch`, `notify_service_update`,
  `settings_integrations` — без значений токенов).

### 4.4 Хранение токенов

* `settings.telegram_bot_token`, `settings.smtp_password` — в общей таблице настроек;
* в API и в UI — **маскированные** (`has_token: true, masked: "••••••4f2a"`), полное
  значение только на запись и только при праве `settings.edit`;
* аудит изменений — без значений;
* опционально (этап 4+): шифрование значения ключом из `SECRET_KEY`
  (потребует `cryptography`);
* исходящие запросы — только `api.telegram.org` и настроенный SMTP-хост (защита от SSRF:
  произвольные URL из настроек не принимаются).

## 5. Медиа (фото и видео)

* `photos` расширяется `media_type`/`mime`/`duration_sec`; `ALLOWED_EXT` в `app/photos.py`
  дополняется `mp4`, `mov`, `webm` (видео), sniffing по magic bytes — как сейчас для картинок;
* лимиты настраиваются в «Интеграциях» так же, как у фото: `media_video_max_mb` — **50 МБ
  (подтверждено владельцем**, это лимит загрузки через Bot API), `photo_max_mb` (12),
  срок хранения медиа в днях;
* срок хранения: нынешний `photo_retention_days` → переименовать по смыслу в «срок хранения медиа»
  (ключ остаётся, чтобы не ломать боевые базы);
* отдача — только авторизованным (`/api/photos/{id}/file`), видео — с `Range`-заголовками
  для проигрывания в браузере;
* на смартфоне: `capture="environment"` для фото и `capture="camcorder"` для видео
  (в прототипе обе кнопки показаны).

## 7. Риски

* **Объём медиа**: видео по 30–50 МБ × десятки объектов → диск и резервные копии.
  Митигируется сроком хранения, лимитом размера и (опционально) сжатием/отказом от видео.
* **Лимиты Telegram**: 50 МБ на файл и 20 сообщений/мин на группу — при большом числе
  недостатков нужны альбомы и очередь, иначе часть не уйдёт.
* **Доставляемость писем**: SPF/DKIM корпоративного SMTP, размер вложений (~20–25 МБ).
* **Дубли уведомлений**: повторная отправка того же недостатка — лечится отметкой
  `dispatched_at` и фильтром «не отправленные».
* **Историчность**: правки справочников не должны менять закрытые смены — как и сейчас,
  всё фиксируется снимком (`snapshot_json`, `service_name`, `items_json`).
* **Миграция пунктов**: сейчас пункты принадлежат объекту, станут — зоне; перенос должен
  сохранить `item_id` в уже закрытых отчётах (колонка nullable, текст — снимок).

## 8. Открытых вопросов нет

Все решения получены (см. список в начале записки). Что понадобится на этапе интеграции —
не блокирует разработку:

* **Telegram**: токен бота и добавление бота в группы служб (после этого «Обновить список чатов»
  в настройках покажет их, а закрепление делается в карточке службы).
* **MS Exchange**: адрес релея/коннектора, порт и режим (релей без авторизации или SMTP AUTH),
  разрешённый адрес отправителя (SPF/DKIM). До получения этих данных отправка писем работает
  в тестовом режиме («Тестовое письмо» в настройках), чаты Telegram — уже полностью.
* **Объём медиа**: при десятках видео по 30–50 МБ за смену — согласовать диск и срок хранения
  (в настройках, по умолчанию 30 дней).

## 9. Что реализовано в прототипе (`docs/archive/prototypes/night-report-v2.html`)

Все двенадцать решений владельца показаны в макете и покрыты автотестом `smoke.mjs`
(jsdom, **120 проверок**, ошибок консоли нет):

* трёхуровневая навигация зоны → объекты → чек-лист: прогресс, перехваты, закрытие
  с неотмеченными пунктами (после подтверждения);
* **индивидуальный чек-лист объекта** — демо-данные: у «Виллы 4001» своя формулировка
  «Вилла убрана (включая детскую комнату)» и свой пункт «Детская кроватка установлена
  и исправна», у «Виллы 4002» отключён пункт «ТВ и Wi-Fi работают»; в обходе такие пункты
  помечены бейджами «индивидуально» и «пункт объекта»;
* медиа: съёмка фото (`capture=environment`) и видео (`capture=camcorder`), выбор из галереи,
  миниатюры с удалением, лимиты и срок хранения — в настройках;
* **Недостатки смены**: группировка по службам, чекбоксы каналов «чат / письмо», выбор
  «всё скопом» или вручную, блок «Не проверено» (неотмеченные пункты), предпросмотр текста
  с ночными батлерами смены, отправка → журнал;
* **журнал отправок**: канал, получатель, число недостатков и «не проверено», статус,
  ошибка SMTP и «Повторить», просмотр ушедшего текста;
* справочники обхода: зоны, объекты (мастер «серия»), пункты зоны, **правки объекта**,
  службы (каналы, ящик и копия, чаты из общего списка, «Тест доставки»);
* **общий экран «Чаты и Почта»** (Настройки → Служебное): токен бота с маскировкой, getMe,
  getUpdates → каталог чатов, SMTP/MS Exchange (релей или SMTP AUTH), шаблоны сообщений
  **по разделам**, лимиты медиа, таблица «кто использует доставку», ссылка на общий журнал;
* **переключатель роли** в топбаре: у батлера справочники скрыты (нет `settings.edit`),
  обход и отправка недостатков доступны;
* **MS Exchange** в настройках почты: режим «внутренний релей» (скрывает логин/пароль)
  или SMTP AUTH, подсказка про коннектор, SPF/DKIM и перспективу Graph/EWS;
* **«исправлено после отправки»**: если недостаток устранили позже — бейдж в обходе,
  наружу ничего не уходит;
* подсказка о том, что общие чаты служб не объединяются: каждая служба шлёт своё сообщение;
* шаг **«Проверка электрокаров» — отдельной панелью** (как в текущей версии, см. PR #43).
