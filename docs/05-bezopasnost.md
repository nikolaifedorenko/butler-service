# 5. Вход, права, безопасность

О найденной уязвимости сообщайте по правилам из [`SECURITY.md`](../SECURITY.md).

## 5.1 Общая схема

Серверная сессия: случайный токен в HttpOnly-cookie и запись о нём в таблице `user_sessions`
(без JWT и OAuth; ADR-0013, раздел 8).

```
логин + пароль → проверка argon2id → токен (256 бит случайности) → HttpOnly-cookie
                  ↓                              ↓
             таблица users              каждый запрос API: SHA-256(токен) → user_sessions
                                        (срок, пользователь, сотрудник) → Principal(роль, сотрудник)
```

Учётная запись (`users`) привязана к сотруднику (`employees`) через `employee_id`; у
администратора привязки может не быть. Код — `app/core/auth.py`, `security.py`, `sessions.py` и
`modules/access/application/auth.py`.

## 5.2 Пароли

* Хранение — строка argon2id (`$argon2id$v=19$m=…,t=…,p=…$соль$хеш`), библиотека `argon2-cffi`,
  параметры по умолчанию (профиль RFC 9106). Если параметры ужесточат, хеш пересчитывается при
  следующем входе (`needs_rehash`). Хеши другого формата не принимаются.
* Сравнение выполняет библиотека за постоянное время. Для несуществующего логина хеш считается
  всё равно — по времени ответа логин не угадать.
* Минимальная длина — 8 символов (`MIN_PASSWORD_LEN`), политики сложности нет (внутренний инструмент).
* Пароль не логируется; смена — «Сотрудники» → «Изменить» (поле «Новый пароль») или
  «Сменить пароль» в шапке; пишется в журнал аудита.
* Демо-пароль `demo1234` — только для демо-базы.

## 5.3 Сессии

* Токен — `secrets.token_urlsafe(32)`, содержимого не несёт. В `user_sessions` хранятся SHA-256
  токена (утечка таблицы не даёт рабочих cookie), пользователь, сотрудник («чьими глазами»),
  флаг `impersonated`, срок. Подделать токен нельзя: записи о нём не будет.
* Cookie `tt_session`: `HttpOnly`, `SameSite=Lax`, `Path=/`, срок `SESSION_TTL_HOURS` (48 ч);
  `COOKIE_SECURE=1` добавляет `Secure` (включайте за HTTPS).
* Отзыв — удаление записи. Выход, смена пароля, смена роли или пароля администратором,
  увольнение и удаление сотрудника удаляют **все** сессии пользователя на всех устройствах;
  вход «как сотрудник» заменяет текущую сессию. Просроченные записи удаляются при открытии новой.
  Отключённая учётка (`is_active = false`) теряет доступ сразу.
* Неизвестный, просроченный или отозванный токен → `401`, интерфейс показывает форму входа.
* Лимит попыток входа — таблица `login_attempts`, общая для всех процессов: 10 неудач за 5 минут на
  пару «адрес + логин» и 50 на адрес. IP берётся из `X-Forwarded-For` только при
  `TRUST_PROXY_HEADERS=1`.

## 5.4 Роли, права, группы

* Роли — данные (таблица `roles`, ADR-0011): `admin`, `manager`, `supervisor`, `employee` и
  свои. У роли есть уровень; обладатель управляет учётками и назначает роли не выше
  `max_assignable_rank` (`can_manage_user`, `core/auth_guards.py`).
* Права — каталог `PERMISSIONS`, который собирают манифесты модулей (`core/permissions.py`).
  Единственная проверка в роутерах — `require_perm("<ключ>")`. Права выдаются грантами роли,
  группы или пользователя; запрет (`deny`) сильнее разрешения, индивидуальный грант сильнее
  группового. Экран — «Настройки → Права доступа».
* Роль вне ядра прав не читает никто (страж `tests/test_permissions_unification.py`).
* Данные сотрудника дополнительно фильтруются: он видит в `/api/punches` только свои строки;
  уровень шахматки «Загрузка без гостей» не получает с сервера ни одного поля гостя.

## 5.5 Режим «как сотрудник»

Менеджер: «Сотрудники» → «Открыть как сотрудник» → `POST /api/auth/impersonate` (право
`employees.impersonate`, плюс `can_manage_user`). Открывается новая сессия с флагом
`impersonated` и сотрудником-целью, прежняя удаляется. В шапке — жёлтый индикатор и кнопка
«Вернуться». Права в режиме — ровно как у сотрудника; действия пишутся в аудит с пометкой «→ как».
Отключается `ALLOW_IMPERSONATION=0`.

## 5.6 CSRF, заголовки, CSP

* CSRF — double-submit: токен в читаемой JS cookie `tt_csrf` и заголовок `X-CSRF-Token`,
  сравнение побайтово до вызова обработчика (ADR-0004). `POST /api/auth/login` исключён.
* CSP: `script-src 'self'`, `style-src 'self' 'unsafe-inline'` (осознанный компромисс), закрыты
  `object-src`, `base-uri`, `form-action`, `frame-ancestors 'none'`. Внешние ресурсы запрещены:
  шрифты и библиотеки лежат в репозитории. `CSP_REPORT_ONLY=1` — для осторожной раскатки.
* Заголовки: `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Permissions-Policy`;
  HSTS — только когда запрос фактически по TLS.
* Разметка интерфейса экранируется шаблонами lit-html; `innerHTML` запрещён линтером.
* Загрузки: проверка по содержимому (не по имени), лимиты размера, защита от zip-бомб; выгрузки в
  CSV и Excel защищены от formula injection.

## 5.7 Шифрование секретов уведомлений

Токен Telegram-бота и пароль SMTP хранятся в базе зашифрованными (Fernet, ключ
`NOTIFY_SECRET_KEY`; `новый,старый` — смена ключа). В базе и бэкапах только шифротекст.

## 5.8 Журнал аудита

Таблица `audit_log`: кто, когда, что (`login`, `logout`, `impersonate`, `password_change`,
изменения графика, отметок, настроек, сотрудников…) и данные в JSON. Экран — «Настройки →
Журнал аудита» (право `audit.view`). Запись делает операция прикладного слоя внутри своей
транзакции.

## 5.9 Чек-лист перед боевым запуском

- [ ] HTTPS настроен, `COOKIE_SECURE=1`, `TRUST_PROXY_HEADERS=1` (за своим nginx);
- [ ] `NOTIFY_SECRET_KEY` задан, копия хранится вне сервера;
- [ ] `ADMIN_PASSWORD` задан; демо-учёток нет (`DEMO_SEED=0`);
- [ ] `ALLOW_IMPERSONATION=0`, если режим «как сотрудник» не нужен;
- [ ] `API_DOCS=0`: Swagger и `/api/openapi.json` выключены (в прод-профиле по умолчанию);
- [ ] бэкапы по расписанию, восстановление проверено (`deploy/README.md`, раздел 4);
- [ ] nginx: ограничение тела запроса, скрытие `Server`-заголовков по политике.

## 5.10 Осознанно не сделано

* двухфакторная аутентификация (при необходимости — TOTP поверх `users`);
* список своих сессий и отзыв одной из них в интерфейсе (отзыв есть при выходе и смене пароля);
* политика сложности пароля и срок его действия.
