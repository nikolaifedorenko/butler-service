# ADR-0002. Миграции схемы: Alembic (пересмотрено 21.10.2026)

**Статус:** принят 15.10.2026 («самодельные шаги, Alembic отложен»), **пересмотрен 21.10.2026**:
переход на Alembic выполнен (аудит 21.10.2026, находки DB-01…DB-06; материалы аудита в
репозиторий не входят, итоги — в `CHANGELOG.md`).

## Контекст
Модуль `bootstrap/migrations.py` (~770 строк, удалён 22.10.2026) выполнял raw-DDL при каждом старте. Без таблицы
версий применённое угадывалось по наличию колонок, а проверки на PostgreSQL не было. Итог
аудита: базы старше 18.10 не обновлялись (DB-01), на PostgreSQL старт падал
(`boolean = integer`, DB-02), тип колонки в существующих базах нельзя было поменять (DB-06),
а пустые и противоречивые шаги шли при каждом старте (DB-03).

## Решение
* Схема ведётся ревизиями Alembic: `app/bootstrap/alembic/versions/`. `0001_baseline` — схема
  `main 3801abf` вместе с индексами, которые базы получали шагами `migrate_night_*`.
* `init_db()` (под `startup_lock`, как и раньше):
  * пустая база — `upgrade head`, схема целиком из ревизий;
  * база под Alembic (есть `alembic_version`) — `upgrade head`;
  * база до перехода (таблицы есть, `alembic_version` нет) — с 22.10.2026 не обновляется:
    старт падает с понятным текстом. Прежние шаги обновления таких баз удалены вместе с
    `migrations.py` — боевых баз на старых версиях нет (решение владельца), демо-базу
    создают заново.
* Страж — `tests/test_db_upgrade.py`: `alembic check` (модели = ревизии), отказ на базе без
  Alembic. Тесты идут на SQLite и PostgreSQL 16 (CI-джоб `postgres`).

## Последствия
* Изменение схемы = правка модели + `alembic revision --autogenerate -m "…"` (адрес БД из
  `DATABASE_URL` / `.env`), ревизию проверить глазами. Без ревизии падает
  `test_models_match_migrations`.
* Legacy-путь (прежние шаги + `create_all` + `stamp 0001`) удалён 22.10.2026: ревизии
  `0005`–`0007` уже создавали таблицы и колонки, и его держали только стражи идемпотентности
  в этих ревизиях (они безвредны и оставлены).
* **Отдельный шаг деплоя (22.10.2026, фаза 5 аудита).** `python -m app.bootstrap.migrate`
  выполняет `init_db()` целиком: ревизии, справочники движка, сид или первого администратора.
  В прод-профиле это сервис `migrate` (`docker-compose.prod.yml`); `app` стартует после его
  успешного завершения (`service_completed_successfully`) с `MIGRATE_ON_START=0` и только
  сверяет ревизию (`schema_version.ensure_current`). При отставании схемы воркер не стартует и
  пишет, какую команду выполнить. Локально и в демо-compose (`MIGRATE_ON_START=1`, по
  умолчанию) всё по-прежнему делает первый воркер; `startup_lock` остаётся страховкой.
