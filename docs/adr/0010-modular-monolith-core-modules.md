# ADR-0010. Модульный монолит: `core/` + `modules/` вместо «прагматичной границы»

**Статус:** предложен 19.10.2026 (вместе с `docs/EXECUTION-SPEC-v2.md`).
Заменяет ADR-0006 («Прагматичная граница чистой архитектуры») — при принятии
тому ставится статус `superseded by ADR-0010`.

## Контекст

ADR-0006 (15.10.2026) сознательно ограничил строгую гексагональную архитектуру
расчётным движком (`app/engine/`), оставив остальные поддомены (night, cars,
employees, справочники) «прагматичным грязным краем» с постепенным вытаскиванием
use-case'ов «по мере правок, без big-bang-рефакторинга».

За прошедшие недели проект вырос: 9 разделов интерфейса, ~40 Python-модулей вне
движка, общий слой доставки `app/notify`, справочники, переехавшие в единый центр
«Настройки» (PR #50). Внешний аудит (EXECUTION-SPEC, ред. 2026-10-20) предложил
полную модульную перестройку; его ревизия (`EXECUTION-SPEC-v2.md`) подтвердила
предпосылки и устранила исполнительские дефекты.

Аргументы «за»:
* единый предсказуемый каркас для всех поддоменов — онбординг (человек или
  LLM-агент) не изучает два разных стиля кода;
* границы модулей закреплены инструментами (import-linter, AST-тесты), а не
  договорённостью в ревью;
* межмодульные связи становятся явными (только `application`/`ports`), что
  сдерживает срастание night ↔ notify ↔ cars;
* боевой базы нет — цена ошибки переноса минимальна, окно рефакторинга свободно.

Аргументы «против» (честно):
* ADR-0006 предупреждал именно о big-bang: перестройка даёт большой диф без
  изменения поведения;
* для одного разработчика + агентов унификация — удобство, а не необходимость;
* риск затягивания и заморозки продуктовых батчей на 1–2 недели (фазы 3–7).

## Решение

Принять модульный монолит с постепенным исполнением (не big-bang):

1. `app/core/` — инфраструктура без бизнес-логики и без знаний о модулях (R5).
2. `app/modules/<name>/` — 9 гексагонов (timesheet, employees, night, cars, docs,
   notify, settings, access, audit), каждый со слоями domain/application/ports/
   adapters/interface; тривиальный слой может быть файлом.
3. Composition root (`main.py` + `bootstrap.py`) — единственное место, импортирующее
   все модули: роутеры, хэндлеры ошибок, реестр моделей, seed, миграции.
4. Правила R1–R6 (EXECUTION-SPEC-v2 §3) закрепляются `.importlinter` и AST-тестами
   после каждой фазы, а не в конце.
5. Фронтенд остаётся SPA без сборки (ADR-0008): реорганизация в `static/js/modules/`
   БЕЗ отказа от глобальных функций и связки `gen_js_globals` + ESLint `no-undef` —
   она ловит класс регрессий («пропавшая» функция раздела → пустой экран), который
   namespace-объект (`window.App.modules.*`) не ловит статистически.
6. Права — только каталог `PERMISSIONS` + `require_perm` (продолжение `night.edit`
   из PR #50); ролевые `require_manager`/`require_supervisor` удаляются после
   добавления недостающих ключей. Исключение — `can_manage_user`: это страж
   иерархии ролей (анти-эскалация), а не право; остаётся в `core/auth_guards.py`.
7. Перестройка идёт фазами 0–9 (EXECUTION-SPEC-v2 §7), каждая фаза — зелёный CI
   (§7.1) и отдельный коммит/PR; фазы 1–2 (чистка мёртвого кода, унификация прав)
   полезны независимо от исхода перестройки и могут быть выполнены сразу.

## Последствия

* Домен движка v7.1 не меняется: перенос `app/engine/**` → `modules/timesheet/**`
  механический, законы AST-тестов сохраняются (обновляются префиксы путей).
* API-контракты не меняются: `docs/openapi.json --check` без дельты после каждой фазы.
* Поведение ролей не меняется: новые ключи прав базово выданы тем же ролям, что и
  прежние ролевые проверки.
* Стоимость: ~4–6 рабочих дней агентной работы, 15–25 коммитов, окно заморозки
  фичевых веток на фазах 3–7.
* Выигрыш: единый каркас, машинопроверяемые границы, дешёвое добавление новых
  поддоменов (шаблон модуля), явные межмодульные контракты.
* Если перестройка будет остановлена между фазами — проект остаётся в валидном
  состоянии на любой фазе (транзитные re-export'ы и контракты), откат = revert фазы.
