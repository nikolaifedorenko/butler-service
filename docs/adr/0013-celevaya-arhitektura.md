# ADR-0013. Целевая архитектура: время, модули, задачи, интерфейс

**Статус:** принят 12.11.2026 (решения владельца 08–12.11.2026). Развивает ADR-0010 (модульный
монолит) и ADR-0012 (манифест модуля). Заменяет ADR-0003 (PBKDF2), ADR-0005 (лимит входа в
памяти) и ADR-0007 (формат токена сессии) — в части, описанной в разделе 8; уточняет ADR-0008
(фронтенд без сборки) — раздел 7. ADR-0002 (отложенный Alembic) утратил силу: Alembic введён.

## Контекст
Система выросла из учёта рабочего времени в рабочее место батлерской службы: табель, ночной
отчёт, электрокары, документы, шахматка с гостями и бронями. Владелец планирует, по порядку:
импорт броней из выгрузки Fidelio (CSV), прямое подключение к базе Fidelio, статусы уборки
номеров и вилл, развитие работы с гостями (CRM), расчёты с гостями. В дальней перспективе
система может заменить PMS. Отель сейчас один; второй возможен в будущем, со своим Fidelio.

Аудит кода 12.11.2026 показал, что переписывать систему с нуля не нужно, но три свойства
нынешнего кода после запуска с данными пришлось бы менять по всему коду (первые два — сейчас,
третье — когда появится второй отель):

* время: 72 колонки даты-времени без часового пояса, часть хранит местное время, часть UTC;
* правила и транзакции живут в роутерах (282 из 291 `HTTPException` и 132 из 153 `commit` —
  в слое `interface`), ответы 273 эндпоинтов не описаны моделями;
* ни одна таблица не привязана к отелю, часовой пояс один на приложение.

Боевых данных нет, поэтому схему можно менять без переноса данных. Приоритет — качество, не
скорость. Python — только последняя версия (3.15), запуск в проде — только Docker.

## Решение

### 1. Один отель, второй — возможность
Система строится для одного отеля (решение владельца 12.11.2026). Сущность «отель», привязка
таблиц к отелю и права с учётом отеля сейчас не вводятся. Чтобы второй отель потом добавлялся
без переделки, соблюдаются четыре правила:

* часовой пояс и гостиничные сутки читаются через одну функцию ядра, а не из настройки
  напрямую — при втором отеле она получит параметр «отель»;
* гости, сотрудники, учётные записи и права не содержат ничего, что относится к одному отелю;
* всё, что относится к объекту размещения (фонд, брони, блоки, недоступность), достижимо от
  корня фонда — привязка к отелю добавится одной колонкой у корня, а не в каждой таблице;
* внешний идентификатор хранит экземпляр внешней системы (раздел 6): два Fidelio различимы.

Настройки, табель, ночной отчёт и электрокары остаются общими на систему. Их привязка к отелю —
отдельное решение, когда второй отель появится.

### 2. Время
* Момент (отметка, создание записи, событие) — `timestamptz`, в базе всегда UTC.
* Длительность (часы смены, банк) — целое число минут.
* Гостиничная дата (заезд, выезд, ночь, день табеля) — `date`.
* Местное время получается из момента и часового пояса отеля — через одну функцию ядра (раздел 1).
* Деньги (когда появятся) — целое число минимальных единиц и код валюты; журнал начислений
  неизменяемый, исправления — сторнирующими записями.

### 3. База данных
* Только PostgreSQL, в том числе локально и в тестах (docker compose). Ветки для SQLite удаляются.
* JSON хранится в `JSONB`.
* Запрет двойной занятости объекта дублируется ограничением базы (`EXCLUDE` по диапазону).
* Миграции 0001–0020 заменяются одной начальной; дальше — обычные ревизии Alembic.

### 4. Слои и контракт
* Роутер (`interface`) разбирает запрос, проверяет право и вызывает прикладную функцию.
* Прикладной слой (`application`) владеет транзакцией и проверками; его вызывают и роутеры, и
  импорт, и фоновые задачи.
* Домен (`domain`) — чистые функции без базы и фреймворка.
* У каждого эндпоинта есть модель запроса и модель ответа; `docs/openapi.json` — контракт,
  по которому проверяется фронтенд.
* Ошибки — типизированные исключения, которые `main.py` переводит в статусы HTTP.

### 5. Модули
Модуль — граница, внутри которой правила меняются вместе и у данных один владелец.

| Вид | Модули | Зависят от |
|---|---|---|
| Ядро | `core` — база, конфигурация, время, ошибки, вход, права, наблюдаемость | — |
| Общие справочники | `people` (сотрудники, периоды работы, группы), `fund` (объекты, категории, версии фонда), `access`, `settings`, `audit` | ядро |
| Предметные | `timesheet`, `guests`, `stays` (брони, блоки, недоступность, размещение), `night`, `cars`, `docs` | ядро, справочники |
| Сквозные сервисы | `exchange` (импорт и экспорт файлов), `notify`, `jobs` (очередь задач) | ядро |
| Представления | `board` (шахматка, «Сегодня», сводки) — только чтение, своих таблиц нет | предметные, через порты |

* Предметные модули не импортируют друг друга. Нужные данные модуль получает через порт,
  который объявляет сам; адаптер подключается в `bootstrap`.
* Брони, блоки и недоступность объектов остаются в одном модуле: у них общий инвариант —
  объект не занят дважды.
* Циклы между модулями запрещены. Слой модуля задаёт поле `layer` его манифеста: модуль
  импортирует только модули слоёв ниже, соседи по слою друг друга не импортируют. Контракт
  import-linter по слоям генерирует `tools/gen_importlinter.py`; то же проверяет тест
  архитектуры. Слои на 13.11.2026, снизу вверх: 1 — `people`, `exchange`; 2 — `timesheet`,
  `cars`, `notify`, `audit`; 3 — `night`; 4 — `employees`, `access`, `stays`, `docs`;
  5 — `settings`.
* Что нижнему модулю нужно от верхнего, он получает без импорта: функцию подключает
  `bootstrap` (поиск вида заявления для Графика) либо модуль объявляет её в манифесте
  (`overview_checks` — сверки для экрана «Настройки → Обзор»).
* Ядро не ссылается на модули даже в аннотациях типов.
* Модули под будущие возможности (уборка, расчёты) заранее не создаются.

### 6. Интеграции и фоновые задачи
* У гостя и брони — внешний идентификатор из трёх частей: система, экземпляр, идентификатор.
  Повторный импорт обновляет запись, а не создаёт вторую.
* Импорт — конвейер: сырые строки, сопоставление полей, проверка, предпросмотр, фиксация.
  Адаптер внешней системы переводит её данные в команды прикладного слоя; модель Fidelio в
  систему не копируется.
* Источник броней — порт с двумя адаптерами: файл и подключение к базе.
* Фоновые задачи (синхронизация, очередь уведомлений, очистка медиа) выполняет очередь на
  PostgreSQL с повторами и расписанием; свой фоновый поток и файловые замки удаляются.
* Связь между модулями «после события» — синхронные доменные события внутри процесса после
  фиксации транзакции. Внешний брокер сообщений не вводится.
* PDF из DOCX делает отдельный контейнер Gotenberg; свой рендер на reportlab удаляется.

### 7. Интерфейс
* Сборки по-прежнему нет (ADR-0008); скрипты становятся ES-модулями, глобальные имена и
  `tools/js_globals.json` удаляются.
* Разметка строится шаблонами `lit-html` с экранированием по умолчанию; прямое `innerHTML`
  с ручным `esc()` не используется.
* Дизайн-система: токены (цвет, шрифт, отступы, светлая и тёмная тема) и набор компонентов;
  экраны собираются только из них. Фирменный стиль (палитра, Manrope, Playfair Display)
  сохраняется.
* Стартовый экран — «Сегодня», свой для каждой роли. Телефон — отдельный сценарий, а не
  сжатый десктоп. Карточка открывается боковой панелью. Поиск единый.
* Сценарии интерфейса проверяются в настоящем браузере (Playwright).
* Макеты «Шахматка» и «Сегодня» одобрены владельцем 12.11.2026.

### 8. Вход и сессии
* Пароли — argon2id (`argon2-cffi`); старые хеши не переносятся — данных нет.
* Сессия — случайный токен в cookie, запись в таблице базы; отзыв — удалением записи.
* Лимит попыток входа хранится в базе, как сейчас.

### 9. Инструменты
* Зависимости — `pyproject.toml` и `uv.lock` (`uv`), с хешами пакетов.
* Тесты идут параллельно (`pytest-xdist`), у каждого потока своя схема базы; файлы тестов
  разложены по модулям.
* В коде нет комментариев с историей решений: история — в git и ADR.

## Порядок работ
1. Этот ADR.
2. Модуль `people`, разрыв циклов между `employees`, `timesheet` и `docs`.
3. Только PostgreSQL: `timestamptz`, `JSONB`, `uv`, параллельные тесты.
4. Транзакции и проверки в прикладном слое, модели ответов.
5. Деление `stays` на `fund`, `guests`, `stays`, `board`; `exchange`; очередь задач.
6. Интерфейс: ES-модули, `lit-html`, дизайн-система, Playwright.
7. Сессии и argon2id.
8. Чистка кода и единая начальная миграция.
9. Документация заново, со сплошной нумерацией.

Каждый шаг — отдельный PR (большой шаг — два), с тестами и зелёным CI.

## Последствия
* Объём работ больше первоначальной программы; до импорта из Fidelio пройдут шаги 2–5.
* Локальный запуск требует Docker (PostgreSQL, Gotenberg); `run.sh` с SQLite уходит.
* В проде появляются два новых процесса: исполнитель очереди задач и Gotenberg.
* Существующие демо-базы не обновляются и создаются заново.
* Второй отель потребует отдельного ADR и миграции: сущность «отель», колонка у корня фонда,
  решение о настройках, табеле и правах. Правила раздела 1 делают это добавлением, а не
  переделкой.
* Не решено и будет решаться по образцам выгрузок Fidelio: состав полей импорта, правило
  «кто главнее» при расхождении с Fidelio, судьба автоматического размещения для броней,
  которые приходят с уже назначенным объектом.
