# ADR-0006. Прагматичная граница чистой архитектуры: engine — порты/адаптеры, app — ORM напрямую

**Статус:** принят 15.10.2026 · **заменён ADR-0010 (20.10.2026)** — модульный
монолит `core/` + `modules/`; исторический контекст сохранён

## Контекст
Расчётный движок v7.1 (`app/engine/`) — образцовая гексагональная архитектура,
законы enforced AST-тестами (`tests/engine/test_architecture.py`). Остальное
приложение (справочники, поддомены night/cars/presence, CRUD) живёт на
SQLAlchemy-моделях напрямую в API-модулях.

## Решение
Граница чистоты — осознанная: строгие порты/адаптеры обязательны только для
расчётного ядра (где цена ошибки — деньги и часы людей). CRUD-поддомены остаются
«прагматичным грязным краем» (ORM-модель = сущность), но с обязательным
сервисным слоем там, где есть правила: образец — `app/cars.py` + тонкий
`cars_api.py`, `tabel_fill.py`, `night.py`. Постепенное вытаскивание use-case'ов
из «божественных» роутеров (`employees.py`, `schedule.py`) — по мере правок в
них, без big-bang-рефакторинга.

## Последствия
Домен engine остаётся единственным носителем бизнес-правил расчёта;
дублирование расчётной логики в API-слое запрещено ревью.

**Дополнение 15.10.2026 (сервисный слой материализован):** созданы
`app/services/` — `errors.py` (доменные ошибки, main.py маппит их в HTTP),
`employee_lifecycle.py` (перевод/блок/увольнение/повторный приём),
`punch_plan.py` («план на сегодня» — был нужен двум api-модулям),
`engine_common.py` (мост к движку, переехал из api). Перекрёстные импорты
api устранены (photos-кейс — через сервис `app/photos.py`). Внедрён
**import-linter** (`.importlinter`, шаг CI): слои api → services → models,
независимость 17 api-модулей, изоляция движка от api/services/main.
Правило бойскаутов действует: следующая правка бизнес-логики в роутере —
повод вынести её в services. ORM-модели как сущности CRUD-поддоменов —
по-прежнему приемлемы (см. Решение).
